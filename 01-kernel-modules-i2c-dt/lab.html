The sections of the lesson showed every build with its output. This lab is the board work. You load the hello module and read its log. Then you bind the toy driver to a device in both orders. The last step is a writing exercise on virtcam_probe().

Goal

  • hello.ko loaded and unloaded on the board, with and without its parameter. Evidence: a transcript of its log lines.
  • toy_i2c.ko bound to a hand-made device, once with the driver first and once with the device first.
  • A worksheet that tags every line of virtcam_probe() with the five role tags.
  • No camera is used.

Hardware

  • Orin Nano devkit with JetPack 7.2.1 (Jetson Linux r39.2.1), reachable over SSH.
  • A host with Docker and the course container jetson-build-jp7.
  • The r39.2.1 tree in the container, built once per sections 1 and 2 of setup/canonical-commands.md.
  • Optional: a Raspberry Pi 5. The section On a Raspberry Pi 5 lists what differs.

Steps

Step 1 — Set the board variables (5 min)

  1. Every lesson addresses the board through two variables. Export them on the host:
host$ export BOARD_IP=<your board's IP>
host$ export BOARD_USER=nvidia

The exports print nothing. BOARD_USER is nvidia on a stock devkit image. The serial console or the router shows the address.

  1. Check the SSH connection and the kernel release:
illustrative, not captured on a board
host$ ssh "$BOARD_USER@$BOARD_IP" "uname -r"
6.8.12-1021-tegra

Write the string down. Step 2 compares it with the modules (verified-on-target: pending).

Step 2 — Build both modules and copy them out (10 min)

  1. From the root of the course clone, copy the two module directories into the container:
host$ docker exec jetson-build-jp7 rm -rf /build/hello /build/toy
host$ docker cp lessons/01-kernel-modules-i2c-dt/lab/hello jetson-build-jp7:/build/hello
host$ docker cp lessons/01-kernel-modules-i2c-dt/examples/toy jetson-build-jp7:/build/toy

The first line removes earlier copies and prints nothing. In a terminal, each docker cp prints one summary line.

  1. Build both modules as sections 1 and 3 of the lesson show. Each build must end with an LD [M] line.

  2. Read the version string of each file, and copy both files to the host:

host$ docker exec jetson-build-jp7 modinfo -F vermagic /build/hello/hello.ko /build/toy/toy_i2c.ko
6.8.12-1021-tegra SMP preempt mod_unload modversions aarch64
6.8.12-1021-tegra SMP preempt mod_unload modversions aarch64
host$ docker cp jetson-build-jp7:/build/hello/hello.ko .
host$ docker cp jetson-build-jp7:/build/toy/toy_i2c.ko .

The first field must equal the uname -r of Step 1. If it differs, stop: the board refuses both files.

Step 3 — Load hello and capture its log (15 min)

  1. Copy the module to the board. Load it, read its parameter from sysfs, and unload it:
illustrative, not captured on a board
host$ scp hello.ko toy_i2c.ko "$BOARD_USER@$BOARD_IP:~"
host$ ssh "$BOARD_USER@$BOARD_IP" "sudo insmod ~/hello.ko && cat /sys/module/hello/parameters/who && sudo rmmod hello" | tee lab01-transcript.txt
world

insmod and rmmod print nothing on success. The one output line is the default value of the parameter.

  1. Load it again with a parameter, unload it, and collect its log lines:
illustrative, not captured on a board
host$ ssh "$BOARD_USER@$BOARD_IP" "sudo insmod ~/hello.ko who=Orin && sudo rmmod hello && sudo dmesg | grep 'hello:'" | tee -a lab01-transcript.txt
[ 8042.113310] hello: hello world, this is Linux 6.8.12-1021-tegra
[ 8042.140244] hello: goodbye world
[ 8090.402113] hello: hello Orin, this is Linux 6.8.12-1021-tegra
[ 8090.418877] hello: goodbye Orin

You get one greeting and one goodbye for each load. The release in the greeting equals the uname -r of Step 1.

  1. Look for a line hello: loading out-of-tree module taints kernel. above the first greeting. Record whether it appeared. Section 2 states that it does not appear on a Jetson. That claim is not yet verified on a board.

    If sudo reports that a terminal is required, add -t to the ssh calls.

Step 4 — Bind the toy driver in both orders (20 min)

Run this step in an SSH session on the board.

  1. Check that the bus exists and that the address is free:
illustrative, not captured on a board
orin$ ls /sys/bus/i2c/devices/ | grep -c '^i2c-7$'
1
orin$ ls /sys/bus/i2c/devices/ | grep -c '^7-0050$'
0

Bus 7 is on pins 3 and 5 of the 40-pin header. Nothing needs to be connected to it. If the second count is 1, use another address in every later command.

  1. Driver first. Load the module, and then create the device:
illustrative, not captured on a board
orin$ sudo insmod ~/toy_i2c.ko
orin$ sudo dmesg | grep -c 'toy 7-0050'
0
orin$ echo toy-sensor 0x50 | sudo tee /sys/bus/i2c/devices/i2c-7/new_device
toy-sensor 0x50
orin$ sudo dmesg | tail -2
[ 2143.615482] toy 7-0050: bound at address 0x50
[ 2143.615561] i2c i2c-7: new_device: Instantiated device toy-sensor at 0x50

The count of 0 shows that loading the module did not run toy_probe(). The echo did.

  1. Read the bind from sysfs. The device has a link to its driver:
illustrative, not captured on a board
orin$ basename "$(readlink /sys/bus/i2c/devices/7-0050/driver)"
toy
  1. Remove the device, and read the two new log lines:
illustrative, not captured on a board
orin$ echo 0x50 | sudo tee /sys/bus/i2c/devices/i2c-7/delete_device
0x50
orin$ sudo dmesg | tail -2
[ 2201.118204] i2c i2c-7: delete_device: Deleting device toy-sensor at 0x50
[ 2201.118260] toy 7-0050: unbound

toy_remove() ran because the device left. The module is still loaded.

  1. Device first. Unload the module, create the device, and then load the module:
illustrative, not captured on a board
orin$ sudo rmmod toy_i2c
orin$ echo toy-sensor 0x50 | sudo tee /sys/bus/i2c/devices/i2c-7/new_device
toy-sensor 0x50
orin$ sudo dmesg | tail -1
[ 2260.402113] i2c i2c-7: new_device: Instantiated device toy-sensor at 0x50
orin$ sudo insmod ~/toy_i2c.ko
orin$ sudo dmesg | tail -1
[ 2275.730018] toy 7-0050: bound at address 0x50

This time the insmod ran toy_probe(). Write down which process ran the probe in each order.

  1. Clean up. Remove the device first, and then the module:
orin$ echo 0x50 | sudo tee /sys/bus/i2c/devices/i2c-7/delete_device
orin$ sudo rmmod toy_i2c

None of the transcripts of this step is captured on a board yet (verified-on-target: pending). Record what your board prints.

Step 5 — Annotate the probe on paper (20 min)

  1. Print this listing, or open virtcam/virtcam.c at the annotated range:
virtcamvirtcam.clines 285–347
#if defined(NV_I2C_DRIVER_STRUCT_PROBE_WITHOUT_I2C_DEVICE_ID_ARG) /* Linux 6.3 */
static int virtcam_probe(struct i2c_client *client)
#else
static int virtcam_probe(struct i2c_client *client,
             const struct i2c_device_id *id)
#endif
{
    struct device *dev = &client->dev;
    struct tegracam_device *tc_dev;
    struct virtcam *priv;
    int err;

    dev_info(dev, "probing virtual sensor assumed at addr 0x%02x\n",
         client->addr);

    if (!IS_ENABLED(CONFIG_OF) || !client->dev.of_node)
        return -EINVAL;

    priv = devm_kzalloc(dev, sizeof(struct virtcam), GFP_KERNEL);
    if (!priv)
        return -ENOMEM;

    tc_dev = devm_kzalloc(dev, sizeof(struct tegracam_device), GFP_KERNEL);
    if (!tc_dev)
        return -ENOMEM;

    priv->i2c_client = tc_dev->client = client;
    tc_dev->dev = dev;
    strscpy(tc_dev->name, "virtcam", sizeof(tc_dev->name));
    tc_dev->dev_regmap_config = &virtcam_regmap_config;
    tc_dev->sensor_ops = &virtcam_common_ops;
    tc_dev->v4l2sd_internal_ops = &virtcam_subdev_internal_ops;
    tc_dev->tcctrl_ops = &virtcam_ctrl_ops;

    err = tegracam_device_register(tc_dev);
    if (err) {
        dev_err(dev, "tegra camera driver registration failed\n");
        return err;
    }

    priv->tc_dev = tc_dev;
    priv->s_data = tc_dev->s_data;
    priv->subdev = &tc_dev->s_data->subdev;
    tegracam_set_privdata(tc_dev, (void *)priv);

    err = tegracam_v4l2subdev_register(tc_dev, true);
    if (err) {
        dev_err(dev, "tegra camera subdev registration failed\n");
        tegracam_device_unregister(tc_dev);
        return err;
    }

    err = virtcam_power_on_probe(priv);
    if (err) {
        tegracam_v4l2subdev_unregister(tc_dev);
        tegracam_device_unregister(tc_dev);
        return err;
    }

    dev_info(dev, "virtcam sensor driver probed\n");

    return 0;
}
  1. Tag every non-blank line with at least one of the five tags of section 6:
Tag Meaning
[client] uses the bus device (i2c_client), or logs through it
[priv] allocates or links the private state
[framework] builds, configures or registers a framework object
[dt] reads the device tree
[power] clocks, regulators, GPIOs, power state

A line that links structs can take several tags. A log line takes the tag of the object that it logs through. Skip braces, blank lines and the preprocessor lines.

  1. Record your answers in this worksheet, one row for each group of statements:
# Code (abridged) Tag(s) What it does (one clause)
1 virtcam_probe(client), the form that compiles on r39.2.1
2 dev = &client->dev
3 locals: tc_dev, priv, err
4 dev_info(dev, "probing virtual sensor assumed at addr 0x%02x\n", ...)
5 if (!IS_ENABLED(CONFIG_OF) ... ) return -EINVAL;
6 priv = devm_kzalloc(dev, sizeof(struct virtcam), ...)
7 tc_dev = devm_kzalloc(dev, sizeof(struct tegracam_device), ...)
8 priv->i2c_client = tc_dev->client = client;
9 tc_dev->dev = dev; + strscpy(tc_dev->name, "virtcam", ...)
10 tc_dev->dev_regmap_config = &virtcam_regmap_config;
11 tc_dev->sensor_ops / v4l2sd_internal_ops / tcctrl_ops = &...
12 err = tegracam_device_register(tc_dev); + error return
13 priv->tc_dev / priv->s_data / priv->subdev = ...
14 tegracam_set_privdata(tc_dev, (void *)priv);
15 err = tegracam_v4l2subdev_register(tc_dev, true); + unwind
16 err = virtcam_power_on_probe(priv); + two-step unwind
17 success dev_info + return 0;

Two rows need attention. Row 8: how many tags does one statement take? Row 12: which tags run inside that call?

Stretch — the ownership question (10 min)

Probe allocates priv and tc_dev with two devm_kzalloc() calls, although their lifetimes are equal. Answer in three to six sentences:

  1. Why does the driver keep struct tegracam_device behind a pointer, and not inside struct virtcam?
  2. What could break, now or after an update of the framework, if it were inside?

Two hints. The joystick driver gets its input device from devm_input_allocate_device() and does not embed it. In the r39.2.1 tree, tegracam_device_unregister() is in nvidia-oot/drivers/media/platform/tegra/camera/tegracam_core.c, lines 186–209. Note what it frees with devm_kfree(), and what it does not free.

On a Raspberry Pi 5

Steps 1 to 4 work on a Raspberry Pi 5 with these differences. None of them is verified on a board yet (verified-on-target: pending).

  • Build on the board. Install the kernel headers package of the distribution. Then run a plain make in a copy of lab/hello and of examples/toy. The default KDIR of the Makefile is the right one.
  • Do not use the container build. Its vermagic starts with 6.18.60-v8-16k. Compare it with uname -r on the board to see why.
  • The bus is i2c-1. It is on pins 3 and 5 of the 40-pin header. It exists after I2C is enabled in raspi-config. So the device name is 1-0050.
  • The taint line appears. The first external module prints loading out-of-tree module taints kernel. Record whether your board agrees.

Expected output

  • lab01-transcript.txt with the value of the parameter and the four log lines of hello. Add the taint line if one appeared.
  • Your notes of Step 4: the log lines of each order, and the process that ran the probe.
  • The worksheet of Step 5 with all 17 rows tagged and described.
  • Compare with ../solutions/SOLUTION.md only after all three exist.

Troubleshooting

Symptom Likely cause Fix
ssh: connect to host ... timed out wrong BOARD_IP, board off, or another subnet ping the board, read the address on the serial console, and export BOARD_IP again
make: *** ... No such file or directory. Stop. KDIR names a path that does not exist check the path with ls in the container
ERROR: Kernel configuration is invalid. the tree was unpacked and never built build it once per section 2 of the canonical commands
insmod: ERROR: ... Invalid module format the vermagic does not match compare modinfo -F vermagic with uname -r, and rebuild against the matching tree
insmod: ERROR: ... File exists an earlier copy is still loaded sudo rmmod it first
insmod: ERROR: ... Operation not permitted sudo is missing run the command with sudo
sudo: a terminal is required ... SSH without a terminal, and sudo asks for a password add -t to ssh, or work in an interactive session
tee: .../new_device: No such file or directory the bus number is wrong list /sys/bus/i2c/devices/ and use a bus that exists
tee: .../new_device: Device or resource busy another device has that address choose another address
rmmod: ERROR: Module toy_i2c is in use not expected for this driver delete the device first, then run rmmod again
grep 'hello:' prints nothing dmesg ran without sudo, or the log buffer rotated load the module again and read the log at once
