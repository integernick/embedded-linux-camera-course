Steps 1–3 — expected results

  • The transcript depends on the board, so no byte-exact answer exists. These conditions must hold.
  • Step 1: uname -r returns the first field of the vermagic that Step 2 prints. The container build gives 6.8.12-1021-tegra.
  • Step 2: each build ends with an LD [M] line. Both modinfo -F vermagic lines are equal.
  • The other fields of the string are configuration options. Only a full match lets the kernel load the file.
  • Step 3: insmod and rmmod exit 0 and print nothing. The evidence of a load is in the kernel log.
  • The first ssh prints world, the default of the parameter, read from sysfs.
  • The grep prints a greeting and a goodbye for each load, the second pair with Orin.
  • The release in the greeting equals uname -r, because utsname()->release reads it from the running kernel.
  • The taint line: section 2 states that it does not appear on a Jetson, because NVIDIA's out-of-tree modules set the flag at boot.
  • cat /proc/sys/kernel/tainted prints the flags as a number. Bit 12, value 4096, is the out-of-tree flag.

Step 4 — the two orders

  • Driver first: the insmod prints nothing, and the count of toy 7-0050 lines is 0. The bound line appears at the echo.
  • The process that ran toy_probe() is the tee that wrote to new_device. The I2C core calls probe() while it creates the device.
  • For that reason the bound line comes before the Instantiated device line. The core prints that line after the device exists.
  • Device first: the echo prints only the Instantiated device line. The bound line appears at the insmod.
  • The process that ran toy_probe() is insmod. The call of i2c_add_driver() in the generated entry function finds the waiting device.
  • At delete_device the core prints Deleting device first and then removes the device, so unbound comes second.
  • In both orders the driver made no transfer on the bus. The device existed because a line of text was written to sysfs.
  • That is the property that section 7 names for virtcam: a bind proves a match, not a sensor.

Rows with more than one defensible answer

  • Rows 4 and 17 as [client]. A log line takes the tag of the object that it logs through. These lines use only &client->dev. The answer "none" is defensible, and [framework] is not.
  • Row 8 with fewer than three tags. One statement writes the client pointer into both other structs. It is the whole pattern in one line.
  • Row 12 as [framework] only. The solution adds [dt] and [power], because parse_dt and power_get run inside that call.
  • Section 7 quotes the line of the framework that calls parse_dt. A print added to virtcam_parse_dt() shows the same on a board: the line appears before the banner.
  • Row 5 as [client]. The condition reads client->dev.of_node, and its subject is the existence of the node. [dt] is the tag that carries the information.
  • Check: count the tags. [framework] appears in about half of the rows.
  • A tegracam probe is mostly bookkeeping for the framework. That is why a sensor driver without hardware access can be this small.

Stretch — the ownership answer

Why a pointer and not an embedded struct

  • struct tegracam_device is an object of the framework, not of the driver.
  • The tegracam functions treat it as a separate handle. Its layout belongs to NVIDIA.
  • A pointer keeps that boundary visible in the type. Everything that struct virtcam points at has another owner.
  • The driver holds i2c_client and v4l2_subdev as pointers for the same reason.
  • An embedded struct would also tie the size and the layout of the private state to a struct that NVIDIA can change in any release.

What would break

Today nothing breaks. tegracam_device_unregister() frees the objects that the framework allocated, and only those:

Jetson Linux r39.2.1nvidia-oot/drivers/media/platform/tegra/camera/tegracam_core.clines 204–208
    devm_kfree(tc_dev->dev, entry);
    devm_kfree(tc_dev->dev, tc_dev->s_data->tegracam_ctrl_hdl);
    devm_kfree(tc_dev->dev, tc_dev->s_data->power);
    devm_kfree(tc_dev->dev, tc_dev->s_data);
    tc_dev->s_data = NULL;
  • It never frees tc_dev itself. The driver allocated tc_dev, so the devres of the driver frees it. With tc_dev embedded, this code still works.
  • The risk is a later version of tegracam that frees its handle or counts references to it.
  • The input framework already works that way. An input_dev is reference-counted and freed by the input core. So the joystick driver gets it from devm_input_allocate_device().
  • A struct input_dev inside struct qwiic_jsk would corrupt the heap. The final release of the input core would call kfree() on a pointer into the middle of the driver's allocation.
  • v4l2_subdev is the opposite case: it is designed to be embedded. The context of tegracam embeds one, and the Raspberry Pi driver embeds one in its private state:
Jetson Linux r39.2.1nvidia-oot/include/media/camera_common.hlines 225
    struct v4l2_subdev          subdev;
Raspberry Pi kernel 6.18drivers/media/i2c/imx477.clines 1023
    struct v4l2_subdev sd;
  • Three framework objects follow three different ownership rules.
  • With every object of another owner behind a pointer, an update of the framework never requires a new check of which kind the driver holds.
  • Lesson 08 uses this boundary when it examines what virtcam omits.

Mechanical verification

  • verify-build-jp7.sh builds hello and toy_i2c against the pristine kernel-noble tree. It asserts the vermagic, the aliases, and every number that the sections read from the sources.
  • verify-build-rpi.sh builds the same two modules against the pinned Raspberry Pi 6.18 tree. It asserts the diff of the joystick driver and the line numbers that section 7 quotes from imx477.c.
