1. A module is code that the kernel links at runtime

The kernel of a board is one image file, and the bootloader loads it once. A driver that is compiled into that image cannot change without a rebuild of the image and a reboot. So the kernel has a second way to receive code. A module is an object file that the kernel links into itself while it runs. Loading a module adds a driver to the running kernel, and unloading removes it.

The hello module

A complete module fits in 31 lines. The file lab/hello/hello.c greets at load time and says goodbye at unload time:

this course01-kernel-modules-i2c-dt/lab/hello/hello.clines 6–31
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt

#include <linux/init.h>
#include <linux/module.h>
#include <linux/utsname.h>

static char *who = "world";
module_param(who, charp, 0444);
MODULE_PARM_DESC(who, "name to greet at load time");

static int __init hello_init(void)
{
    pr_info("hello %s, this is Linux %s\n", who, utsname()->release);
    return 0;
}

static void __exit hello_exit(void)
{
    pr_info("goodbye %s\n", who);
}

module_init(hello_init);
module_exit(hello_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Greet at load, say goodbye at unload");

Four parts of this file occur in every module:

  • Entry and exit. module_init() names the function that the kernel runs at load. module_exit() names the function that it runs at unload. hello_init() returns 0 to accept the load, and a negative errno refuses it.
  • Logging. pr_info() writes to the kernel log, which dmesg reads. The file defines pr_fmt before its first #include, so every line carries the prefix hello:.
  • A parameter. module_param() turns the variable who into a load-time option: insmod hello.ko who=Orin. The third argument, 0444, makes its sysfs file read-only.
  • A license. MODULE_LICENSE() is read by the build and by the loader. Section 2 shows what each one does with it.
More detail: __init, __exit, and a writable string parameter
  • __init places the function in a section that the kernel frees once the load completes.
  • __exit code is dropped when the same source is built into the kernel image, because built-in code never unloads.
  • The kernel's printk.h supplies a default pr_fmt without a prefix. It does so only when no definition exists yet, which is why the definition comes before the first #include.
  • MODULE_PARM_DESC() sets the text that modinfo prints for the parameter.
  • A charp parameter with a write bit can be replaced through sysfs while the module runs. Each write frees the string that an earlier write stored. Code that kept the old pointer then reads freed memory.

The build

A module is built by the build system of the kernel, pointed at a kernel tree that is configured and built. The Makefile of the module has the two-part form of the kernel documentation:

this course01-kernel-modules-i2c-dt/lab/hello/Makefilelines 2–12
ifneq ($(KERNELRELEASE),)
obj-m := hello.o
else
KDIR ?= /lib/modules/$(shell uname -r)/build

all:
    $(MAKE) -C $(KDIR) M=$(CURDIR) modules

clean:
    $(MAKE) -C $(KDIR) M=$(CURDIR) clean
endif

Make reads this file twice. On the first read, from the shell, KERNELRELEASE is not set, so the all recipe runs. It starts make again inside the kernel tree with -C $(KDIR), and M= points back at this directory. On the second read, by the kernel's build system, KERNELRELEASE is set. So only the line obj-m := hello.o applies, and it requests hello.ko.

KDIR is the kernel tree. Its default is the build directory of the kernel that the building machine runs. A build for another machine sets it explicitly.

2. The kernel checks a module before it runs it

A module runs inside the kernel, with no protection between the two. So a module that was built for another kernel must not load. The loader makes two checks before it runs a line of the module, and the build makes a third. Each check has its own error message.

The version string

Every module file carries a description of the kernel that it was built for. modinfo prints it:

container$ modinfo hello.ko
filename:       /build/hello/hello.ko
description:    Greet at load, say goodbye at unload
license:        GPL
depends:
name:           hello
vermagic:       6.8.12-1021-tegra SMP preempt mod_unload modversions aarch64
parm:           who:name to greet at load time (charp)

The vermagic line is the description. Its first field is the kernel release, the string that uname -r prints on the board. The other fields are the configuration options that change the interface between a module and the kernel. The kernel builds the string from this macro:

Jetson Linux r39.2.1kernel/kernel-noble/include/linux/vermagic.hlines 42–47
#define VERMAGIC_STRING                         \
    UTS_RELEASE " "                         \
    MODULE_VERMAGIC_SMP MODULE_VERMAGIC_PREEMPT             \
    MODULE_VERMAGIC_MODULE_UNLOAD MODULE_VERMAGIC_MODVERSIONS   \
    MODULE_ARCH_VERMAGIC                        \
    MODULE_RANDSTRUCT

At load time, the loader compares the string of the module with its own:

Jetson Linux r39.2.1kernel/kernel-noble/kernel/module/main.clines 2091–2095
    } else if (!same_magic(modmagic, vermagic, info->index.vers)) {
        pr_err("%s: version magic '%s' should be '%s'\n",
               info->name, modmagic, vermagic);
        return -ENOEXEC;
    }

So a mismatch fails the load with ENOEXEC. insmod reports Invalid module format, and the kernel log names both strings.

Raspberry Pi 5 the module from the 6.18 build of section 1 carries a different string:

container$ modinfo -F vermagic hello.ko
6.18.60-v8-16k SMP preempt mod_unload modversions aarch64

The fields are the same and the release differs. So neither file loads on the other board. The release 6.18.60-v8-16k also belongs to this build of the pinned tree. A kernel that a distribution installs has its own release string, and uname -r on the board prints it (verified-on-target: pending).

Warning

insmod fails with Invalid module format.

  • Cause: the vermagic of the file does not match the running kernel. dmesg shows version magic '...' should be '...'.
  • Fix: compare modinfo -F vermagic <file>.ko with uname -r. Then rebuild with KDIR on a tree of the same release. Do not use insmod --force.
More detail: the second check, a CRC for each symbol
  • The word modversions in the string announces a second check. With CONFIG_MODVERSIONS, the kernel stores a CRC of the prototype of every exported symbol.
  • A module stores the CRC of each symbol that it imports. The loader compares the two.
  • A module whose CRCs differ is refused even when the strings match. The kernel logs disagrees about version of symbol for each such symbol.
  • The compiler takes part in neither check.

The out-of-tree mark

After the version check, the loader records where the module came from:

Jetson Linux r39.2.1kernel/kernel-noble/kernel/module/main.clines 2016–2021
    if (!get_modinfo(info, "intree")) {
        if (!test_taint(TAINT_OOT_MODULE))
            pr_warn("%s: loading out-of-tree module taints kernel.\n",
                mod->name);
        add_taint_module(mod, TAINT_OOT_MODULE, LOCKDEP_STILL_OK);
    }

The mark is a taint flag and not an error. The kernel stores it in /proc/sys/kernel/tainted and prints it in every crash report. So a report shows that code from outside the kernel tree was loaded. The message prints only for the first such module since boot.

Here the two boards differ. On a Jetson, NVIDIA's camera and GPU modules are out-of-tree modules too. They set the flag during boot, so hello.ko loads without the message. On a Raspberry Pi, the drivers come from the kernel tree. So the first external module prints the message (verified-on-target: pending, both boards).

The license decides which functions a module may call

The third check runs at build time. A kernel function that modules may call is exported in one of two ways: EXPORT_SYMBOL or EXPORT_SYMBOL_GPL. MODPOST refuses a module that calls a function of the second kind without a GPL-compatible license:

Jetson Linux r39.2.1kernel/kernel-noble/scripts/mod/modpost.clines 1765–1767
        if (!mod->is_gpl_compatible && exp->is_gpl_only)
            error("GPL-incompatible module %s.ko uses GPL-only symbol '%s'\n",
                  basename, exp->name);

That rule applies to every camera sensor driver of both boards. The file Module.symvers of NVIDIA's tree shows how the entry point of its camera framework is exported:

container$ grep -w tegracam_device_register /build/work-l4t-r39.2.1/Linux_for_Tegra/source/nvidia-oot/Module.symvers | cut -f2,4
tegracam_device_register    EXPORT_SYMBOL_GPL

The function is GPL-only, and so is every other function of that framework. The registration function of a mainline sensor driver, v4l2_async_register_subdev_sensor(), is exported in the same way. So a sensor driver for either board declares a GPL-compatible license, or it does not build.

Warning

The build stops in MODPOST with GPL-incompatible module ... uses GPL-only symbol.

  • Cause: the MODULE_LICENSE() string is not GPL-compatible, and the module calls an EXPORT_SYMBOL_GPL function.
  • Fix: declare a GPL-compatible license.

insmod loads one file, modprobe loads its dependencies

Two commands load a module. insmod <file>.ko loads one file and nothing else. modprobe <name> loads a module that is installed under /lib/modules/$(uname -r)/, and it loads the modules that it depends on first. It finds them in modules.dep, which depmod -a writes.

hello.ko depends on nothing: its depends: line above is empty. A sensor driver does depend on other modules. For example, virtcam calls into NVIDIA's framework, so its depends: line names the module tegra-camera.

Warning

insmod of a sensor driver fails, and dmesg lists Unknown symbol lines.

  • Cause: insmod never loads dependencies, and the module that exports those symbols is not loaded.
  • Fix: install the file under /lib/modules/$(uname -r)/, run depmod -a, and load it with modprobe.
Source: the line that the loader prints for each missing symbol

3. A driver registers, and the bus core calls probe

The hello module runs code at load and at unload, and nothing between. A driver has a different shape. At load it only announces itself. Its real work starts later, when the kernel finds a device for it. This section shows that shape on the smallest I2C driver.

The toy driver

The file examples/toy/toy_i2c.c is a driver for an invented device. It keeps one private struct for the device, and it logs. It never transfers a byte on the bus:

this course01-kernel-modules-i2c-dt/examples/toy/toy_i2c.clines 10–34
struct toy {
    struct i2c_client *client;
};

static int toy_probe(struct i2c_client *client)
{
    struct toy *priv;

    priv = devm_kzalloc(&client->dev, sizeof(*priv), GFP_KERNEL);
    if (!priv)
        return -ENOMEM;

    priv->client = client;
    i2c_set_clientdata(client, priv);

    dev_info(&client->dev, "bound at address 0x%02x\n", client->addr);
    return 0;
}

static void toy_remove(struct i2c_client *client)
{
    struct toy *priv = i2c_get_clientdata(client);

    dev_info(&priv->client->dev, "unbound\n");
}

The file has no module_init(). Its last lines replace it:

this course01-kernel-modules-i2c-dt/examples/toy/toy_i2c.clines 48–57
static struct i2c_driver toy_driver = {
    .driver = {
        .name = "toy",
        .of_match_table = toy_of_match,
    },
    .probe = toy_probe,
    .remove = toy_remove,
    .id_table = toy_id,
};
module_i2c_driver(toy_driver);

struct i2c_driver is the announcement: a name, two match tables, and the two functions probe and remove. module_i2c_driver() generates the entry and the exit function of the module:

Jetson Linux r39.2.1kernel/kernel-noble/include/linux/i2c.hlines 952–954
#define module_i2c_driver(__i2c_driver) \
    module_driver(__i2c_driver, i2c_add_driver, \
            i2c_del_driver)

So the generated entry function calls i2c_add_driver(), and the generated exit function calls i2c_del_driver(). Loading the module registers a driver with the I2C core. That is all. Registration is not probing, and no device is involved yet.

probe runs when a device and a driver meet

probe() needs two things: a registered driver and a device that the driver claims. The two arrive independently, and the kernel acts when the second one arrives. A board shows this with a device that is created by hand. The file new_device of an I2C bus creates a device from a name and an address:

illustrative, not captured on a board
orin$ sudo insmod toy_i2c.ko
orin$ echo toy-sensor 0x50 | sudo tee /sys/bus/i2c/devices/i2c-7/new_device
toy-sensor 0x50
orin$ sudo dmesg | tail -2
[ 2143.615482] toy 7-0050: bound at address 0x50
[ 2143.615561] i2c i2c-7: new_device: Instantiated device toy-sensor at 0x50

After the insmod, the log has no line from the driver: a driver exists and no device does. The echo creates the device, and the first log line is from toy_probe(). So the I2C core called probe() while it created the device. In the opposite order the result is the same. If the device is created first, probe() runs during the insmod (verified-on-target: pending).

Nothing is connected at address 0x50 of that bus. The driver still binds, because a device is an object of the kernel and not a proof of hardware. A real driver proves the hardware itself, inside probe(), with a first transfer. Section 7 shows a driver that does and a driver that does not.

Driver code runs in the context of its caller

A driver is not a program and not a thread. It is a set of functions, and the kernel calls them at defined moments:

  • probe() runs in the context of the side that arrived second. That is boot code that created the device, or the insmod process that loaded the module.
  • A system call on a device node of the driver, such as an ioctl(), runs inside the program that made the call.
  • Between those calls nothing in the driver runs, unless the driver starts a kernel thread, a timer or an interrupt handler.

The call of probe() is one line of the I2C core:

Jetson Linux r39.2.1kernel/kernel-noble/drivers/i2c/i2c-core-base.clines 586–589
    if (driver->probe)
        status = driver->probe(client);
    else
        status = -EINVAL;
More detail: the older probe with two arguments
  • Before Linux 6.3, probe() of an I2C driver had a second argument, a const struct i2c_device_id *. Before 6.1, remove() returned an int.
  • Both kernels of this course are newer. So toy_i2c.c has one form of each function.
  • A driver that also supports older kernels selects the form at compile time. virtcam.c does so with two #if blocks around its signatures, which section 7 quotes.
  • Lesson 16 — Porting the stack to JetPack 7.2.1 (Jetson Linux r39.2.1) covers the method behind those blocks.

Two kinds of devices: I2C and platform

The toy device and a camera sensor are I2C devices. Their bus has addresses, and the kernel represents each device as a struct i2c_client. Other blocks of a camera pipeline are not on a bus of that kind.

The CSI-2 receiver of an SoC, for example, is a block of registers in the memory map. The kernel calls such a block a platform device. A platform driver registers with module_platform_driver() and gets its probe() call in the same way. Lesson 03, section 1, shows where the two kinds meet.

4. A compatible string joins a node to a driver

Section 3 created a device by hand. A camera sensor is not created that way. Its device comes from the device tree, and one string pairs it with its driver. This section follows that string.

The two halves of a match

The driver's half is a table of strings. The toy driver has two tables:

this course01-kernel-modules-i2c-dt/examples/toy/toy_i2c.clines 36–46
static const struct of_device_id toy_of_match[] = {
    { .compatible = "toy,sensor" },
    { }
};
MODULE_DEVICE_TABLE(of, toy_of_match);

static const struct i2c_device_id toy_id[] = {
    { "toy-sensor" },
    { }
};
MODULE_DEVICE_TABLE(i2c, toy_id);

The first table serves devices from a device tree. "toy,sensor" follows the vendor,device convention of every compatible string. The second table serves devices that are created by name, and section 3 used it. The i2c_driver struct passes both tables to the I2C core, in .of_match_table and .id_table.

The device's half is a node of the device tree, under the node of an I2C bus. The file examples/toy/toy-node.dts holds such a node for the toy driver:

this course01-kernel-modules-i2c-dt/examples/toy/toy-node.dtslines 18–21
        toy@50 {
            compatible = "toy,sensor";
            reg = <0x50>;
        };

compatible is the string to match, and reg is the I2C address. Lesson 02 covers how a node of this kind reaches the kernel. This lesson needs one fact: when the I2C adapter probes, the I2C core creates one i2c_client for each child node.

How a device and a driver meet. The device-tree node becomes an i2c_client when the adapter probes. The module registers an i2c_driver when it loads. The I2C core compares the compatible strings when the second side arrives.

The diagram is also a method. A driver that does not probe has one broken link in this chain, and debugging starts by finding that link.

Warning

modprobe returns success, and dmesg has no line from the driver.

  • Cause: no match happened. Either the compatible strings differ, or the device-tree node does not exist.
  • Fix: look under /sys/bus/i2c/devices/. If no entry with the expected bus and address exists, the device half is missing. If the entry exists and has no driver link, the strings differ.

Autoloading uses the same tables

MODULE_DEVICE_TABLE() does not take part in the match. It copies the table into the module file, as aliases:

container$ modinfo -F alias toy_i2c.ko
of:N*T*Ctoy,sensorC*
of:N*T*Ctoy,sensor
i2c:toy-sensor

The first two aliases come from the device-tree table, and the third comes from the name table. depmod collects the aliases of every installed module in modules.alias. When the kernel creates a device, it sends an event with the alias of that device to userspace. udev answers with a modprobe of the module that claims the alias. That is how a sensor driver loads at boot without a command.

Warning

A driver probes after a manual insmod, and after a reboot it is absent with no error.

  • Cause: MODULE_DEVICE_TABLE() is missing. A second cause is a new file that was copied to the board without depmod -a.
  • Fix: add the macro, and run depmod -a after every install.

5. Three structs: bus device, private state, framework device

The toy driver has two structs: the i2c_client that the bus core made, and its own struct toy. It is not useful yet, because no program can reach it. A useful driver joins a kernel framework, the layer that gives a class of devices one interface to userspace. That adds a third struct, and the three together are the pattern of this lesson.

The three roles

  • The bus device is the kernel's handle to the device on its bus: struct i2c_client. The bus core creates it, and a driver never allocates one.
  • The private state belongs to the driver. Probe allocates it. It holds the way to the other two structs, and everything that the driver must keep between calls.
  • The framework device makes the hardware a member of a framework: an input device for the joystick, a V4L2 subdevice for a camera sensor.

On the Raspberry Pi, the sensor driver calls V4L2 directly. It owns the subdevice, so it embeds it.

On the Jetson, a sensor driver does not call V4L2 directly. The three-struct pattern in three drivers. The joystick driver points at its input device. The Raspberry Pi imx477 driver has the subdevice inside its private struct. The Jetson virtcam driver points at a tegracam handle and at a tegracam context, which holds the subdevice.

Five role tags for the lines of a probe

The course tags every line of a probe function with the role that it serves. Section 7 and the lab use these tags, and so do the lessons on driver anatomy:

  • [client]: the line uses the bus device: a transfer, an address, or a log line through it.
  • [priv]: the line allocates or links the private state.
  • [framework]: the line builds, configures or registers a framework object.
  • [dt]: the line reads the device tree.
  • [power]: the line acts on a clock, a regulator, a GPIO, or the power state.

    imx477->pad[IMAGE_PAD].flags = MEDIA_PAD_FL_SOURCE;
    imx477->pad[METADATA_PAD].flags = MEDIA_PAD_FL_SOURCE;

    ret = media_entity_pads_init(&imx477->sd.entity, NUM_PADS, imx477->pad);
    if (ret) {
        dev_err(dev, "failed to init entity pads: %d\n", ret);
        goto error_handler_free;
    }

    ret = v4l2_async_register_subdev_sensor(&imx477->sd);
    if (ret < 0) {
        dev_err(dev, "failed to register sensor sub-device: %d\n", ret);
        goto error_media_entity;
    }

    pm_runtime_mark_last_busy(&client->dev);
    pm_runtime_put_autosuspend(&client->dev);

    return 0;

error_media_entity:
    media_entity_cleanup(&imx477->sd.entity);

error_handler_free:
    imx477_free_controls(imx477);

error_power_off:
    pm_runtime_disable(&client->dev);
    pm_runtime_put_noidle(&client->dev);
    imx477_power_off(&client->dev);

    return ret;
}

One row has no counterpart. imx477_identify_module() is the first transfer on the bus. It reads the identity register of the sensor and compares it:

Raspberry Pi kernel 6.18drivers/media/i2c/imx477.clines 1836–1847

            expected_id, ret);
        return ret;
    }

    if (val != expected_id) {
        dev_err(&client->dev, "chip id mismatch: %x!=%llx\n",
            expected_id, val);
        return -EIO;

So the two drivers answer one question in opposite ways. With no camera connected, the Raspberry Pi driver fails its probe with failed to read chip id, and no device node appears. The virtcam probe succeeds with no camera, because it never asks. That also explains the position of the power step. The Raspberry Pi driver needs a powered sensor during probe, so it powers the sensor early. virtcam does not, so its power step comes last.

8. Cleanup, and the log that a probe leaves

A probe allocates memory and registers objects. Something must undo both when the driver unbinds or when probe fails halfway. The kernel undoes one kind by itself, and the driver undoes the other.

Allocations are released by the kernel, registrations by the driver

devm_kzalloc() attaches an allocation to a struct device. The driver core releases everything that is attached when the device loses its driver. That happens after remove() returns. It also happens when probe() fails, because the I2C core opens a group for these resources around the probe call. This mechanism is devres. It explains two properties of both sensor drivers: neither contains a kfree(), and an error path can return without freeing memory.

A registration is different. tegracam_device_register() and v4l2_async_register_subdev_sensor() have no managed form in these drivers. So the driver calls the matching unregister function itself, in reverse order.

Jetson the remove function of virtcam:

virtcamvirtcam.clines 349–365
#if defined(NV_I2C_DRIVER_STRUCT_REMOVE_RETURN_TYPE_INT) /* Linux 6.1 */
static int virtcam_remove(struct i2c_client *client)
#else
static void virtcam_remove(struct i2c_client *client)
#endif
{
    struct camera_common_data *s_data = to_camera_common_data(&client->dev);
    struct virtcam *priv = (struct virtcam *)s_data->priv;

    tegracam_v4l2subdev_unregister(priv->tc_dev);
    tegracam_device_unregister(priv->tc_dev);
    /* Deliberate defect, second half: mclk enabled in probe is still on. */

#if defined(NV_I2C_DRIVER_STRUCT_REMOVE_RETURN_TYPE_INT) /* Linux 6.1 */
    return 0;
#endif
}

remove() receives only the client. The first two lines walk the way of section 6: client, context, private state. Then the two registrations are undone, subdevice first.

Important

virtcam_remove() has a deliberate defect. Probe enables the sensor clock, and remove never disables it. So the clock keeps running after rmmod until a reboot. The lab of Lesson 08 demonstrates the defect and fixes it.

Raspberry Pi 5 the remove function of imx477:

Raspberry Pi kernel 6.18drivers/media/i2c/imx477.clines 2243–2256
static void imx477_remove(struct i2c_client *client)
{
    struct v4l2_subdev *sd = i2c_get_clientdata(client);
    struct imx477 *imx477 = to_imx477(sd);

    v4l2_async_unregister_subdev(sd);
    media_entity_cleanup(&sd->entity);
    imx477_free_controls(imx477);

    pm_runtime_disable(&client->dev);
    if (!pm_runtime_status_suspended(&client->dev))
        imx477_power_off(&client->dev);
    pm_runtime_set_suspended(&client->dev);
}

It has the same structure, and it has the step that virtcam omits: imx477_power_off(). The rule behind both functions is short. remove() is probe() in reverse, and every error path inside probe() is the first part of remove().

Warning

rmmod reports nothing, and a crash follows seconds later.

  • Cause: devres frees the private state right after remove() returns. A timer, a work item or an interrupt handler that still uses it then reads freed memory.
  • Fix: stop every such source in remove().
  • The joystick driver has no such source of its own. The input core owns its poller and stops it.

The name of a device in a log line

The dev_info() family puts two names before every message: the name of the driver and the name of the device. For an I2C device, the device name is the bus number and the address. So virtcam 9-001a means the driver virtcam, on I2C bus 9, at address 0x1a.

The address comes from the reg property of the node. The bus number is assigned at boot. Lesson 02, section 7, explains why it is 9 for a camera on the CAM0 connector of the Jetson. On a Raspberry Pi 5 the camera bus has another number, and the board shows it under /sys/bus/i2c/devices/ (verified-on-target: pending).

Every log line has a source line

A probe log can be predicted from the source, because every line of it is one call. The four dev_info() calls of virtcam are:

297:    dev_info(dev, "probing virtual sensor assumed at addr 0x%02x\n",

Self-check

insmod hello.ko fails on the board with Invalid module format. Which two strings must be compared, and what is the fix?
Show the answer
  • The vermagic of the file, from modinfo -F vermagic hello.ko, and the uname -r of the board.
  • dmesg names both, in its version magic '...' should be '...' line.
  • Fix: rebuild against the tree of the release that the board runs. Forcing the load is never the fix.
The hello.ko of the 6.18 container build has the release 6.18.60-v8-16k. A Raspberry Pi 5 runs a 6.18.60 kernel that its distribution installed. Does the file load?
Show the answer
  • Only if uname -r on the board prints exactly 6.18.60-v8-16k.
  • The first field of the vermagic is the whole release string, not only the version numbers. A distribution kernel has its own suffix.
  • The fix is a build on the board, against the headers of the running kernel.
toy_i2c.ko is loaded, and dmesg has no line from it. Is that an error?
Show the answer
  • No. Loading the module registers a driver, and registration is not probing.
  • toy_probe() runs when a device that the driver claims exists. Until then nothing in the driver runs.
A board boots with a camera overlay applied. The sensor module is loaded with modprobe minutes later. When was the i2c_client created, and what started probe()?
Show the answer
  • The client was created during boot, when the I2C adapter probed and the I2C core read its child nodes.
  • probe() ran at modprobe time. A bind needs both sides, and the driver arrived second.
MODULE_DEVICE_TABLE(of, ...) is deleted, and the module is rebuilt. sudo insmod still probes. What stopped working?
Show the answer
  • Loading at boot.
  • The module file has no alias now, so modules.alias does not list it. The modprobe that udev runs for the device finds no module.
  • The match uses .of_match_table, which did not change.
imx477_remove() and virtcam_remove() each receive only an i2c_client. How does each one reach its private state?
Show the answer
  • imx477: the client data is the subdevice. to_imx477() applies container_of(), because the subdevice is inside struct imx477.
  • virtcam: to_camera_common_data() gives the context of tegracam, again through container_of(). The member priv of the context is struct virtcam. Probe stored it with tegracam_set_privdata().
The probe of virtcam fails inside tegracam_v4l2subdev_register(). Which cleanup happens by itself, and which one is written in the driver?
Show the answer
  • By itself: the two devm_kzalloc() allocations. devres releases them when probe returns the error.
  • In the driver: tegracam_device_unregister(). A registration is not managed by devres, so the error path undoes it.
No camera is connected. On which board does the sensor driver of this lesson still probe, and why?
Show the answer
  • On the Jetson. virtcam_probe() makes no transfer on the bus, so it cannot find out that the sensor is absent.
  • On the Raspberry Pi 5, imx477_probe() reads the identity register. The read fails, and probe returns an error.
A dev_info() is added to virtcam_parse_dt(), and the module is rebuilt. Where does the new line appear relative to the banner of tegracam?
Show the answer
  • Before the banner.
  • parse_dt runs inside tegracam_device_register(). tegracam calls it, and it prints the banner last.
What does virtcam 9-001a state, and which part of it is not in the device tree?
Show the answer
  • virtcam is the name of the driver, from .driver.name.
  • 9-001a is the name of the device: I2C bus 9, address 0x1a.
  • The address is the reg property of the node. The bus number is assigned at boot, and /sys/bus/i2c/devices/ shows it.
