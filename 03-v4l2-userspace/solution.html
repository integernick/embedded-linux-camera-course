Step 2 — the worksheet, filled

  • The drawing: imx477 9-001a → nvcsi channel → vi-output. Data flows left to right, as in the diagram of section 3 of the lesson.
  • The I2C sensor driver creates imx477 9-001a.
  • The NVCSI channel and the vi-output node belong to the NVCSI and tegra-camrtc-capture-vi platform drivers, which probed from the base device tree. The overlay of Lesson 02 only connected them to the sensor through endpoints.
  • Under a dual-camera overlay the CAM0 sensor is 10-001a, and the graph is the same (Lesson 02, section 7).
  • The entity type of the video node is Node subtype V4L, not a subdev. It is the one entity that is not a processing stage.
  • On kernel 6.8 the NVCSI entity name carries its channel number, -0, because the subdev name buffer has 52 bytes. The recorded name on a flashed r39.2.1 board is (verified-on-target: pending).

Step 3 — formats and the saved control list

  • Expected enumeration: one pixel format 'RG10' (10-bit Bayer RGRG/GBGB) with exactly two sizes, 3840x2160 at 30 fps and 1920x1080 at 60 fps.
  • They come from the two-row imx477_frmfmt[] table at the end of nvidia-oot/drivers/media/i2c/imx477_mode_tbls.h, quoted in section 4.
  • The sizes and the rates are the rows. The fourcc comes from the DT mode properties mode_type, pixel_phase and csi_pixel_bit_depth.

In imx477-ctrls.txt, against the device tree (min_gain_val=16, max_gain_val=356, min_exp_time=13, max_exp_time=683709):

  • gain: min=16 max=357 and exposure: min=13 max=683710. Both maximum values are the DT value +1, the tegracam sentinel for a value left indeterminate by alternating exposure (section 8).
  • frame_rate: min=2000000 max=30000000 has no +1. Only gain and exposure get the sentinel.
  • sensor_mode: min=0 max=2. The maximum equals the number of DT modes, not modes − 1.
  • Keep the file. Lesson 08 runs the same -l against virtcam and compares the two lists.
  • The comparison shows the same four tegracam controls with different ranges, which is evidence for the source of the ranges.

Step 4 — the captures

orin$ v4l2-ctl -d /dev/video0 -c bypass_mode=0,sensor_mode=0
orin$ v4l2-ctl -d /dev/video0 --set-fmt-video=width=3840,height=2160,pixelformat=RG10 \
        --stream-mmap --stream-count=5 --stream-to=mode0.raw
orin$ v4l2-ctl -d /dev/video0 -c sensor_mode=1
orin$ v4l2-ctl -d /dev/video0 --set-fmt-video=width=1920,height=1080,pixelformat=RG10 \
        --stream-mmap --stream-count=5 --stream-to=mode1.raw

The sizes must be exact, because this path adds no header and no padding:

  • mode0.raw = 3840 × 2160 × 2 B × 5 = 82,944,000 bytes
  • mode1.raw = 1920 × 1080 × 2 B × 5 = 20,736,000 bytes
  • The most common failure is a mode1.raw of 82,944,000 bytes. The sensor_mode=1 write was skipped, or done after the format was set.
  • use_sensor_mode_id = "true" in the IMX477 node means that the sensor_mode control selects the mode, not the requested width and height.
  • camera_common_try_fmt() rewrites a size that does not match back to the size of the current mode, without an error.
  • Confirm with v4l2-ctl -d /dev/video0 -V before streaming.

Step 5 — what the PNGs must show

illustrative, not captured on a board
orin$ python3 bayer_view.py mode1.raw --width 1920 --height 1080 --bits 10 --stats --out mode1.png
file: mode1.raw
frames: 5  frame: 0  size: 1920x1080  bits: 10  stride: 3840 bytes  backend: pure-python
min: 60  max: 1023  mean: 341.72  saturated: 0.21%
channel means  R: 355.9  Gr: 405.1  Gb: 404.6  B: 201.3
wrote mode1.png
  • min is well above 0. The sensor adds a constant black-level pedestal, so a raw zero is not scene black.
  • Gr ≈ Gb: the two green sites receive the same scene. A large difference between them indicates a parsing or pattern error, not a property of the scene.
  • Under normal indoor light B is the lowest. Tungsten and warm LED light contain little blue. AWB would correct this imbalance, and nothing corrects it on this path.
  • In the grayscale PNG at 800% zoom the 2×2 mosaic checkerboard is visible.
  • The --demosaic PNG shows the scene with a green cast. That is expected. The green sites read higher than the red and blue sites, and no white balance scaled the channels, because the ISP is bypassed (Lesson 12).
  • Red-object check: over the red area only one site per 2×2 cell responds strongly, the R site. The grayscale PNG shows a repeating cell of one bright and three dim sites.

Step 6 — the sweep script

The complete script, sweep.sh, from its first command on:

this course03-v4l2-userspace/solutions/sweep.shlines 15–42
set -euo pipefail

DEV=${DEV:-/dev/video0}
WIDTH=${WIDTH:-1920}
HEIGHT=${HEIGHT:-1080}
VIEWER=${VIEWER:-bayer_view.py}

if [ "$#" -lt 2 ]; then
    echo "usage: $0 CONTROL VALUE..." >&2
    exit 1
fi
ctrl=$1
shift

run() {
    if [ "${DRY_RUN:-0}" = 1 ]; then
        printf '%s\n' "$*"
    else
        "$@"
    fi
}

for value in "$@"; do
    run v4l2-ctl -d "$DEV" -c "$ctrl=$value"
    run v4l2-ctl -d "$DEV" --set-fmt-video="width=$WIDTH,height=$HEIGHT,pixelformat=RG10" \
        --stream-mmap --stream-count=3 --stream-to="${ctrl}_${value}.raw"
    run python3 "$VIEWER" "${ctrl}_${value}.raw" --width "$WIDTH" --height "$HEIGHT" --bits 10 --frame 2 --stats
done
  • Every command of the loop goes through run, so one variable switches between printing and running.
  • set -euo pipefail stops the sweep at the first failed capture, so a select timeout does not produce a table with holes.
  • The viewer path defaults to bayer_view.py in the current directory, which is where Step 1 put it.
  • Frame 2 is read because the control write arrives while the sensor streams its first frames. The value applies to the integration of a later frame.

The dry run is deterministic, so the battery asserts it:

orin$ DRY_RUN=1 ./sweep.sh exposure 1000 4000 16000
v4l2-ctl -d /dev/video0 -c exposure=1000
v4l2-ctl -d /dev/video0 --set-fmt-video=width=1920,height=1080,pixelformat=RG10 --stream-mmap --stream-count=3 --stream-to=exposure_1000.raw
python3 bayer_view.py exposure_1000.raw --width 1920 --height 1080 --bits 10 --frame 2 --stats
v4l2-ctl -d /dev/video0 -c exposure=4000
v4l2-ctl -d /dev/video0 --set-fmt-video=width=1920,height=1080,pixelformat=RG10 --stream-mmap --stream-count=3 --stream-to=exposure_4000.raw
python3 bayer_view.py exposure_4000.raw --width 1920 --height 1080 --bits 10 --frame 2 --stats
v4l2-ctl -d /dev/video0 -c exposure=16000
v4l2-ctl -d /dev/video0 --set-fmt-video=width=1920,height=1080,pixelformat=RG10 --stream-mmap --stream-count=3 --stream-to=exposure_16000.raw
python3 bayer_view.py exposure_16000.raw --width 1920 --height 1080 --bits 10 --frame 2 --stats
  • Without DRY_RUN=1, each v4l2-ctl -c line prints nothing, each capture prints <<<, and each viewer call prints its four lines of statistics.
  • The script with no values prints usage: ./sweep.sh CONTROL VALUE... and exits with status 1.

Step 7 — the sweep, worked

The deliverable table with example numbers from a fixed indoor scene:

Setting Value Physical Mean (DN) Saturated %
exposure 1000 1 ms 92.4 (illustrative) 0.0
exposure 4000 4 ms 341.7 0.2
exposure 16000 16 ms 953.1 41.8
gain (at 4 ms) 16 1.0x 341.7 0.2
gain 64 4.0x 891.6 37.5
gain 256 16.0x 1014.8 91.9

Answers to the three questions:

  • Linearity: 1 ms to 4 ms multiplies the mean by about 3.7, not by 4.0. With the black-level pedestal subtracted from both means, the ratio is about 4.
  • Exposure scales the photon signal, not the pedestal. The same holds for the first gain step before clipping.
  • Flattening: samples clip at 1023, the 10-bit maximum. When Saturated % grows, clipped pixels add no further DN, so the mean approaches 1023, as rows 3 and 6 show.
  • A sweep that measures linearity stays near 0% saturation. Dim the scene or limit the exposure range.
  • Frame 2: the control writes program the sensor over I2C, and exposure and gain take effect a frame or two later. The value applies to the integration of a following frame.
  • Frame 0 of a new stream can still have the previous settings. Frame 2 is after the transition.

The exported tool: bayer_view.py

  • Assumptions, stated in section 5 of the lesson and normative in the kernel's pixfmt-srggb10 page: each pixel is one 16-bit little-endian word. The 10- or 12-bit sample is in the LOW bits, the Jetson VI T_R16 memory format.
  • Frames are concatenated with no headers. The default stride is width*2, and --stride handles padded layouts.
  • The default pattern is RGGB. --pattern selects the other phases.
  • numpy is used when it can be imported. Otherwise a pure-Python fallback gives identical results more slowly: a 4K frame takes a few seconds.
Flag Meaning
--width/--height frame geometry (must match the captured mode exactly)
--bits {10,12} RG10 vs RG12 sample width; sets scaling and saturation threshold
--frame N pick one frame out of a multi-frame --stream-to file
--stats min/max/mean, saturated %, per-site means R/Gr/Gb/B
--out FILE 16-bit grayscale PNG (samples shifted up to 16 bits)
--demosaic half-res RGB8 PNG instead: R, avg(Gr,Gb), B per 2×2 cell
--self-test hardware-free synthetic-buffer test suite (exit 0/1)
  • The PNG writer is self-contained (zlib and struct, filter 0), so the tool has no dependency beyond Python 3.
  • That is deliberate, because Lessons 09, 12 and 14 copy it onto boards and into containers.
  • read_png() reads the PNGs that the tool writes. The transcripts of section 6 use it to read a pixel back.

Mechanical verification

  • verify-build-jp7.sh runs inside jetson-build-jp7 with TREE at the pristine r39.2.1 tree and SOLDIR at this directory.
  • It byte-compiles the viewer and the toy generator, and it runs the self-test of the viewer. The self-test covers the RG10 and RG12 paths, PNG writing and readback, padded strides and multi-frame indexing.
  • It re-runs the toy transcripts of the lesson. Those are the toy file and its bytes, the statistics of both frames, the geometry error and the two PNG readbacks.
  • It re-runs the arithmetic transcripts: the CID and size arithmetic, the name length, the fourcc and the unit conversions.
  • It runs the dry run of sweep.sh and compares it with the nine lines above, and it checks the usage error.
  • It greps the course's own virtcam files for the devnode, use_sensor_mode_id, mode_type, frmfmt and ctrl_cid_list transcripts.
  • It greps the r39.2.1 tree for the kernel lines that the lesson prints. Those are VIDEO_MAJOR, the 52-byte subdev name buffer, the RG10 fourcc and the camera control class.
  • It greps the stock IMX477 overlay and driver for the devnode, use_sensor_mode_id and mode_type lines and the two frmfmt rows.
  • verify-build-rpi.sh checks the Raspberry Pi parts of the sections against the pinned Raspberry Pi tree. It asserts the eight video nodes, the two link flags, the mode table and the control IDs.
  • Neither script writes into the trees, and neither depends on another lesson. Both finish in seconds. The course battery (tools/verify.sh) runs both inside the build container.
