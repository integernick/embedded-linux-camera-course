The sections of the lesson showed the three device nodes, the graph and the raw layout on a toy file. This lab is the board work. You read the real graph of the devkit, capture at both modes, and write one script that sweeps a control. The brightness of the captures is the evidence that the control writes reached the sensor.

Goal

  • A filled map of the media graph of the devkit, each entity tied to its driver and its device node.
  • The control list of the IMX477, saved as imx477-ctrls.txt for Lesson 08.
  • Raw captures at both IMX477 modes with the exact sizes, and their PNGs from bayer_view.py.
  • A sweep script, written from a skeleton, and a table of brightness against exposure and gain.

Hardware

  • Orin Nano devkit with JetPack 7.2.1 (Jetson Linux r39.2.1), reachable over SSH. BOARD_USER and BOARD_IP are exported as in Lab 01.
  • The IMX477 on CAM0, enabled since the lab of Lesson 02. ls /dev/video* shows /dev/video0 after boot.
  • About 200 MB free on the board for the raw files.
  • Python 3 on the board. The viewer runs without numpy, and faster with it.
  • No container. Every step runs on the board, or on the host to copy a file.

Steps

Step 1 — Install the tools and copy the viewer (10 min)

  1. Install v4l-utils, the package that holds media-ctl and v4l2-ctl:
orin$ sudo apt install v4l-utils

apt prints its install log. Both tools are then on the path.

  1. Copy the viewer from the course clone on the host. The lab does not ask for the viewer to be written, so taking it from solutions/ is intended:
host$ ssh "$BOARD_USER@$BOARD_IP" "mkdir -p ~/lab03"
host$ scp lessons/03-v4l2-userspace/solutions/bayer_view.py "$BOARD_USER@$BOARD_IP:lab03/"

ssh prints nothing, and scp prints one progress line.

  1. Check that the tool works without the camera:
illustrative, not captured on a board
orin$ cd ~/lab03 && python3 bayer_view.py --self-test | tail -1
self-test: OK (13 checks, artifacts in /tmp/bayer_view_selftest_mkk049p2)

The directory name differs on every run. You should see self-test: OK with 13 checks and the exit code 0. Without tail -1, the output is one ok: line per check.

Step 2 — List the nodes and map the graph (15 min)

  1. List the device nodes:
orin$ ls -l /dev/video* /dev/media* /dev/v4l-subdev*

Expected: one /dev/video0, one /dev/media0 and two /dev/v4l-subdev* nodes, all with major 81. If /dev/video0 is missing, the overlay is not applied. Return to the lab of Lesson 02.

  1. Dump the graph:
orin$ media-ctl -p -d /dev/media0

Expected: three entities and two links marked [ENABLED], as in section 3 of the lesson.

  1. Fill in this worksheet from the dump. It is the first deliverable of the lab:
Entity name (from the dump) Kind /dev node Its source pad links to

The kinds are: sensor subdev, NVCSI channel subdev, video node. Answer two questions in writing. Which entity does the I2C sensor driver create? Which two entities belong to platform drivers that the overlay of Lesson 02 did not create?

  1. Draw the three entities with arrows in the direction of the data flow.

  2. Record the NVCSI entity name exactly as printed. Section 3 of the lesson expects 13e00000.host1x:nvcsi@15a00000-0 on kernel 6.8. Your record confirms or corrects that expectation.

Step 3 — Enumerate the formats and save the control list (10 min)

  1. List the formats:
orin$ v4l2-ctl -d /dev/video0 --list-formats-ext

Record the fourcc and both pairs of size and rate. Compare them with the two rows of imx477_frmfmt[] in nvidia-oot/drivers/media/i2c/imx477_mode_tbls.h that section 4 quotes.

  1. Save the control list to a file. Lesson 08 compares it with the list of virtcam:
orin$ v4l2-ctl -d /dev/video0 -l | tee imx477-ctrls.txt

Note the min, max and default of gain, exposure, frame_rate and sensor_mode. Compare the max of gain and of exposure with the device-tree values quoted in section 7. Each is higher by exactly one. State the reason in one sentence.

Step 4 — Capture five frames at each mode (15 min)

  1. Select the mode by control first, then stream. The two commands are separate on purpose, because controls persist:
orin$ v4l2-ctl -d /dev/video0 -c bypass_mode=0,sensor_mode=0
orin$ v4l2-ctl -d /dev/video0 --set-fmt-video=width=3840,height=2160,pixelformat=RG10 \
        --stream-mmap --stream-count=5 --stream-to=mode0.raw
orin$ ls -l mode0.raw

Expected: five < marks, then a file of 82,944,000 bytes. That is 3840 × 2160 × 2 bytes × 5 frames. If ls -l shows another size, stop and read the Troubleshooting table.

  1. Repeat for mode 1. The sensor_mode control comes first:
orin$ v4l2-ctl -d /dev/video0 -c sensor_mode=1
orin$ v4l2-ctl -d /dev/video0 --set-fmt-video=width=1920,height=1080,pixelformat=RG10 \
        --stream-mmap --stream-count=5 --stream-to=mode1.raw
orin$ ls -l mode1.raw

Expected: 20,736,000 bytes, that is 1920 × 1080 × 2 × 5. Confirm that the driver accepted the smaller mode: v4l2-ctl -d /dev/video0 -V must report 1920x1080.

Step 5 — View the Bayer data (15 min)

  1. Convert frame 0 of each capture to a 16-bit grayscale PNG, then to a color PNG with a simple demosaic:
orin$ python3 bayer_view.py mode0.raw --width 3840 --height 2160 --bits 10 --out mode0.png
orin$ python3 bayer_view.py mode0.raw --width 3840 --height 2160 --bits 10 --demosaic --out mode0_rgb.png
orin$ python3 bayer_view.py mode1.raw --width 1920 --height 1080 --bits 10 --out mode1.png
orin$ python3 bayer_view.py mode1.raw --width 1920 --height 1080 --bits 10 --demosaic --out mode1_rgb.png

Each command prints one wrote line. A 4K frame takes a few seconds without numpy.

  1. Open the PNGs in an image viewer, on the board or after an scp to the host. Record three observations:
    • The grayscale PNG is viewable, because the tool scaled 10 bits up to 16. At 800% zoom on a bright, uniform area, the 2×2 checkerboard of the mosaic is visible.
    • The --demosaic PNG has real colors and a green cast. State the reason in one sentence (section 6 of the lesson).
    • Point the camera at a red object and capture one more frame. In the grayscale PNG the red area shows one bright site and three dim sites per 2×2 cell.

  1. Replace each TODO with one run line. Every command goes through run, so DRY_RUN=1 prints the commands instead of running them.

  2. Check the script without the camera:

orin$ chmod +x sweep.sh
orin$ DRY_RUN=1 ./sweep.sh exposure 1000 4000 16000
v4l2-ctl -d /dev/video0 -c exposure=1000
v4l2-ctl -d /dev/video0 --set-fmt-video=width=1920,height=1080,pixelformat=RG10 --stream-mmap --stream-count=3 --stream-to=exposure_1000.raw
python3 bayer_view.py exposure_1000.raw --width 1920 --height 1080 --bits 10 --frame 2 --stats

The dry run prints these three lines, then the same three for 4000 and 16000: nine lines in all. Nothing is captured.

  1. Run it for real. Keep the scene and the lighting fixed, because no automatic control runs on this path:
orin$ v4l2-ctl -d /dev/video0 -c bypass_mode=0,sensor_mode=1
orin$ ./sweep.sh exposure 1000 4000 16000
orin$ v4l2-ctl -d /dev/video0 -c exposure=4000
orin$ ./sweep.sh gain 16 64 256

Expected: for each value, three < marks and the four lines of statistics. The mean grows with the value until saturated grows.

Step 7 — Fill the brightness table (10 min)

  1. Fill the deliverable table from the --stats lines. The mean is in DN out of 1023:
Setting Value (control units) Physical value Mean (DN) Saturated %
exposure 1000 1 ms
exposure 4000 4 ms
exposure 16000 16 ms
gain 16 1.0x
gain 64 4.0x
gain 256 16.0x
  1. Answer three questions under the table:
    • Is the mean roughly linear in exposure until saturation starts? Four times the exposure should give about four times the mean.
    • Why does the trend flatten when Saturated % grows?
    • Why does the script read frame 2 and not frame 0? The control writes arrive while the sensor already streams its first frames.

On a Raspberry Pi 5

This lab has no Raspberry Pi form yet. Three of its steps are different there, and none is verified on a board (verified-on-target: pending).

  • Step 2. media-ctl -p prints more entities: the sensor, the CSI-2 receiver, the front end and eight video nodes.
  • Step 3. The mode list comes from the subdevice of the sensor, not from a video node.
  • Step 4. Before a capture, a program enables the link to csi2_ch0 and sets a format on each pad. The frames are packed, so bayer_view.py cannot read them as they are.

Expected output

  1. The worksheet. The three-row entity table with each row tied to its /dev node. The two written answers, the drawing, and the recorded NVCSI entity name.
  2. imx477-ctrls.txt, saved in ~/lab03 for Lesson 08, with the one-sentence reason for the two +1 ranges.
  3. The captures. mode0.raw of 82,944,000 bytes and mode1.raw of 20,736,000 bytes, with their PNG pairs and the three observations.
  4. sweep.sh, with a dry run that prints the nine expected lines.
  5. The brightness table with six measured means, and the three answers.

A typical form of the result. The absolute numbers depend on the scene and the lighting:

illustrative, not captured on a board
exposure 1000  -> mean  92.4 DN, sat 0.0%
exposure 4000  -> mean 341.7 DN, sat 0.2%
exposure 16000 -> mean 953.1 DN, sat 41.8%   <- flattening: pixels clip at 1023

Troubleshooting

Symptom Likely cause Fix
No /dev/video0 at all The overlay of Lesson 02 is not applied, or the wrong extlinux entry booted Repeat the verification of the lab of Lesson 02: extlinux.conf, reboot, dmesg | grep imx477
select timeout during --stream-mmap No pixels reach VI: mode and format do not match, an Argus session hangs, or a CSI problem Run the two -c commands again. Run sudo systemctl restart nvargus-daemon. Check dmesg | tail -30. Lesson 14 lists further causes
The capture file is four times the expected size sensor_mode is still 0 while 1920x1080 was requested Run v4l2-ctl -c sensor_mode=1, set the format again, and confirm with v4l2-ctl -V
bayer_view.py refuses: "is not a multiple of one frame" Width and height do not match the captured mode, or the copy is truncated Use the exact width and height of the mode. Repeat the scp. Check the ls -l arithmetic first
The PNG opens and is black The raw file was viewed without the tool and without scaling Use bayer_view.py, which shifts 10-bit samples up to 16 bits, or multiply the data by 64
Device or resource busy Another consumer streams the node Run sudo fuser -v /dev/video0, stop the pipeline, and retry
Permission denied on /dev/video0 The user is not in the video group Use sudo for the commands, or run sudo usermod -aG video $USER and log in again
The dry run of sweep.sh prints nothing, or runs the commands A run prefix is missing, or DRY_RUN=1 was not set Put run in front of every command inside the loop. Set DRY_RUN=1 in the same command line
The sweep means change very little with exposure The scene is saturated, or the lighting changed Dim the scene or shorten the exposures. Keep the lighting constant across the sweep
