A camera sensor cannot report its own presence. The kernel learns about it from a description that a person wrote: the device tree. On a Jetson, the description of a camera is a separate file, an overlay. The bootloader merges it into the tree of the board at every boot.

This lesson follows that description from its source file to the running kernel, in eight numbered sections. Each section shows its commands together with their output, so it can be read without a board.

Note

The text describes two boards. The Jetson Orin Nano runs JetPack 7.2.1 (Jetson Linux r39.2.1), with kernel 6.8 in the kernel-noble tree and UEFI firmware 36.0 or newer. The Raspberry Pi 5 side is read from the Raspberry Pi kernel at tag stable_20261103, which is Linux 6.18.60. The Jetson is the default board. Each section follows the Jetson first, and its last part shows the same step on the Raspberry Pi 5.

The two cameras

The sections read the overlays of two cameras. Both use the same connector and the same blocks of the SoC, so their overlays have the same structure.

The stock camera is the Raspberry Pi High Quality Camera, which carries a Sony IMX477 sensor. NVIDIA ships a driver for it, nv_imx477, and a set of overlays. Both are part of every JetPack install. This camera is the reference of the course. It works on a fresh install, so a statement about a working camera can always be checked against it.

virtcam is the course's own sensor driver, in the virtcam/ directory. To the kernel it is a normal camera sensor. It has a device-tree node, it registers with NVIDIA's camera framework, and it produces /dev/video0. It differs from a normal driver in one respect: it never writes a register of the sensor. A userspace program, picam-conf, sends the register sequences over I2C instead. Lesson 09 covers that program.

A driver that does not program its sensor has three uses in this course:

  • It is small. In a production sensor driver, most lines are register tables and exposure arithmetic. virtcam.c has fewer than 400 lines. What remains is what NVIDIA's stack demands from every sensor driver, and Lesson 08 reads all of it.
  • Products use the same split. Some sensors are behind a serializer and deserializer pair, an FPGA, or a bridge chip. Register settings also change often during bring-up. A userspace configurator handles both cases without a kernel rebuild.
  • It separates two kinds of fault. With virtcam, a symptom belongs to one of two sides: the description that the kernel holds, or the registers that the sensor holds.

This lesson needs only the overlay of virtcam. The lab compiles it and prepares its boot entry. Lesson 08 loads the driver.

The Raspberry Pi kernel has its own overlay for the stock camera, imx477-overlay.dts, and Lesson 01 read its driver. The last part of each section reads that overlay.

1. Why the kernel needs a description

A camera is connected to the CAM0 connector of a freshly installed board. Nothing happens: no /dev/video0 appears, and dmesg has no line about a camera. The camera is not broken. The kernel does not know that it exists.

A USB or PCI device announces itself when it is connected. But a camera sensor cannot do that. It is connected to an I2C bus and to a CSI-2 link, and neither has a discovery mechanism. So a person must tell the kernel which device is at which address. That description is the device tree: a data structure that the kernel receives from the bootloader at boot.

Four terms on a toy tree

Four terms describe every device tree. They are easier to see on a small invented tree than on a real board. The file examples/toy-base.dts describes a board with a GPIO controller, an I2C bus and one EEPROM:

this course02-device-tree-overlays/examples/toy-base.dtslines 15–35
    gpio: gpio@2000 {
        compatible = "toy,gpio";
        reg = <0x2000 0x100>;
        gpio-controller;
        #gpio-cells = <2>;
    };

    bus: i2c@1000 {
        compatible = "toy,i2c";
        reg = <0x1000 0x100>;
        #address-cells = <1>;
        #size-cells = <0>;
        clock-frequency = <100000>;
        status = "okay";

        eeprom@50 {
            compatible = "toy,eeprom";
            reg = <0x50>;
            wp-gpios = <&gpio 4 0>;
        };
    };
Node. i2c@1000 { ... } is a node: one device or one bus. Nodes nest like directories, so the EEPROM on this bus is the child node eeprom@50.
  • The number after @ is the unit address. For the bus it is a register address, and for the EEPROM it is an I2C address.
  • Property. Each name = value; line is a property. A value is a string ("okay"), a list of 32-bit numbers in angle brackets (<100000>), or a mix.
    • A property without a value, such as gpio-controller;, is a flag.
  • Label. bus: and gpio: in front of the nodes are labels. Another place in the source can then write &gpio instead of the path of the node.
  • Phandle. A property can point at another node. wp-gpios = <&gpio 4 0> names pin 4 of the node with the label gpio.
    • The compiler gives the target node a unique number, the phandle, and stores that number in the property.

    • The compiled tree shows the last point. dtc is the device tree compiler, and fdtget reads one value out of a compiled tree:

    container$ cd /course/lessons/02-device-tree-overlays/examples
container$ dtc -@ -I dts -O dtb -o /tmp/toy-base.dtb toy-base.dts
container$ fdtget /tmp/toy-base.dtb /i2c@1000 status
okay
container$ fdtget /tmp/toy-base.dtb /i2c@1000/eeprom@50 wp-gpios
1 4 0
container$ fdtget /tmp/toy-base.dtb /gpio@2000 phandle
1

    The first cell of wp-gpios is 1, and 1 is the phandle that dtc gave the GPIO node. So the label gpio is not in the property any more: the compiled tree holds only the number. Section 4 explains the -@ flag.

    The same four terms in NVIDIA's source

    The real tree uses the same four terms. The source file of the Orin SoC defines the camera I2C controller like this:

    Jetson Linux r39.2.1hardware/nvidia/t23x/nv-public/tegra234.dtsilines 2801–2807
            cam_i2c: i2c@3180000 {
            compatible = "nvidia,tegra194-i2c";
            reg = <0x0 0x3180000 0x0 0x100>;
            interrupts = <GIC_SPI 27 IRQ_TYPE_LEVEL_HIGH>;
            #address-cells = <1>;
            #size-cells = <0>;
            status = "disabled";

    Only three things are new here:

    • The node has the label cam_i2c. Every camera overlay uses that label.
    • reg has four cells, because the SoC uses 64-bit addresses: two cells for the address and two for the size.
    • interrupts names the interrupt line of the controller. GIC_SPI and IRQ_TYPE_LEVEL_HIGH are C macros, which section 3 explains.

    The clocks and resets properties point at the node with the label bpmp. The form is the same as wp-gpios in the toy tree.

    More detail: the properties whose name starts with #

    A property whose name starts with # is a cell count: it states how many 32-bit cells another property uses. The specification and the binding of each provider fix these names, so a tree cannot rename them. The toy tree has both kinds.

    • #address-cells and #size-cells describe the reg of the children of the node that carries them.
      • The root of the toy tree declares one address cell and one size cell. So gpio@2000 writes reg = <0x2000 0x100>, a 256-byte register window at 0x2000.
      • The I2C bus declares one address cell and no size cell. So eeprom@50 writes reg = <0x50>, because an I2C address has no length.
      • The unit address after @ repeats the first address cell. The SoC tree above declares two cells for each, so its reg has four.
    • #gpio-cells describes the cells that follow a phandle to the node that carries it.
      • The toy controller declares two. So one GPIO is &gpio and two cells, the pin and its flags: <&gpio 4 0>.
      • The GPIO core reads the count from the controller that each phandle names, and it splits a list of several GPIOs with that count.
      • Clocks and resets follow the same pattern: #clock-cells and #reset-cells on the provider, clocks and resets on the consumer. The three cells of interrupts above are the #interrupt-cells of the interrupt controller.

    Neither pair is inherited. A node that omits them gets the defaults of the specification, two address cells and one size cell, and dtc warns. That is why the overlay fragments of this lesson repeat the pair inside __overlay__. A fragment is compiled alone, and dtc needs the pair to check the reg of the new node.

    Two properties with a fixed meaning

    Two properties mean the same for every device.

    compatible connects a node to a driver. First the kernel creates a device for the node. Then it calls the probe function of the driver whose match table holds the same string (Lesson 01). So "nvidia,tegra194-i2c" selects NVIDIA's I2C controller driver, and no driver in the kernel matches "toy,i2c".

    status switches a node on or off. The kernel creates no device for a node with status = "disabled". For example, the SoC file lists the camera I2C controller as disabled, because an SoC file describes every controller of the chip. Then the board file of the devkit sets "okay", because the devkit routes this controller to the camera connectors. Section 2 reads that value out of the compiled tree of the board.

    Note

    A device tree describes. It does not detect. A node for a device that is not connected still creates a kernel device, and a connected device without a node stays unknown.

    2. Compiled on the host, merged at every boot

    A device tree exists in three forms: a text source, a binary file, and a structure in the memory of the kernel. Three programs handle them, at three different times. This section states that order before the syntax starts, because every later section depends on it.

    Three programs in three places

    The life cycle of a device tree: compiled on the build host, stored in /boot, merged by UEFI at every boot

    First, on the build host. dtc turns a text source (.dts) into a binary file, a blob. The blob of a whole board is a .dtb, and the blob of an overlay is a .dtbo. Compilation runs on the build host, and only after a source changed. Nothing on the board compiles a device tree.

    Then, on the storage of the board. The blobs are ordinary files in /boot. JetPack installs the base .dtb of the board and NVIDIA's camera overlays there. An overlay of the course is copied there with scp. The file /boot/extlinux/extlinux.conf names the blobs that a boot entry uses.

    Finally, at every boot. UEFI reads extlinux.conf, loads the base blob, and applies the listed overlays to it in order. The result is one merged tree in RAM. UEFI passes that tree to the kernel and writes nothing back to storage. The kernel then creates devices from the merged tree, and the drivers probe.

    Three consequences follow:

    • The merge repeats at every boot. So an overlay removed from extlinux.conf is absent after the next reboot, and no part of it remains.
    • The files in /boot change only when a person copies or edits them. A wrong tree on a running board therefore means a wrong file or a wrong extlinux.conf.
    • The kernel sees one tree. It has no record of the overlay that created a node.

    3. An overlay is a patch for the tree

    The base tree of the devkit has no camera in it. A camera is added without an edit of the base tree: a second file, an overlay, states what to add and where. This section reads the syntax on a toy overlay first. Then it reads the first lines of NVIDIA's overlay for the IMX477.

    A toy overlay

    The file examples/toy-overlay.dts adds a sensor to the I2C bus of the toy tree of section 1:

    this course02-device-tree-overlays/examples/toy-overlay.dtslines 7–29
    /dts-v1/;
/plugin/;

/ {
    fragment@0 {
        target = <&bus>;
        __overlay__ {
            #address-cells = <1>;
            #size-cells = <0>;
            clock-frequency = <400000>;

            eeprom@50 {
                read-only;
            };

            cam: sensor@1a {
                compatible = "toy,sensor";
                reg = <0x1a>;
                reset-gpios = <&gpio 5 0>;
            };
        };
    };
};

    Three lines make this file an overlay:

    • /plugin/; declares it. A plugin may use a label that it does not define, such as &bus and &gpio. In a normal source that is an error.
    • fragment@0 is one patch. An overlay is a list of fragments.
    • target = <&bus> names the node to patch. Everything inside __overlay__ { } is merged into that node.

    The merge follows three rules, and this fragment uses all of them:

    Rule In the toy overlay Effect on the tree
    A property that the target already has is overwritten. clock-frequency = <400000> The bus runs at 400 kHz instead of 100 kHz.
    A subnode that the target already has is merged by the same rules. eeprom@50 { read-only; } The EEPROM keeps its properties and gets one more.
    Any other property or subnode is created. sensor@1a { ... } The bus gets a second device.

    fdtoverlay performs the merge on the host. It is the same merge that UEFI performs at boot:

    container$ dtc -@ -I dts -O dtb -o /tmp/toy-overlay.dtbo toy-overlay.dts

container$ fdtoverlay -i /tmp/toy-base.dtb -o /tmp/toy-merged.dtb /tmp/toy-overlay.dtbo
container$ fdtget /tmp/toy-merged.dtb /i2c@1000 clock-frequency
400000
container$ fdtget -l /tmp/toy-merged.dtb /i2c@1000
sensor@1a
eeprom@50
container$ fdtget -p /tmp/toy-merged.dtb /i2c@1000/eeprom@50
read-only
compatible
reg
wp-gpios

    The three rules are visible in the merged tree. The frequency is 400000, the bus has two children, and the EEPROM has its three old properties and the new read-only. The warning is expected, because the overlay names eeprom@50 without a reg: the reg is in the base tree. NVIDIA's overlays print the same kind of warning.

    A source with #include lines passed directly to dtc.

    The first fragment of NVIDIA's overlay

    Two things differ from the toy.

    First, the fragment uses target-path = "/" instead of target = <&label>. It names its target by path, and the path is the root. So this one fragment can reach every node of the tree. It repeats the chain of node names from the root down to each place that it changes. The stock overlay has only this one fragment.

    4. Labels connect an overlay to the tree

    The toy overlay of section 3 says target = <&bus>. But section 1 showed that a compiled tree holds numbers, not labels. So the overlay has a problem: it is compiled alone, and it cannot know the phandle of a node in another file. This section shows how the problem is solved, first on the toy and then on NVIDIA's overlay.

    The label table of a blob

    The solution starts at compile time. The -@ flag makes dtc keep the labels of a source in the blob, in a node with the name __symbols__. Each entry maps one label to the path of its node:

    container$ fdtget -p /tmp/toy-base.dtb /__symbols__
gpio
bus
container$ fdtget /tmp/toy-base.dtb /__symbols__ bus
/i2c@1000

    The toy base exports its two labels. Without -@, the blob has no such node, and a label exists only in the source.

    What an overlay blob holds instead of a phandle

    The overlay blob cannot hold the phandle of bus or gpio. The decompiled blob shows what it holds instead. dtc -I dtb -O dts turns a blob back into text:

    container$ dtc -I dtb -O dts /tmp/toy-overlay.dtbo 2>/dev/null
/dts-v1/;

/ {

    fragment@0 {
        target = <0xffffffff>;

        __overlay__ {
            #address-cells = <0x01>;
            #size-cells = <0x00>;
            clock-frequency = <0x61a80>;

            eeprom@50 {
                read-only;
            };

            sensor@1a {
                compatible = "toy,sensor";
                reg = <0x1a>;
                reset-gpios = <0xffffffff 0x05 0x00>;
                phandle = <0x01>;
            };
        };
    };

    __symbols__ {
        cam = "/fragment@0/__overlay__/sensor@1a";
    };

    __fixups__ {
        bus = "/fragment@0:target:0";
        gpio = "/fragment@0/__overlay__/sensor@1a:reset-gpios:0";
    };
};

    Three things replaced the two label references:

    • Each reference is now the placeholder 0xffffffff: in target, and in the first cell of reset-gpios.
    • __fixups__ lists the places that hold a placeholder. An entry reads as label = path of the node : property : byte offset.
    • __symbols__ holds the label that the overlay itself defines, cam.

    At merge time, the program that applies the overlay does the rest. First it looks up each label of __fixups__ in the __symbols__ table of the tree. Then it writes the real phandle over each placeholder. Finally it adds the labels of the overlay to the table of the tree:

    container$ fdtget /tmp/toy-merged.dtb /i2c@1000/sensor@1a reset-gpios
1 5 0
container$ fdtget -p /tmp/toy-merged.dtb /__symbols__
cam
gpio
bus

    In the merged tree the placeholder is 1, the phandle of the GPIO node. The table has three labels now. So a later overlay can use &cam, and section 8 depends on that.

    The table of the base is necessary. Compiled without -@, the same base has no __symbols__ node, and the merge fails:

    container$ dtc -I dts -O dtb -o /tmp/toy-base-nosym.dtb toy-base.dts
container$ fdtoverlay -i /tmp/toy-base-nosym.dtb -o /tmp/x.dtb /tmp/toy-overlay.dtbo

Failed to apply '/tmp/toy-overlay.dtbo': FDT_ERR_NOTFOUND

    FDT_ERR_NOTFOUND means that a label of __fixups__ is not in the table of the tree.

    The three linkage nodes, for reference:

    Node Present in Content Used at merge time to
    __symbols__ the base DTB and every overlay each label that the file defines, with the path of its node find a label that a later overlay needs
    __fixups__ overlays only each label that the file uses and does not define, with the places that use it write the real phandle into those places
    __local_fixups__ overlays only the places that point at a node of the same overlay renumber those phandles, so that none collides with a phandle of the base tree
    More detail: the renumbering of phandles inside an overlay
    • In the decompiled toy overlay, the sensor node has phandle = <0x01>. dtc gave it a phandle because it has a label.
    • The GPIO node of the base also has phandle 1. So the merge adds an offset to every phandle of the overlay.
    • In the merged toy tree, fdtget /tmp/toy-merged.dtb /i2c@1000/sensor@1a phandle prints 3.
    • A property that points at a node of the same overlay must get the same offset. __local_fixups__ lists those properties. The toy overlay has none, so it has no such node.

    5. From /boot to the kernel, and back

    Sections 3 and 4 merged overlays on the host with fdtoverlay. On a board, UEFI performs the same merge at every boot. One text file tells it what to merge: /boot/extlinux/extlinux.conf. This section reads that file. Then it reads the merged tree back on the running board, which is the only proof that an overlay arrived.

    The merge at boot

    The kernel takes no part in the merge. UEFI does all of it, in four steps:

    1. It reads /boot/extlinux/extlinux.conf and selects a boot entry.
    2. It loads the base DTB that the FDT line of the entry names.
    3. It applies the blobs on the OVERLAYS line of the entry, from left to right.
    4. It starts the kernel and passes the merged tree.

    NVIDIA's platform adaptation guide states steps 2 and 3 (see the references of the references). The guide also states a fallback. Without an FDT line, UEFI uses a copy of the device tree that the boot firmware holds. The overlays are applied only to a tree that an FDT line names. So an entry without that line gets no overlays.

    A boot entry

    The entry of the course for the stock camera, from the command index (setup/canonical-commands.md, section 4):

    illustrative, not captured on a board
    LABEL imx477-a
      MENU LABEL devkit IMX477 on CAM0
      LINUX /boot/Image
      INITRD /boot/initrd
      FDT /boot/tegra234-p3768-0000+p3767-0005-nv.dtb
      OVERLAYS /boot/tegra234-p3767-camera-p3768-imx477-A.dtbo
      APPEND <the APPEND line of the stock entry, unchanged> course_label=imx477-a
    Line Meaning
    LABEL / MENU LABEL The name of the entry. DEFAULT <label> at the top of the file selects the entry that boots without a keypress.
    LINUX, INITRD The kernel image and the initrd. Course entries copy both lines from the stock entry.
    FDT The base DTB. The next section shows how to choose it.
    OVERLAYS The overlay blobs, separated by commas and applied in order. Here it is one file, the stock CAM0 overlay that JetPack installed in /boot.
    APPEND The kernel command line. The bootloader substitutes ${cbootargs}. The trailing course_label=imx477-a is the marker of the course.
    More detail: why a course entry has a marker

    The marker solves one problem. Two entries with the same kernel and the same overlays cannot be told apart from inside the running system. The kernel ignores an argument that it does not recognize, and /proc/cmdline shows the argument after boot. So grep -o 'course_label=[^ ]*' /proc/cmdline names the entry that UEFI selected.

    The base DTB that matches the board

    A stock JetPack 7.2.1 install writes its boot entry without an FDT line (verified-on-target: pending). So an added entry must name the base DTB that matches the board. The model string cannot identify the file, because the p3767-0003, -0004 and -0005 trees share one model string. The first string of the root compatible property is unique for each file:

    More detail: the third base blob in /boot

    Important

    /boot also holds tegra234-p3768-0000+p3767-0005.dtb, a file without the -nv suffix. It is the device tree of the Ubuntu kernel. The course overlays are checked only against the two -nv files.

    Rules for editing extlinux.conf

    A mistake in this file can stop the boot. Four rules prevent that, and each one names its failure:

    Warning

    root= copied from another board.

    • Symptom: the kernel panics because it cannot mount root, or the board returns to the bootloader repeatedly.
    • Fix: copy the APPEND line from the entry that the board already boots with, never from an example. Add only the marker.
    • Fix: keep the stock primary entry unchanged. It stays selectable from the boot menu on the serial console.

    Warning

    extlinux.conf edited, old entry booted.

    • Symptom: no change has an effect, and /proc/cmdline shows the wrong course_label.
    • Cause: DEFAULT still names another entry, or jetson-io added an entry of its own below.
    • Fix: check before every reboot that DEFAULT matches the entry character for character.

    Warning

    FDTOVERLAY line outside a LABEL block.

    • Symptom: the OVERLAYS list is correct and the nodes never appear.
    • Cause: the line is an older mechanism, and it conflicts with the OVERLAYS line of an entry.
    • Fix: delete the line or comment it out.

    The fourth rule is to always write the FDT line. The booted base is then a file that dtc can read, and an overlay can be checked against it on the host before a reboot.

    More detail: jetson-io writes the same file
    • jetson-io (sudo /opt/nvidia/jetson-io/jetson-io.py) is NVIDIA's menu tool for extlinux.conf.
    • It finds the dtbos in /boot, shows their overlay-name strings, and writes a boot entry with its own FDT and OVERLAYS lines.
    • It suits the stock cameras. It cannot write a list of several files in a required order, which section 8 needs. This lesson therefore writes the entry by hand.

    6. The data path: sensor, NVCSI, VI

    The single fragment of the stock overlay writes to four places of the tree. This section reads the two places that describe the path of the image data. The nodes there have names like port and endpoint, and they raise one question: which of them is a real wire. Section 7 reads the other two places.

    Three devices and two links

    Image data passes through three devices:

    • The sensor, a chip on the camera module. It sends frames over MIPI CSI-2.
    • NVCSI, the CSI-2 receiver of the SoC. It turns the signal on the lanes into a stream of pixels.
    • VI, the video input block of the SoC. It writes the pixels into memory buffers.

    Each device has a node in the tree. A connection between two devices is described by a pair of endpoint nodes. One endpoint is inside each device, and each names the other through a remote-endpoint property:

    The capture graph: two endpoints describe the cable to the sensor, and two describe a connection inside the SoC

    The two links are of different kinds.

    Link 1 is a cable. The sensor endpoint and the first NVCSI endpoint describe the MIPI CSI-2 lanes. The lanes run from the camera module through the ribbon cable and the CAM0 connector to pins of the SoC.

    So the properties of these two endpoints describe the board. bus-width = <2> is the number of data lanes. port-index = <1> is the CSI port of the SoC that the CAM0 connector is wired to.

    Link 2 is a connection inside the SoC. NVCSI and VI are two blocks of the same chip, each with its own registers, clock and power switch. The pixel words leave NVCSI on dedicated on-chip wiring into VI: a one-way stream with line and frame markers, and no addresses. NVCSI has no DMA engine, so it cannot write memory. VI is the first block that can, and it writes the stream into the buffers of Lesson 10. No pin, trace or connector corresponds to this link.

    More detail: the switch between NVCSI and VI

    The link is nevertheless a choice. NVCSI has several receiver ports, VI has several capture channels, and a switch between them connects any port to any channel. The endpoint pair states which NVCSI stream feeds this VI channel, and port-index = <1> on the VI side names that stream. The VI driver reads the number from its endpoint and passes it on in the setup of the capture channel. So the switch is set at every capture start, not at boot.

    More detail: the switch between NVCSI and VI
    • The arrangement is the one of a peripheral and a DMA controller in a microcontroller. The peripheral produces samples and has no access to memory. A DMA channel writes them, and a request mux selects which peripheral feeds which channel.
    • NVCSI is the peripheral, a VI channel is the DMA channel, and port-index is the mux setting.
    • On Orin the CPU does not program the two blocks itself. The VI driver sends the setup of a capture channel, with the stream id and the virtual channel, to the camera firmware on the RTCPU.
    • The firmware programs NVCSI and VI from that setup. Appendix B covers the firmware.
    • One port can carry several streams, separated by the virtual channel field of the CSI-2 packets. The vc_id property of a mode node selects one. Lesson 09 uses it behind a deserializer.
    • The endpoint on the NVCSI side of this link, rbpcv3_imx477_csi_out0, carries only remote-endpoint. The three other endpoints carry port-index and bus-width, because NVCSI and VI each read the port number from their own node.

    An endpoint is a record, not a device

    No driver binds to an endpoint node, and it gets no entry in /dev. Instead, an endpoint is a record that the driver of the surrounding device reads once, at probe time.

    More detail: the files that read an endpoint

    In NVIDIA's camera sources, three files read port-index and bus-width: camera_common.c for the sensor, csi/csi.c for NVCSI, and vi/channel.c for VI. Then vi/graph.c follows the remote-endpoint references from device to device. From them it builds the media graph that Lesson 03 lists with media-ctl.

    7. The control path: mux, reset, clock

    Section 6 followed the image data from the sensor to the SoC. Control goes the other way: the SoC must reach the sensor over I2C, release its reset, and in some designs give it a clock. This section reads the part of the overlay that describes those three connections.

    One pattern: a consumer names its provider

    All three connections are written in the same way. A consumer node names a provider node by phandle, in a property whose name states the kind of resource. The toy tree of section 1 had one such line, wp-gpios = <&gpio 4 0>. The devkit has these:

    The control wiring of the devkit cameras: one I2C controller, a mux with a GPIO select line, and a reset line for each connector

    The I2C mux

    Both camera connectors share one I2C controller of the SoC, cam_i2c. A mux on the carrier board connects the SDA and SCL lines to one connector at a time, and a GPIO selects the connector.     The clock

    The stock IMX477 node declares no clock, because the Raspberry Pi module has its own oscillator. The virtcam node declares one, in the form that a sensor without an oscillator needs:

    I2C bus numbers

    The driver of the stock camera logs as imx477 9-001a. The 9 is the number of the I2C bus, and it comes from the tree in two steps. First, the base tree fixes the first nine bus numbers through aliases. i2c2 is cam_i2c, and i2c7 is gen8_i2c, the I2C bus of the 40-pin header. So /dev/i2c-0 through /dev/i2c-8 are fixed, and the adapters of the mux get the next free numbers.

    Second, the mux driver creates one adapter for each i2c@N child of the mux node, in the order of the merged tree. The reg of the child is the channel that the adapter selects. The stock -A overlay gives a reg only to i2c@0, the channel that it uses. Its i2c@1 holds the disabled placeholder and no reg, so that adapter selects channel 0 as well:

    More detail: why the second adapter is channel 0, and when CAM0 is bus 10
    • The merge of section 3 inserts a new subnode in front of the existing ones. So the applied tree lists i2c@1 before i2c@0, as the fdtget -l transcript above shows.
    • The mux driver i2c-mux-gpio walks the children in that order and reads reg into a zero-filled array. A child without reg keeps 0. The -A overlay therefore yields the channels 0 and 0, and the -C overlay 1 and 0.
    • The first adapter gets the first free number. Under -A it is channel 0 with the CAM0 sensor, so imx477 9-001a. Under -C it is channel 1 with the CAM1 sensor, so imx477 9-001a again.
    • The second adapter, bus 10, holds no sensor in either case.
    • A dual overlay gives both channels a reg. Then bus 9 is channel 1, CAM1, and bus 10 is channel 0, CAM0.
    • The numbers assume that no other adapter without an alias registered first. The order of the mux channels does not depend on that.

    8. Several overlays: order and collisions

    An OVERLAYS line can list more than one file. Two things can then go wrong, and neither prints an error on the board. Either an overlay is applied before the overlay that it depends on, or two overlays write the same nodes. This section shows both failures on the host.

    Two ways to build a camera overlay

    Two forms of camera overlay: a self-contained file, and a factored stack whose second overlay needs a label from the first

    The stock overlay is self-contained. It is one file with one fragment, and it needs three labels of the base tree and nothing else (section 4). The virtcam overlay has the same form. So a self-contained overlay has no ordering constraint.

    In a factored stack, one overlay creates the nodes that all cameras share and exports labels for them. Then a separate overlay for each camera targets those labels and adds only the sensor.

    More detail: where each form is used, and the first lines of the virtcam overlay
    • Product overlay families are often built as a factored stack. The mux and the channel skeleton are written once, and each camera overlay is a small patch.

    Warning

    Factored overlays out of order.

    • Symptom: the boot succeeds. No /dev/video* exists for the sensor, dmesg has no line of its driver, and its node is missing from /proc/device-tree.
    • Cause: the failed merge means no node. Without a node there is no i2c_client, and no probe function runs (Lesson 01).
    • Fix: list the overlay that creates a label before every overlay that targets it. Check the order with fdtoverlay before the reboot, and check it before reading driver code.

    That is why NVIDIA ships a separate source for two cameras. It holds two VI channels, two ports, two NVCSI channels and both sensors, merged by hand into one file:

                tegra-capture-vi  {
                num-channels = <2>;
                ports {

    Warning

    Two self-contained overlays stacked.

    • Symptom: imx477-A and imx477-C on one OVERLAYS line apply without error, both sensor nodes appear, and only one camera ever streams.
    • Fix: use the file of the arrangement, imx477-dual for two IMX477 cameras. Never stack self-contained overlays.

    Two cameras on a Raspberry Pi 5: one overlay, twice

    The Raspberry Pi overlay avoids both failures with a parameter. Two cameras are two lines of config.txt that name the same file:

    dtoverlay=imx477
dtoverlay=imx477,cam0

    The parameter cam0 changes the targets of the second instance before the merge:

    Raspberry Pi kernel 6.18arch/arm/boot/dts/overlays/imx477_378-overlay.dtsilines 81–87
            cam0 = <&i2c_frag>, "target:0=",<&i2c_csi_dsi0>,
               <&csi_frag>, "target:0=",<&csi0>,
               <&clk_frag>, "target:0=",<&cam0_clk>,
               <&reg_frag>, "target:0=",<&cam0_reg>,
               <&reg_alwayson_frag>, "target:0=",<&cam0_reg>,
               <&cam_node>, "clocks:0=",<&cam0_clk>,
               <&cam_node>, "VANA-supply:0=",<&cam0_reg>;

    Each line of the parameter replaces one reference. The fragments of that instance then patch i2c_csi_dsi0, csi0, cam0_clk and cam0_reg. So the two instances write different nodes, and neither overwrites the other. They need no label of each other, so their order does not matter.

    Self-check

    1. In wp-gpios = <&gpio 4 0>, what does the compiled tree hold in place of &gpio, and where does that value come from?
    Show the answer
    • It holds the phandle of the node that has the label gpio. In the toy tree that number is 1.
    • dtc assigns the phandle at compile time and writes it into the target node as a phandle property.
    • The label itself is not in the property. A compiled tree keeps label names only in a separate table, which section 4 covers.
    How often is a device tree compiled, how often is it merged, and which single artifact shows the result of the merge?
    Show the answer
    • Compilation runs on the build host, once for each source change. Nothing on the board compiles.
    • The merge runs in UEFI at every boot: the base DTB is loaded, and the overlay blobs are applied in order. The result exists only in RAM.
    • The kernel never receives individual overlays.
    • The result is visible on the live board at /proc/device-tree, which section 5 reads.
    The Raspberry Pi overlay for the IMX477 has a node __overrides__. What does it declare, and which program uses it?
    Show the answer
    • It declares the parameters of the overlay. Each line maps a parameter name to a property that it changes, or to a target that it replaces.
    • The bootloader of the Raspberry Pi applies a parameter before the merge, for example dtoverlay=imx477,cam0.
    • fdtoverlay ignores the node. NVIDIA's overlays have no parameters, so each arrangement is a separate file.
    Which blobs contain a __symbols__ node, which contain a __fixups__ node, and which program reads both?
    Show the answer
    • Every blob that dtc -@ compiled has __symbols__: the base DTB (699 labels on r39.2.1) and each overlay, for the labels that the file defines.
    • Only overlays have __fixups__. It lists the labels that the overlay uses and does not define.
    • The program that merges reads both: UEFI at boot, or fdtoverlay on the host. It resolves the fixups of an overlay against the symbols of the tree. Then it adds the symbols of the overlay to the tree.
    In the decompiled stock overlay, mux-gpios = <0xffffffff 0x13 0x00>. What is each of the three cells?
    Show the answer
    • Cell 1 is the phandle of the provider &gpio_aon. It cannot be resolved when the overlay is compiled. So dtc wrote the 0xffffffff placeholder and a __fixups__ entry that points at this property.
    • The merge writes the real phandle into cell 1. On the r39.2.1 base blob it is 262.
    • Cell 2 is the pin: TEGRA234_AON_GPIO(CC, 3) = 2 × 8 + 3 = 19 = 0x13, expanded by cpp before dtc ran.
    • Cell 3 is the flags cell, GPIO_ACTIVE_HIGH = 0.
    A new boot entry has a correct OVERLAYS line and no FDT line. What does the kernel receive, and why?
    Show the answer
    • UEFI uses the copy of the device tree that the boot firmware holds.
    • It applies overlays only to a tree that an FDT line names. So the kernel receives a tree without the nodes of the overlay.
    • The board boots, and no message reports the missing overlay. /proc/device-tree has no camera node.
    • The fix is an FDT line that names the -nv base DTB whose first compatible string equals the one of the running board.
    The stock overlay has four endpoint nodes. Which of them describe a cable, and what do bus-width and port-index state there?
    Show the answer
    • rbpcv3_imx477_out0 in the sensor node and rbpcv3_imx477_csi_in0 in the NVCSI channel describe the MIPI CSI-2 lanes between the camera module and the SoC.
    • bus-width = <2> is the number of data lanes. port-index = <1> is the CSI port that the CAM0 connector is wired to.
    • rbpcv3_imx477_csi_out0 and rbpcv3_imx477_vi_in0 describe the connection from NVCSI to VI inside the SoC: the switch setting that feeds this VI channel from NVCSI port 1. The pixels travel on-chip, and no cable corresponds to it.
    • No endpoint is a device. The drivers of the sensor, NVCSI and VI read them at probe time.
    The stock camera logs as imx477 9-001a on the Jetson and as imx477 11-001a on the Raspberry Pi 5. Where does each bus number come from?
    Show the answer
    • Jetson: aliases of the base tree fix the bus numbers 0 to 8. The adapters of the camera mux get the next free numbers, in the order of the merged tree. The first one is 9.
    • Raspberry Pi 5: each connector has its own I2C controller, and the alias i2c11 names the controller of connector 1. So the number is fixed by the tree.
    The OVERLAYS line lists the practice cam overlay before the practice mux overlay. What fails, where, and what is observed on the booted board?
    Show the answer
    • UEFI applies overlays from left to right. It resolves the __fixups__ of each overlay against the __symbols__ of the merged tree.
    • The only fixup of the cam overlay, practice_mux_i2c0, finds no symbol, because the mux overlay has not been applied yet.
    • The merge fails with FDT_ERR_NOTFOUND, and the node never enters the tree. The board still boots.
    • Observed: no cam@1a under /proc/device-tree/bus@0/i2c@c250000, and nothing in dmesg, because without a DT node no i2c_client is created.
    • On the host, fdtoverlay stops at the first failure and writes no output, so the wrong order is found before a reboot.
    imx477-A.dtbo and imx477-C.dtbo on one OVERLAYS line apply without error. Why is the result wrong, and what does the tree contain?
    Show the answer
    • Both overlays are self-contained, and both write the same nodes: num-channels = <1> in tegra-capture-vi and in the NVCSI node, and one port@0 in each.
    • A merge overwrites existing properties. The tree ends with one VI channel and one NVCSI channel whose endpoints point at CAM1, while both sensor nodes and both badges exist.
    • Nothing fails at merge time or in the boot log.
    • Two cameras need the imx477-dual file, which declares two channels and two ports.
