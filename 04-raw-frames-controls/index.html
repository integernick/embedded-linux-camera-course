Lesson 03 ended with a graph: a sensor, a receiver and a video node. This lesson uses that video node. It captures raw frames with two generic Linux tools, and then it reads one frame byte by byte. No camera service takes part, so every sample in the file is a value that the sensor sent.

Three topics come up, and every camera bring-up meets them. They are the source of the mode list, the meaning of the bytes in a raw frame, and the controls of the sensor. The six sections take them in that order. Each section shows its commands together with their output, so the lesson can be read without a board.

Note

The text describes two boards. The Jetson Orin Nano runs JetPack 7.2.1 (Jetson Linux r39.2.1), with kernel 6.8 in the kernel-noble tree. The Raspberry Pi 5 side is read from the Raspberry Pi kernel at tag stable_20261103, which is Linux 6.18.60. The Jetson is the default board. Each section follows the Jetson first, and its last part shows the same step on the Raspberry Pi 5.

What this lesson uses

The stock camera is the Raspberry Pi High Quality Camera with its Sony IMX477 sensor, enabled by the lab of Lesson 02. NVIDIA's driver nv_imx477 probes it. Every board transcript of this lesson shows that camera.

The two tools are media-ctl and v4l2-ctl, both from the v4l-utils package. media-ctl prints how the parts of the camera connect. v4l2-ctl lists the formats, sets the controls, and writes frames to a file. Neither tool knows anything about NVIDIA. Both use the standard V4L2 and media-controller interfaces of the kernel, so their output is what any V4L2 program sees.

Three small raw files ship with the lesson, in examples/. toy.raw and toy_packed.raw hold 8×4 pixels, and section 2 reads them byte by byte. scene.raw holds 160×120 pixels, and section 3 turns it into pictures. A script of the same directory wrote all three, and the lesson does not need it.

ffmpeg turns a raw file into a picture, in section 3 and in the lab. It is a standard tool: sudo apt install ffmpeg.

virtcam, the course's own sensor driver, appears in section 1 as a second example. Its overlay declares three modes while its driver table has two, and that difference shows which list each tool reads. Lesson 09 covers the driver itself.

The Raspberry Pi side is read from two drivers of the Raspberry Pi kernel. They are imx477.c, the sensor driver of Lesson 01, and rp1-cfe, the driver of the camera front end. Its transcripts are searches in those sources, because this course has no board capture of a Raspberry Pi yet.

1. Where the mode list comes from

A capture starts with a format: a pixel format, a width and a height. So the first question to a camera is which formats it supports. v4l2-ctl asks the video node:

illustrative, not captured on a board
orin$ v4l2-ctl -d /dev/video0 --list-formats-ext
ioctl: VIDIOC_ENUM_FMT
    Type: Video Capture

    [0]: 'RG10' (10-bit Bayer RGRG/GBGB)
        Size: Discrete 3840x2160
            Interval: Discrete 0.033s (30.000 fps)
        Size: Discrete 1920x1080
            Interval: Discrete 0.017s (60.000 fps)

The camera offers one pixel format, RG10, in two sizes with one frame rate each. Three ioctls produce the listing: VIDIOC_ENUM_FMT for the pixel formats, VIDIOC_ENUM_FRAMESIZES for the sizes of each format, and VIDIOC_ENUM_FRAMEINTERVALS for the rates of each size.

None of these numbers is measured from the sensor. Each one comes from a table that a person wrote, in one of two places: the C source of the driver, or the device tree. The place decides where a missing or wrong mode is fixed:

Two sources and two listings: v4l2-ctl reads the C table and the pixel format, Argus reads every mode node

Sizes and rates come from the C table

A mode is one complete setting of the sensor, stored as a table of register values. It fixes the size of the frame and the area of the sensor that is read. It also fixes the bit depth, the range of frame rates and the rate of the CSI-2 link. So a mode is more than a resolution, and two modes can have the same size.

Every tegracam sensor driver has a frmfmt table, a C array with one row per mode. The IMX477 table has two rows, so v4l2-ctl printed two sizes:

Jetson Linux r39.2.1nvidia-oot/drivers/media/i2c/imx477_mode_tbls.hlines 844–847
static const struct camera_common_frmfmt imx477_frmfmt[] = {
    {{3840, 2160}, imx477_30_fr, 1, 0, IMX477_MODE_3840x2160_30FPS},
    {{1920, 1080}, imx477_60_fr, 1, 0, IMX477_MODE_1920x1080_60FPS},
};

Each row is {size, framerate list, framerate count, hdr flag, mode index}. The last field selects the register table that set_mode writes into the sensor over I2C when that mode starts. Those register tables fill the top of the same header.

The pixel format comes from the device tree

The pixel format is not in that table. It comes from the mode node of the sensor in the device tree, the mode0 of the overlay that Lesson 02 applied. Three of its properties state it:

Jetson Linux r39.2.1hardware/nvidia/t23x/nv-public/overlay/tegra234-p3767-camera-p3768-imx477-A.dtslines 216–218
                                mode_type = "bayer";
                                pixel_phase = "rggb";
                                csi_pixel_bit_depth = "10";

Together they say that this mode emits 10-bit Bayer data in the order R, G, G, B. The camera-common layer of tegracam turns the three strings into the media-bus code MEDIA_BUS_FMT_SRGGB10_1X10. A lookup table then turns that code into the V4L2 pixel format V4L2_PIX_FMT_SRGGB10. The API writes that format as 'RG10', a fourcc: four ASCII characters that name a pixel format. That is the [0]: 'RG10' of the listing.

The memory layout comes from the VI table

One more table matters, although v4l2-ctl does not print it. VI must know how to write the pixels of a format into memory, so it has a format table of its own:

Jetson Linux r39.2.1nvidia-oot/drivers/media/platform/tegra/camera/vi/vi5_formats.hlines 110–112
    /* RAW 10 */
    TEGRA_VIDEO_FORMAT(RAW10, 10, SRGGB10_1X10, 2, 1, T_R16,
                RAW10, SRGGB10, "RGRG.. GBGB.."),

The entry for SRGGB10_1X10 says 2 bytes per pixel and the memory format T_R16. So VI stores each 10-bit sample in a 16-bit word. Section 2 reads a file in that layout.

Two lists that nothing compares

The two sources of the listing are written separately, and the build never checks one against the other. Argus, NVIDIA's camera service, makes the gap visible. It never reads the C table. It parses the DT mode nodes, and nvargus_nvraw --lps prints its list. For the stock IMX477 the two lists agree, with two modes in each.

virtcam separates them on purpose. Its C table has two rows, and its overlay declares three modes:

2. The bytes of a raw frame

A capture with v4l2-ctl writes the frames to a file exactly as VI wrote them to memory. Two facts describe that file. The first is the color mosaic of the sensor. The second is the storage of one sample, which section 1 found in the VI table.

A color sensor does not capture color pixels. Each photosite sits under one color filter, and the filters form a repeating 2×2 mosaic. pixel_phase = "rggb" names its order: red and green on even rows, green and blue on odd rows. That is the "RGRG.. GBGB.." string of the VI table. A cell has two green sites by design, because human vision takes most of its detail from green.

The RGGB mosaic of the sensor, and the 16-bit little-endian word that holds one 10-bit sample

Two operations turn such a mosaic into a picture. Demosaicing computes three colors for each pixel from one sample per site. White balance scales red and blue so that a white object appears white. On a Jetson both belong to the ISP, which Argus drives with its 3A loops. A v4l2-ctl capture bypasses all of it: VI writes the output of the sensor's analog-to-digital converter to memory unchanged. Lesson 16 covers the ISP side.

A toy frame, byte by byte

The layout is easier to see on a small frame than on 8 million pixels. The lesson ships such a file, examples/toy.raw: two frames of 8×4 pixels in the layout of a Jetson capture. Every color site of the first frame holds a constant. The R sites hold 600, both green sites hold 900, and the B sites hold 300. So each byte can be checked by hand, from the directory of the lesson:

host$ wc -c < examples/toy.raw
128
host$ od -An -tx1 -N 32 examples/toy.raw
 58 02 84 03 58 02 84 03 58 02 84 03 58 02 84 03
 84 03 2c 01 84 03 2c 01 84 03 2c 01 84 03 2c 01
host$ od -An -tx1 -j 64 -N 8 examples/toy.raw
 ff 03 ff 03 ff 03 ff 03

The file is 128 bytes: 8 × 4 pixels × 2 bytes × 2 frames, with no header and no padding. The first od line is row 0 of the first frame, and the second line is row 1. Each pair of bytes is one pixel, stored as a 16-bit word with the low byte first. So 58 02 is 0x0258 = 600, the R site, and 84 03 is 0x0384 = 900, a green site. Row 1 alternates 900 and 2c 01 = 300, the B site.

The third command reads the start of the second frame. That frame holds the largest 10-bit value at every site: ff 03 is 0x03ff = 1023.

The upper six bits of every word are zero, because a 10-bit sample fills only bits 0 to 9. That is the definition of V4L2_PIX_FMT_SRGGB10 in the kernel documentation (see References), and it matches the T_R16 format of VI. RG12 has the same layout with 12 valid bits and four zero bits. So a frame is always width × height × 2 bytes, and a capture of five frames is five such frames back to back.

A raw file holds neither its size nor its bit depth. So a tool that reads it needs both on its command line. A wrong size gives a scrambled picture and no error message. Section 3 passes both to ffmpeg.

The same samples in a packed file on a Raspberry Pi 5

The front end of the Raspberry Pi can write the samples as they are on the CSI-2 link, without the padding to 16 bits. In that packed layout four 10-bit pixels use five bytes. The lesson ships the same two frames in it, as examples/toy_packed.raw:

host$ wc -c < examples/toy_packed.raw
80
host$ od -An -tx1 -w10 -N 20 examples/toy_packed.raw
 96 e1 96 e1 00 96 e1 96 e1 00
 e1 4b e1 4b 00 e1 4b e1 4b 00

Each line is one row of 8 pixels in 10 bytes, so the file has 80 bytes where the 16-bit file has 128. The first four bytes hold the upper eight bits of four pixels. So 96 is 600 ÷ 4 = 150, and e1 is 900 ÷ 4 = 225. The fifth byte holds the lower two bits of all four, which are zero for these values. The fourcc of this layout is pRAA. The 12-bit layout, pRCC, puts two pixels in three bytes.

3. Why a raw frame looks dark, gridded and green

A raw frame opened in an ordinary image viewer looks broken in three ways: almost black, covered by a fine grid, and green. Each effect is correct raw data. This section shows all three as pictures of one small frame, examples/scene.raw. It holds 160×120 pixels with twelve color patches, as a sensor without white balance records them. The frame is synthetic: a script wrote it, and no camera captured it (verified-on-target: pending for a real capture).

One standard tool makes the pictures. ffmpeg reads a raw file when the command line states its size and its pixel format. Two variables hold what every command of this section repeats:

host$ RAW="-loglevel error -y -f rawvideo -video_size 160x120"
host$ BIG="scale=480:360:flags=neighbor"

$RAW states the size of the frame. $BIG enlarges each picture three times without smoothing.

First, the frame looks almost black

host$ ffmpeg $RAW -pixel_format gray16le -i examples/scene.raw -vf "$BIG" dark.png
The frame read as 16-bit words. The picture is a black rectangle.

gray16le tells ffmpeg that each word holds 16 bits, which an image viewer assumes too. Then 65535 is white. But the brightest sample of this frame is 900, because a 10-bit sample fills only the low bits of its word:

host$ echo "$((900 * 100 / 65535))% of white as 16 bits, $((900 * 100 / 1023))% as 10 bits"
1% of white as 16 bits, 87% as 10 bits

So the fix is to state the true depth. With gray10le, ffmpeg takes 1023 as white:

host$ ffmpeg $RAW -pixel_format gray10le -i examples/scene.raw -vf "$BIG" gray.png
The frame read as 10-bit samples. Twelve grey patches are visible, each with a fine dot pattern.

The twelve patches are visible now. A multiplication of every sample by 64 gives the same result, because it moves the 10 bits to the top of the word.

Second, a fine grid covers the picture

The patches of that picture are not smooth. A crop of the white patch, 16×12 pixels, shows the pattern:

host$ ffmpeg $RAW -pixel_format gray10le -i examples/scene.raw -vf "crop=16:12:12:14,$BIG" grid.png
A crop of the white patch, enlarged. It is a checkerboard of light and dark squares.

The patch is uniform white, and still its samples alternate. Adjacent sites are under different filters. So a white surface gives 900 at the green sites, 450 at the red sites and 540 at the blue sites. In a real capture, the same 2×2 structure is visible at high zoom on any bright, uniform area.

Third, a simple demosaic looks green

bayer_rggb16le tells ffmpeg the order of the mosaic, so it computes three colors for each pixel. ffmpeg has no 10-bit form of this format. So the filter colorlevels sets white to 1023 ÷ 65535 = 0.0156 for each channel:

host$ ffmpeg $RAW -pixel_format bayer_rggb16le -i examples/scene.raw -vf "format=rgb48le,colorlevels=rimax=0.0156:gimax=0.0156:bimax=0.0156,$BIG" green.png
The demosaiced frame. The patches have colors, and the white patch is green.

The patches have colors, and all of them are too green. The white patch shows the cause: its green sites read 900, and its red and blue sites read about half of that. A real sensor behaves in the same way, because its green sites are the most sensitive.

A white balance is one gain for each channel. With a lower white level for red and for blue, the white patch becomes white:

host$ ffmpeg $RAW -pixel_format bayer_rggb16le -i examples/scene.raw -vf "format=rgb48le,colorlevels=rimax=0.0078:gimax=0.0156:bimax=0.0094,$BIG" balanced.png
The same frame after a white balance. Four patches are grey, and eight have their colors.

The two lower levels were chosen for this synthetic frame. For a real scene the ISP finds them, frame after frame.

Important

The capture path of this lesson applies no white balance. The raw path is useful because nothing modifies the pixels. Lesson 16 — ISP and auto-exposure on three stacks covers what the ISP does with this input.

Warning

The raw frame renders black.

  • Symptom: an image viewer shows a black picture.
  • Cause: 10 valid bits in the low bits of 16-bit words, so the brightest sample is 1.6% of white.
  • Fix: state the depth to the tool, gray10le for ffmpeg, or multiply the samples by 64.

The same three effects on a Raspberry Pi 5

The three effects are properties of the sensor data, so a raw frame of a Raspberry Pi shows them too. One step comes first there. A packed frame is unpacked into one word for each pixel, because a viewer for 16-bit words cannot read five-byte groups. After that, the dark image, the grid and the green tint have the causes of this section. On both boards the ISP removes all three, and the raw path does not use the ISP.

4. Controls: what they set, and in which units

Sections 1 to 3 described the shape of a frame. Controls adjust the sensor that produces it: its gain, its exposure time and its frame rate. The V4L2 control API can be queried, so a generic tool lists controls that it has never seen before:

illustrative, not captured on a board
orin$ v4l2-ctl -d /dev/video0 -l
Camera Controls

                     group_hold 0x009a2003 (bool)    : default=0 value=0 flags=execute-on-write
                    sensor_mode 0x009a2008 (int64)   : min=0 max=2 step=1 default=0 value=0 flags=slider
                           gain 0x009a2009 (int64)   : min=16 max=357 step=1 default=16 value=16 flags=slider
                       exposure 0x009a200a (int64)   : min=13 max=683710 step=1 default=2495 value=2495 flags=slider
                     frame_rate 0x009a200b (int64)   : min=2000000 max=30000000 step=1 default=30000000 value=30000000 flags=slider
                    bypass_mode 0x009a2064 (intmenu) : min=0 max=1 default=0 value=0
                override_enable 0x009a2065 (intmenu) : min=0 max=1 default=0 value=0
                   sensor_modes 0x009a2082 (int)     : min=0 max=30 step=1 default=30 value=2 flags=read-only

Each line of the listing has the same parts. First come the name and the numeric ID, then the type in parentheses. After the colon follow the range, the step, the default, the current value and the flags. flags=slider marks a control with a continuous range, and flags=read-only marks one that only reports a value.

Four entries are the sensor controls that the IMX477 driver and virtcam declare: gain, exposure, frame_rate and sensor_mode. Two more, bypass_mode and override_enable, belong to VI (section 5). group_hold holds a group of register writes, so that gain and exposure change in the same frame (Lesson 11). The full listing also has read-only payload controls, such as sensor_signal_properties and sensor_image_properties. Argus reads the DT mode list through them (Lesson 09).

The driver lists its controls, and the framework creates them

A sensor driver does not define these controls. It lists the IDs that it supports and provides a setter for each. The whole list in the IMX477 driver is six lines, and virtcam has the same six:

Jetson Linux r39.2.1nvidia-oot/drivers/media/i2c/nv_imx477.clines 38–43
static const u32 ctrl_cid_list[] = {
    TEGRA_CAMERA_CID_GAIN,
    TEGRA_CAMERA_CID_EXPOSURE,
    TEGRA_CAMERA_CID_FRAME_RATE,
    TEGRA_CAMERA_CID_SENSOR_MODE_ID,
};

The framework does the rest. tegracam owns the control objects: their names, types and flags. At probe it registers one control for each listed ID, and it takes the range of each control from the device tree. Lesson 11 covers the setters.

5. Three controls with side effects

Most controls do what their names say. Three entries of the listing do more: the gain and exposure ranges, sensor_mode, and bypass_mode.

The +1 in the ranges

The device tree says max_gain_val = "356", but the listing shows max=357. The exposure range ends at 683710 instead of 683709. tegracam adds one to both maxima on purpose, when it copies the ranges from the device tree:

Jetson Linux r39.2.1nvidia-oot/drivers/media/platform/tegra/camera/tegracam_ctrls.clines 614–620
        case TEGRA_CAMERA_CID_GAIN:
            err = v4l2_ctrl_modify_range(ctrl,
                ctrlprops->min_gain_val,
                ctrlprops->max_gain_val + 1,
                ctrlprops->step_gain_val,
                ctrlprops->default_gain);
            break;

The extra value is not a gain. It is a marker with the meaning unknown, and a write of it programs nothing.

Some sensors can alternate between two settings of exposure and gain from frame to frame, for HDR. NVIDIA calls that alternating exposure. When it stops, the sensor holds one of the two settings, and no software can tell which.

That is a problem for V4L2. It remembers the last value of every control, and it does not pass a write to the driver when the value did not change. After alternating exposure the remembered value can be wrong. A write of the same number is then dropped, although the sensor holds another setting.

The marker repairs that. A program writes the maximum plus one, and tegracam accepts the value without a call to the driver. The remembered value now differs from every real value, so the next real write reaches the sensor. For a capture with v4l2-ctl one consequence remains: the range in the listing is one larger than the range in the device tree.

Source: the comment, and the check in the control dispatch

Warning

v4l2-ctl -l ranges are off by one against the device tree (max=357, max=683710).

  • Cause: tegracam adds one value to each range, with the meaning unknown. It is not an error.
  • Effect: none for normal use. frame_rate has no sentinel, and the max of sensor_mode equals the number of modes, not modes − 1.

sensor_mode selects the mode, when a flag says so

Section 1 defined a mode: one complete setting of the sensor, and one row of the mode list. On the Jetson, two things decide which row is active, and their names are easy to confuse.

sensor_mode is a control. Its value is the number of a row. For the IMX477, 0 is the 3840×2160 mode and 1 is the 1920×1080 mode. Row N of the C table and the node modeN of the device tree describe the same mode, so one number names both.

use_sensor_mode_id is a flag in the device tree. It does not select a list, because both lists are always in use. It selects the way in which a row is chosen:

use_sensor_mode_id How the mode is chosen
"false", the default From the request. The framework finds the row with the requested width and height. NVIDIA's camera software also compares the color format and the frame rate.
"true" From the number in sensor_mode. A requested size that differs from that row is corrected back, and no error is reported.

Both ways exist because a request cannot always name a mode. Two modes can have the same size and the same rate, for example one that bins and one that crops. With the flag, NVIDIA's camera software names the row directly. NVIDIA's driver guide states both cases (see References). The sensor node of the IMX477 sets the flag:

Jetson Linux r39.2.1hardware/nvidia/t23x/nv-public/overlay/tegra234-p3767-camera-p3768-imx477-A.dtslines 114

The control defaults to 0, the 3840×2160 mode. So on this driver, a 1920×1080 capture with v4l2-ctl needs the control first:

bypass_mode chooses the path to memory

The last two entries of the listing are not sensor controls. The VI channel registers bypass_mode and override_enable on the video node, because the same /dev/video0 serves two capture paths. When Argus owns the camera, it sets bypass_mode to 1. The frames then go through the RTCPU capture path to the ISP, instead of the VI-to-memory path of this lesson.

The default is 0, so direct V4L2 capture works without configuration. However, an Argus session that ended mid-stream can leave the value at 1. That is why Jetson raw-capture recipes include v4l2-ctl -c bypass_mode=0, and the recipe of section 6 starts with it. This lesson does not use override_enable.

Three failures of the capture command have known causes:

Warning

select timeout or Resource temporarily unavailable on --stream-mmap.

  • Cause: the queue started and no frame arrived. The message states only that no pixels reached VI.
  • First checks: dmesg | tail for CSI or VI messages, media-ctl -p for links that are still [ENABLED], bypass_mode=0, and whether nvargus-daemon holds the channel.

Self-check

v4l2-ctl --list-formats-ext against a probed virtcam reports two sizes. Its overlay declares three DT modes, and Argus lists all three. What is the source of each list, and why does the devkit IMX477 not show the same difference?
Show the answer
  • v4l2-ctl enumerates the camera_common_frmfmt[] C table of the driver, which has two rows for virtcam.
  • Argus reads the mode0..modeN nodes of the device tree, and the overlay of virtcam has three.
  • The two consumers read different sources, and the build does not cross-check them. Lesson 09 covers this layer boundary.
  • The stock IMX477 has two modes in its C table and two in its device tree, so its two listings agree.
A captured RG10 frame opened as 16-bit grayscale looks black. What is the arithmetic?
Show the answer
  • RG10 puts each 10-bit sample in the low bits of a 16-bit little-endian word, with the upper six bits zero. That is the T_R16 memory format of VI.
  • The largest sample is 1023 against a 16-bit full scale of 65535, that is 1.6% brightness.
  • A multiplication by 64, a left shift by 6, makes the image visible. In the toy file, 900 becomes 57600.
A simple demosaic looks green. What are the two reasons, and what corrects it in normal operation?
Show the answer
  • Under white light the green sites of the sensor read higher than the red and blue sites. A naive demosaic takes the samples as they are.
  • No white balance has scaled red and blue relative to green.
  • Demosaic and AWB are ISP functions driven by the 3A loops of Argus, and the raw path bypasses the ISP. Lesson 16 uses the ISP path.
With gain_factor = "16" and exposure_factor = "1000000", what do -c gain=64 and -c exposure=8000 set physically?
Show the answer
  • Control value ÷ factor = physical value.
  • Gain 64 ÷ 16 = 4.0× analog gain.
  • Exposure 8000 ÷ 10⁶ s = 8 ms. The device tree gives the exposure limits in microseconds for that reason.
v4l2-ctl -l reports gain: min=16 max=357, and the device tree says max_gain_val = "356". What is the value 357 for?
Show the answer
  • tegracam registers the gain and exposure ranges as the DT maximum plus one.
  • The extra value is a sentinel. It means that a previous alternating-exposure capture left the setting indeterminate. Then the sensor must not be programmed, per the comment above tegracam_init_ctrl_ranges_by_mode().
  • The dispatch of a control write returns 0 without calling the driver when it sees the sentinel. On kernel 6.8 that comparison is guarded by check_add_overflow.
v4l2-ctl --set-fmt-video=width=1920,height=1080 alone keeps producing 3840×2160 frames on this driver. Why, and what is the fix?
Show the answer
  • The device tree sets use_sensor_mode_id = "true", so camera_common_try_fmt takes the mode from the sensor_mode control. It defaults to 0, the 3840×2160 mode.
  • A request that does not match that mode is rewritten to the size of the mode without an error.
  • Fix: run v4l2-ctl -c sensor_mode=1 first, then set the format, and confirm with v4l2-ctl -V.

  • Two lessons in the earlier form still use solutions/bayer_view.py, an older viewer of this lesson, until they are converted.

References

  • v4l2-ctl(1) — v4l-utils — Debian testing — the full option syntax for everything this lesson does with v4l2-ctl: formats, controls and streaming.
  • V4L2_PIX_FMT_SRGGB10 ('RG10') and 10-bit Bayer siblings — The Linux Kernel documentation — the normative memory layout that bayer_view.py assumes: one sample per 16-bit little-endian word, high bits zero.
  • User Controls (V4L2 userspace API) — The Linux Kernel documentation — the control API from the application side, including VIDIOC_QUERYCTRL.
  • Sensor Software Driver Programming — NVIDIA Jetson Linux Developer Guide (r39.2.1) — the reference for the properties of a sensor node. Its entry for use_sensor_mode_id states both ways of selecting a mode.
  • Camera Software Development Solution — NVIDIA Jetson Linux Developer Guide (r39.2.1) — the stack-level description of both capture paths. Its "Applications Using V4L2 IOCTL Directly" section is NVIDIA's statement of the ISP-bypass workflow used in this lesson.
