The sections of the lesson showed the mode list, the raw layout and the controls on small files. This lab is the board work. You capture at both modes of the IMX477 and turn the captures into pictures. Then you sweep a control with a short loop. The brightness of the captures then follows the control.

Goal

  • The control list of the IMX477, saved as imx477-ctrls.txt for a later lesson.
  • Raw captures at both IMX477 modes with the exact sizes, and their pictures from ffmpeg.
  • A sweep of the exposure and of the gain, and a table of brightness against both.

Hardware

  • Orin Nano devkit with JetPack 7.2.1 (Jetson Linux r39.2.1), reachable over SSH. BOARD_USER and BOARD_IP are exported as in Lab 01.
  • The IMX477 on CAM0, with v4l-utils installed since Lab 03.
  • About 200 MB free on the board for the raw files.
  • No container. Every step runs on the board, or on the host to copy a file.

Steps

Step 1 — Install ffmpeg (5 min)

  1. Install ffmpeg, and make a directory for the files of this lab:
orin$ sudo apt install ffmpeg
orin$ mkdir -p ~/lab04 && cd ~/lab04

apt prints its install log. Every later command runs in ~/lab04.

Step 2 — Enumerate the formats and save the control list (10 min)

  1. List the formats:
orin$ v4l2-ctl -d /dev/video0 --list-formats-ext

Record the fourcc and both pairs of size and rate. Compare them with the two rows of imx477_frmfmt[] in nvidia-oot/drivers/media/i2c/imx477_mode_tbls.h that section 1 quotes.

  1. Save the control list to a file. Lesson 09 compares it with the list of virtcam:
orin$ v4l2-ctl -d /dev/video0 -l | tee imx477-ctrls.txt

Note the min, max and default of gain, exposure, frame_rate and sensor_mode. Compare the max of gain and of exposure with the device-tree values quoted in section 4. Each is higher by exactly one. State the reason in one sentence.

Step 3 — Capture five frames at each mode (15 min)

  1. Select the mode by control first, then stream. The two commands are separate on purpose, because controls persist:
orin$ v4l2-ctl -d /dev/video0 -c bypass_mode=0,sensor_mode=0
orin$ v4l2-ctl -d /dev/video0 --set-fmt-video=width=3840,height=2160,pixelformat=RG10 \
        --stream-mmap --stream-count=5 --stream-to=mode0.raw
orin$ ls -l mode0.raw

Expected: five < marks, then a file of 82,944,000 bytes. That is 3840 × 2160 × 2 bytes × 5 frames. If ls -l shows another size, stop and read the Troubleshooting table.

  1. Repeat for mode 1. The sensor_mode control comes first:
orin$ v4l2-ctl -d /dev/video0 -c sensor_mode=1
orin$ v4l2-ctl -d /dev/video0 --set-fmt-video=width=1920,height=1080,pixelformat=RG10 \
        --stream-mmap --stream-count=5 --stream-to=mode1.raw
orin$ ls -l mode1.raw

Expected: 20,736,000 bytes, that is 1920 × 1080 × 2 × 5. Confirm that the driver accepted the smaller mode: v4l2-ctl -d /dev/video0 -V must report 1920x1080.

Step 4 — View the Bayer data (15 min)

  1. Turn the first frame of each capture into two pictures, a grey one and a color one. The commands are those of section 3:
orin$ M0="-loglevel error -y -f rawvideo -video_size 3840x2160"
orin$ M1="-loglevel error -y -f rawvideo -video_size 1920x1080"
orin$ LEVELS="format=rgb48le,colorlevels=rimax=0.0156:gimax=0.0156:bimax=0.0156"
orin$ ffmpeg $M0 -pixel_format gray10le -i mode0.raw -frames:v 1 mode0.png
orin$ ffmpeg $M0 -pixel_format bayer_rggb16le -i mode0.raw -vf "$LEVELS" -frames:v 1 mode0_rgb.png
orin$ ffmpeg $M1 -pixel_format gray10le -i mode1.raw -frames:v 1 mode1.png
orin$ ffmpeg $M1 -pixel_format bayer_rggb16le -i mode1.raw -vf "$LEVELS" -frames:v 1 mode1_rgb.png

The commands print nothing. Each one reads the first frame of its file, because of -frames:v 1.

  1. Open the four pictures in an image viewer, on the board or after an scp to the host. Record three observations:
    • The grey picture is viewable, because gray10le states the true depth. At 800% zoom on a bright, uniform area, you see the 2×2 checkerboard of the mosaic.
    • The color picture has real colors and a green cast. State the reason in one sentence (section 3 of the lesson).
    • Point the camera at a red object and capture one more frame. In the grey picture the red area shows one bright site and three dim sites in each 2×2 cell.

Step 5 — Sweep the exposure, then the gain (15 min)

  1. Define one function that prints the mean and the maximum of a frame. Both are in DN out of 1023:
orin$ stats() { ffmpeg -loglevel error -f rawvideo -video_size 1920x1080 -pixel_format gray10le -i "$1" \
          -vf "scale=in_range=full:out_range=full,signalstats,metadata=print:file=-" -f null - | grep -E 'YAVG|YMAX'; }

The function prints nothing now. YAVG is the mean of all samples, and YMAX is the largest sample.

  1. Sweep the exposure. Keep the scene and the lighting fixed, because no automatic control runs on this path:
illustrative, not captured on a board
orin$ v4l2-ctl -d /dev/video0 -c bypass_mode=0,sensor_mode=1
orin$ for e in 1000 4000 16000; do
          v4l2-ctl -d /dev/video0 -c exposure=$e
          v4l2-ctl -d /dev/video0 --set-fmt-video=width=1920,height=1080,pixelformat=RG10 \
              --stream-mmap --stream-skip=2 --stream-count=1 --stream-to=exposure_$e.raw
          echo "exposure $e"; stats exposure_$e.raw
      done
<
exposure 1000
lavfi.signalstats.YAVG=92.4
lavfi.signalstats.YMAX=411

You get the same four lines for 4000 and for 16000. --stream-skip=2 drops the first two frames, so each file holds one frame.

  1. Write the same loop for gain, with the values 16, 64 and 256. Set exposure=4000 first. This loop is the writing exercise of the lab.

Step 6 — Fill the brightness table (10 min)

  1. Fill the table from the YAVG and YMAX lines:
Setting Value (control units) Physical value Mean (DN) Maximum (DN)
exposure 1000 1 ms
exposure 4000 4 ms
exposure 16000 16 ms
gain 16 1.0x
gain 64 4.0x
gain 256 16.0x
  1. Answer three questions under the table:
    • Is the mean roughly linear in exposure? Four times the exposure should give about four times the mean.
    • Why does the trend flatten when the maximum reaches 1023?
    • Why does the loop skip two frames? The control writes arrive while the sensor already streams its first frames.

On a Raspberry Pi 5

This lab has no Raspberry Pi form yet. Two of its steps are different there, and none is verified on a board (verified-on-target: pending).

  • Step 2. The mode list comes from the subdevice of the sensor, not from a video node.
  • Step 3. Before a capture, a program enables the link to csi2_ch0 and sets a format on each pad. The frames are packed, so the gray10le commands of Step 4 cannot read them as they are.

Expected output

  1. imx477-ctrls.txt, saved in ~/lab04 for a later lesson, with the one-sentence reason for the two +1 ranges.
  2. The captures. mode0.raw of 82,944,000 bytes and mode1.raw of 20,736,000 bytes, with their two pictures each and the three observations.
  3. The two loops of Step 5, saved in a text file.
  4. The brightness table with six measured means and maxima, and the three answers.

A typical form of the result. The absolute numbers depend on the scene and the lighting:

illustrative, not captured on a board
exposure 1000  -> YAVG  92.4, YMAX  411
exposure 4000  -> YAVG 341.7, YMAX 1023
exposure 16000 -> YAVG 953.1, YMAX 1023   <- flattening: samples clip at 1023

Troubleshooting

Symptom Likely cause Fix
select timeout during --stream-mmap No pixels reach VI: mode and format do not match, an Argus session hangs, or a CSI problem Run the two -c commands again. Run sudo systemctl restart nvargus-daemon. Check dmesg | tail -30. Lesson 20 lists further causes
The capture file is four times the expected size sensor_mode is still 0 while 1920x1080 was requested Run v4l2-ctl -c sensor_mode=1, set the format again, and confirm with v4l2-ctl -V
The picture is scrambled or striped The -video_size does not match the captured mode Use the exact width and height of the mode. Check the ls -l arithmetic first
The picture is black The file was read as 16-bit words Use -pixel_format gray10le, which states the true depth
Device or resource busy Another consumer streams the node Run sudo fuser -v /dev/video0, stop the pipeline, and retry
Permission denied on /dev/video0 The user is not in the video group Use sudo for the commands, or run sudo usermod -aG video $USER and log in again
stats prints nothing The file is shorter than one frame, or the function was not defined in this shell Check the size with ls -l. Define the function again
The sweep means change very little with exposure The scene is saturated, or the lighting changed Dim the scene or shorten the exposures. Keep the lighting constant across the sweep
