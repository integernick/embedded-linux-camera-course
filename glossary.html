Silicon / SoC blocks

VI

  • Video Input: the Tegra capture engine (tegra-capture-vi). It receives pixels from NVCSI and writes them into memory buffers by DMA.
  • The V4L2 /dev/video* nodes are the interface to VI channels.

NVCSI

  • The Tegra234 MIPI CSI-2 receiver block (nvcsi@15a00000).
  • It terminates the D-PHY lanes, decodes packets, and routes streams into VI by port and virtual channel.

ISP

  • NVIDIA's hardware image signal processor: demosaic, black level, white-balance gains, color correction, gamma, noise reduction.
  • Only the Argus path uses it. A v4l2-ctl capture bypasses it entirely, which is why raw captures look dark and green.

RTCPU / RCE

  • The camera real-time co-processor ("Real-time Camera Engine"), which runs NVIDIA's firmware blob.
  • It owns per-frame capture scheduling and error detection. Linux communicates with it over capture-IVC channels.
  • Many dmesg capture errors are messages from it. Appendix B covers it in detail.

NVENC

  • NVIDIA's hardware video encoder block. The Orin Nano does not have one.
  • Encoding on this platform is CPU software encoding (x264enc), per NVIDIA's official "Software Encode in Orin Nano" statement. Lesson 19 depends on that fact.

host1x / syncpoint

  • Tegra's DMA and synchronization layer.
  • Syncpoints are hardware counters that engines increment as work completes. The capture stack uses them to signal "frame N landed in buffer B".
  • A capture timeout is a syncpoint that never arrived. On r36 the message is uncorr_err: request timed out. Descriptions of the older vi4 driver name PXL_SOF syncpt timeout.

BPMP

  • Boot and Power Management Processor.
  • It owns clock tree operations. Sensor mclk / extperiph1 requests go through it. It also proxies one of the I2C buses.

Protocol / interface

MIPI CSI-2

  • The camera serial interface protocol: packets that carry pixel data over D-PHY lanes. Lesson 05 covers it.

D-PHY

  • The physical layer under CSI-2 on this platform: one clock lane plus 1–4 data lanes, each a differential pair.
  • Each lane alternates between LP (low-power signaling) and HS (high-speed payload) states.
  • cil_settletime and discontinuous_clk in the DT are D-PHY settings.

virtual channel (VC)

  • A 2-bit field in every CSI-2 packet header. It lets one physical port carry several independent streams.
  • vc-id in the DT selects the channel that a capture receives.
  • A direct-attached sensor sets the VC itself. On a SerDes link the deserializer typically rewrites it, which makes multi-camera aggregation possible.

data type (DT id)

  • The CSI-2 packet-header field that names the payload format: RAW10 = 0x2B, RAW12 = 0x2C.
  • A mismatch between the arriving type and the type that the DT declares produces CHANSEL_NOMATCH errors.

GMSL

  • Maxim/ADI Gigabit Multimedia Serial Link: a coax/twisted-pair SerDes family for cameras that are meters away from the SoC.
  • This course covers SerDes as vendor-neutral theory in Lesson 13, from public ADI datasheets. The practical track uses direct-attached CSI sensors.

serializer

  • The camera-side SerDes chip. It takes the sensor's CSI-2 output and serializes it over the link.
  • The public reference part in this course is ADI's MAX9295D, whose datasheet is freely available.

deserializer

  • The SoC-side SerDes chip. It recovers the stream and emits MIPI CSI-2 into the CAM connector, and rewrites VCs when configured to.
  • The public reference datasheet is ADI's MAX96716A family. Interpretations beyond public documentation are marked as inferred.

SLVS-EC

  • Sony's high-speed sensor interface: 8b/10b-coded lanes with embedded clock, no LP states, link training.
  • Orin has no SLVS-EC receiver, so a bridge to MIPI is mandatory. Lesson 22 is based on that fact.

Bayer / RGGB / RG10 / RG12

  • The color-filter mosaic that raw sensors emit (RGGB pattern here), and its 10/12-bit V4L2 formats.
  • Raw Bayer needs demosaic and white balance, both ISP functions, to look like a photograph.

Kernel objects & frameworks

platform device

  • A block of the SoC with a register window at a fixed address, such as NVCSI or VI. It sits on no scannable bus, so the kernel creates its struct device from its device tree node.
  • The reg property gives the address, as in nvcsi@15a00000. A platform driver probes it by compatible, the same rule as for an I2C device (Lesson 01).

v4l2_subdev

  • The kernel object that represents one entity in a media pipeline, here the sensor driver.
  • It exposes ops tables and controls. VI binds to it at probe, which prints the subdev … bound dmesg line.

media controller

  • The topology API (/dev/media0, media-ctl -p): entities, pads and links that describe how subdevs connect to video nodes.

pad

  • A media-controller connection point on an entity, either sink or source. Formats are negotiated per pad.

ctrl handler

  • v4l2_ctrl_handler: the kernel's control registry per device or subdev.
  • On this platform tegracam builds it from the driver's CID list.

tegracam

  • NVIDIA's sensor-driver framework (tegracam_device, camera_common_data, camera_common_sensor_ops, tegracam_ctrl_ops).
  • The driver provides ops tables and mode metadata, and the framework does the V4L2 and media registration.
  • The tegracam sensor driver:<name>_vX.Y.Z line of the probe log shows its version.

frmfmt table

  • The driver-side mode list (camera_common_frmfmt[]). It feeds V4L2 enumeration only (v4l2-ctl --list-formats-ext).
  • virtcam's table has 2 entries, deliberately different from the 3 modes of its DT. See DT mode nodes and Lesson 09.

DT mode nodes

  • The mode0..modeN device-tree nodes that carry the property set: resolutions, clocks, gain and exposure factors and limits.
  • They feed Argus enumeration. nvargus_nvraw --lps and the GST_ARGUS ranges are read from these nodes, not from the sensor.

the three-struct pattern

  • Physical device struct (i2c_client) ↔︎ private glue struct (the driver's own) ↔︎ framework device (v4l2_subdev/tegracam_device).
  • Every framework driver has this structure, from an I2C joystick on the input subsystem to virtcam (Lesson 01).

videobuf2 (vb2)

  • The kernel's capture-buffer framework: queues, buffer states, and the REQBUFS→QBUF→STREAMON→DQBUF call sequence that Lesson 06's capture.c performs by hand.

dmabuf

  • Fd-based buffer sharing between devices and processes. It is the common buffer handle of the Jetson multimedia stack.
  • The error string dmabuf_fd -1 mapped entry NOT found is a lifetime error in this layer.

NVMM

  • "NVIDIA memory" as a GStreamer caps feature (memory:NVMM).
  • Its buffers stay in device-accessible memory, backed by NvBufSurface, so elements can pass frames without a copy.

NvBufSurface

  • The NVIDIA userspace buffer API behind NVMM: allocation, pitch/block-linear layout, and CPU mapping when needed.

OOT modules

  • NVIDIA's out-of-tree kernel modules (nvidia-oot/). All camera code has been there since JetPack 6.
  • They are built against the kernel headers (kernel-jammy-src on r36.4.4, kernel-noble on r39.2.1) and shipped as oot_modules.tar.xz.

regmap

  • The kernel's register-access abstraction, configured here for 16-bit addr / 8-bit val, plus NVIDIA's regmap_util_write_table_8 for mode-table blobs.
  • It handles 16-bit register addresses, which the i2c_smbus_* helpers cannot.

Userspace stack

Argus

  • NVIDIA's camera userspace: the libargus client API and nvargus-daemon. They own the ISP path, run 3A, and serve nvarguscamerasrc.
  • nvargus_nvraw is its tool for dumping raw frames with metadata.

nvarguscamerasrc

  • The GStreamer source that wraps Argus (NVMM NV12 output).
  • Its sensor-id/sensor-mode indexes are positions in the Argus/DT list, not in the frmfmt list.

badge

  • The module identity string of tegra-camera-platform, which Argus uses to select ISP tuning. virtcam's is jakku_front_VIRTCAM.
  • A badge that does not match degrades color.
  • On JetPack 7.2.1 the badge is the module name that nvargus matches against every nito file it finds. Every badge therefore needs its own tuning file (Lessons 17 and 17).

nito

  • The per-module ISP tuning blob (.nito): AE/AWB tables, noise profiles, LSC and CCMs. It is keyed by badge, and it never touches the sensor.
  • On JP6 a missing nito fell back to default tuning.
  • On JetPack 7.2.1 (Jetson Linux r39.2.1) nvargus requires one per badge and serves nothing without it.
  • A nito holds one knobset per sensor mode, eight at most. Its module name must equal the badge as the daemon prints it.
  • The converter (nvcfg2nito) was partner-only until NVIDIA published it in the JetPack 7.2.1 Customer IQ Migration Tools. A camera hotfix in the same package restores the daemon's text-configuration mode.
  • Lesson 17 produces an untuned nito, and Lesson 17 a tuned one.

personality

  • The course's word for everything that distinguishes one camera from another.
  • It covers the sensor and lens, and the mode table and control table in the device tree. It also covers the nito that tunes the ISP for that sensor behind that lens. Lesson 17 covers it.

conftest.h

  • NVIDIA's generated feature-test header (<nvidia/conftest.h>).
  • At OOT-build time, conftest.sh compile-tests the real kernel headers and emits NV_* macros, for example for one-arg probe and void remove.
  • With these macros one driver source builds on kernel 5.15 and on 6.8.
  • The generated cache is at out/nvidia-conftest/ in a built tree, and the tegracam headers include it transitively. Lesson 21 covers the mechanism.

3A

  • Auto-exposure, auto-white-balance, autofocus.
  • On the course setup, virtcam's ctrl ops ignore the AE writes (the layer boundary), AWB is digital in the ISP, and AF does not exist.

picam-conf

  • The course's MIT-licensed userspace configurator. It parses YAML register sequences and writes them to a real IMX219 over /dev/i2c-*.
  • Its sequences are derived from NVIDIA's GPL imx219_mode_tbls.h by derive_imx219.py and byte-compared on every battery run, so the values cannot differ from their source.

sequences (picam-conf YAML)

  • The picam-conf file schema: a device block (name, i2c_addr) plus named sequences, each an ordered list of write: {reg, val} and sleep_ms steps.

nvvidconv

  • GStreamer element for conversion and scaling, and for moving frames between NVMM and system memory.
  • Every transfer between NVMM and CPU memory in a pipeline goes through it.

x264enc

  • CPU H.264 encoder. It is the only H.264 option on Orin Nano, which has no NVENC.
  • The course pipelines use it with tune=zerolatency speed-preset=ultrafast. At a constrained bitrate that setting produces the block artifacts that Lesson 19 examines.

nvv4l2h264enc

  • The NVENC-backed hardware encoder element on Jetsons that have NVENC. It is not available on Orin Nano.
  • Lessons mention it only to state the difference.

Course-specific shorthand

the stub driver

  • virtcam/virtcam.c, the course's own tegracam sensor driver. Every op returns 0, and the driver consists of metadata only.
  • With it the framework can be studied without a sensor. The layer boundary between what the driver declares and what the hardware does stays visible.

the devkit path

  • Orin Nano devkit and Raspberry Pi IMX477: a real sensor with NVIDIA's own driver (nv_imx477.c).
  • It is the course's reference system for the standard behaviour of the stack.

layer boundary

  • Any point where responsibility passes from one layer to another (driver ↔︎ DT ↔︎ Argus ↔︎ app). Lessons name each layer boundary when they reach one.
  • The two main ones are virtcam's mode lists of 2 and 3 entries, and the AE writes that the stub ignores.
