The sections of the lesson did the arithmetic of one mode. This lab is the board work. You read the PHY settings of the running device tree and fill a worksheet for three modes. Then you record one minute of a healthy link, with its error events counted.

Goal

  • The PHY settings of the two IMX477 modes, read from the running device tree.
  • A worksheet with the rate of one lane for three modes, each line with its unit.
  • A baseline file: one minute of capture at 1920×1080, with the frame events and the error events counted.
  • Two written answers about the declared pixel clock.

Hardware

  • Orin Nano devkit with JetPack 7.2.1 (Jetson Linux r39.2.1), reachable over SSH.
  • The IMX477 on CAM0, with v4l-utils installed since Lab 03.
  • No container. Every step runs on the board.

Steps

Step 1 — Read the settings of the running tree (10 min)

  1. Find the mode nodes of the sensor in the live tree:
illustrative, not captured on a board
orin$ find /proc/device-tree -name 'mode[01]' | sort
/proc/device-tree/bus@0/cam_i2cmux/i2c@0/rbpcv3_imx477_a@1a/mode0
/proc/device-tree/bus@0/cam_i2cmux/i2c@0/rbpcv3_imx477_a@1a/mode1

You get one directory for each mode. Every property of section 7 is a file there.

  1. Print the six properties that the worksheet needs, for both modes:
illustrative, not captured on a board
orin$ for m in $(find /proc/device-tree -name 'mode[01]' | sort); do
          for p in num_lanes csi_pixel_bit_depth active_w active_h max_framerate pix_clk_hz; do
              printf '%s %s = %s\n' "${m##*/}" "$p" "$(tr -d '\0' < "$m/$p")"
          done
      done
mode0 num_lanes = 2
mode0 csi_pixel_bit_depth = 10
mode0 active_w = 3840
mode0 active_h = 2160
mode0 max_framerate = 30000000
mode0 pix_clk_hz = 300000000

The six lines of mode1 follow. Write all twelve values down. The frame rate has six more digits than the rate in frames per second.

Step 2 — Fill the worksheet (15 min)

  1. Copy this table. Fill rows (a) and (b) from Step 1. Row (c) is the first mode of virtcam: 1920×1080, 10 bits, 2 lanes, 30 frames.
# Mode Pixels in a second Bits in a second Bits in a second for each lane Part of 1500 Mbps
a IMX477 mode0
b IMX477 mode1
c virtcam mode0
  1. Compute each cell with the five steps of section 5. The shell can do the arithmetic, as in this example for 1280×720 at 60 frames:
orin$ echo $((1280 * 720 * 60)) $((1280 * 720 * 60 * 10)) $((1280 * 720 * 60 * 10 / 2))
55296000 552960000 276480000

That mode needs 276 megabits per second on each lane, which is 18.4% of the limit. Write the unit into every cell.

  1. Check the result: all three rows fit, and one of them has much less room than the others.

Step 3 — Record a baseline of a healthy link (20 min)

The camera firmware reports frame events and link errors as trace events. You count them over one capture.

  1. Enable the two groups of events and clear the trace buffer:
orin$ sudo sh -c 'cd /sys/kernel/debug/tracing && echo 1 > events/tegra_rtcpu/enable && echo 1 > events/tegra_capture/enable && echo > trace'

The command prints nothing on success.

  1. Capture 3600 frames at 1920×1080, which takes about one minute. Select the mode by control first:
illustrative, not captured on a board
orin$ v4l2-ctl -d /dev/video0 -c bypass_mode=0,sensor_mode=1
orin$ v4l2-ctl -d /dev/video0 --set-fmt-video=width=1920,height=1080,pixelformat=RG10 --stream-mmap --stream-count=3600
<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<<< 59.94 fps

You get one such line for each second. The rate must stay near 60.

  1. Count the frame starts, the frame ends and the errors, and read the kernel log:
illustrative, not captured on a board
orin$ sudo grep -c capture_event_sof /sys/kernel/debug/tracing/trace
3603
orin$ sudo grep -c capture_event_eof /sys/kernel/debug/tracing/trace
3602
orin$ sudo grep -c -E 'vinotify_error|nvcsi_intr' /sys/kernel/debug/tracing/trace
0
orin$ sudo dmesg | tail -5

The first two counts are close to the number of frames. The error count is 0, and dmesg has no new line about the camera.

  1. Write the four results into a file, baseline-imx477.md, with the date and the mode. Then disable the events:
orin$ sudo sh -c 'cd /sys/kernel/debug/tracing && echo 0 > events/tegra_rtcpu/enable && echo 0 > events/tegra_capture/enable'

None of the transcripts of this step is captured on a board with JetPack 7.2.1 yet (verified-on-target: pending). Record what your board prints.

Step 4 — Two written answers (15 min)

This step is the writing exercise. Answer each question in three to five sentences.

  1. In Step 1, pix_clk_hz of mode0 is 300,000,000. Your worksheet has 248,832,000 pixels in a second for that mode. Why is the declared number larger, and why is that correct?
  2. A colleague lowers pix_clk_hz to the number of the worksheet, to "make it exact". What happens, and in which modes?

On a Raspberry Pi 5

Steps 1 and 2 have a Raspberry Pi form. It is not verified on a board yet (verified-on-target: pending).

  • The settings. The endpoint of the sensor holds them: data-lanes and link-frequencies, under the node imx477@1a of /proc/device-tree.
  • The rate. The kernel log has the line Using a link rate of 900 Mbps when a capture starts.
  • The worksheet. The limit is the range of the PHY, 1500 megabits per second for each lane.

Expected output

  1. The twelve values of Step 1.
  2. The worksheet with three rows, every cell with its unit.
  3. baseline-imx477.md with a rate near 60, two frame counts near 3600, and no error event.
  4. The two written answers.

Troubleshooting

Symptom Likely cause Fix
find prints no mode node The camera overlay is not applied Repeat the check of the lab of Lesson 02
The rates are 1.6 times the reference The row used 16 bits for each pixel Use csi_pixel_bit_depth, the depth of the wire
Everything fits with 99.9% of room, or nothing fits The limit was read in the wrong unit The limit is 1,500,000 kilobits per second, which is 1500 megabits per second
The frame rate is near 30 sensor_mode is still 0 Run v4l2-ctl -c sensor_mode=1, and set the format again
The directory events/tegra_rtcpu is missing The command ran without sudo, or tracefs is mounted elsewhere Use sudo. Try /sys/kernel/tracing
Both frame counts are 0 after a capture The events were enabled after the capture, or the buffer was cleared after it Keep the order: enable, clear, capture, count
