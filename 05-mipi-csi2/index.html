Lesson 04 read a raw frame as bytes in memory. This lesson reads the same frame one step earlier, on the wires between the sensor and the SoC. That link is MIPI CSI-2, and both boards of the course use it with the same camera.

The seven sections go from the wires up: the lanes, the packets, the pixels inside a packet, and the virtual channels. Then comes the arithmetic that decides whether a mode fits on the link. Each section shows its commands together with their output, so the lesson can be read without a board.

1. One clock lane, a few data lanes, and two states

The camera cable carries two kinds of connection. One is I2C, for the registers of the sensor. The other is the CSI-2 link, for the pixels. Its electrical layer is called D-PHY. A D-PHY link is one clock lane and one to four data lanes, and each lane is a pair of wires. The cameras of this course use two data lanes.

Two states of a lane

A lane works in one of two ways, and it changes between them many times in a frame.

  • LP, low power. The transmitter drives the two wires separately and slowly. LP states are the control signals of the link. They mark the start and the end of a transmission, and they park the lane between transmissions.
  • The parked state, with both wires high, is LP-11.
  • HS, high speed. The pair carries a small differential signal, at hundreds of megabits per second or more for each lane. The pixels travel in this state.
  • Both edges of the clock lane clock the data. So the frequency of the clock lane is half the bit rate of a data lane.

A burst, and the window that the receiver waits

One transmission in HS is a burst. The lane goes from LP to HS, carries one packet, and returns to LP:

One burst on a data lane. The transmitter signals the start in LP states. The receiver ignores the lane for the settle time, finds the sync byte, and receives the packet. The lane then returns to LP-11.

The receiver sees the LP states and knows that a burst comes. It then ignores the lane for a fixed time, T-HS-SETTLE, while the HS signal of the transmitter becomes stable. After that time it searches for the sync byte. So the time must fit the link. A receiver that searches too early finds noise, and one that starts too late misses the sync byte. Both lose the burst, and the symptom is missing lines or frames on a cable without a fault.

Three settings of a Jetson mode

Each mode of the stock overlay states three properties of this layer:

container$ grep -n -E '^\s+(discontinuous_clk|cil_settletime|lane_polarity) = ' "$OVL"
210:                                discontinuous_clk = "no";
212:                                cil_settletime = "0";
213:                                lane_polarity = "6";
248:                                discontinuous_clk = "no";
250:                                cil_settletime = "0";
251:                                lane_polarity = "6";

The two modes of the IMX477 state the same three values:

  • cil_settletime = "0" is the settle time. The value 0 gives no time of its own, and the receiver then derives the time from the rate of the link.
  • discontinuous_clk = "no" describes the clock lane. With a continuous clock, the clock lane stays in HS between bursts. With a discontinuous clock, it returns to LP between bursts, and the receiver synchronizes again at every burst.
  • lane_polarity = "6" is one bit for each lane. A set bit states that the board swapped the two wires of that pair.
  • On the CAM0 connector of the devkit, two pairs are swapped. The overlay for the other connector states "0".

The kernel passes the settings on, and firmware programs the receiver

On an Orin, the kernel does not write the registers of the receiver. It collects the settings and sends them to the camera firmware, which runs on a separate processor, the RTCPU:

The path of the PHY settings on a Jetson. The mode node is parsed by sensor_common.c. csi5_fops.c fills one message. The camera firmware receives it and writes the CIL registers of NVCSI.

The part of the receiver that ends the lanes is the CIL, the camera interface logic. The code that fills the message shows the settle time and the rate side by side:

A mode node without discontinuous_clk is read as discontinuous.

  • Symptom: a copied mode node works in its source file and gives sync or settle errors at stream start in the copy.
  • Cause: the parser sets the value 1 when the property is absent.
  • Fix: keep discontinuous_clk = "no" in every mode node of a sensor with a continuous clock.
Source: the default of the parser

The Raspberry Pi overlay states this layer in the endpoint of the receiver, with the standard properties of the kernel:

Raspberry Pi kernel 6.18arch/arm/boot/dts/overlays/imx477_378-overlay.dtsilines 60–65

2. Packets: a header that is corrected, a payload that is only checked

Everything that a burst carries is a packet. The receiver cannot ask for a packet again, because the sensor has already sent the next line. So the protocol protects two parts of a packet in two different ways. That difference decides what a link error looks like in a picture.

Two kinds of packet

Short packets have four bytes and carry signals. Frame start and frame end are short packets. Long packets carry the pixels, and in the common case one long packet is one line of the image:

The fields of a long packet. The header has the data ID with the virtual channel and the data type, the word count, and an ECC byte. The payload is one line of pixels. A checksum of two bytes follows it.

The header says what the packet is and how long it is. The payload is the bytes of the pixels, and the checksum is a CRC of the payload.

Two kinds of protection

The ECC byte of the header corrects one wrong bit and detects two. So the receiver repairs a header with one flipped bit, and it still knows the kind and the length of the packet. The CRC of the payload only detects. A line with a wrong CRC cannot be repaired, and the receiver can only drop it or deliver it with a flag.

Damaged part Protection What is observed
Header, one bit The ECC corrects it Nothing in the picture. A counter goes up
Header, two bits or more The ECC detects it and cannot correct it The kind or the length of the packet is lost. A line or a frame is missing
Payload, any bits The CRC detects it The line is delivered with a flag. The picture has streaks, and the frame count is correct

The same three cases in the firmware interface of the Jetson

The header file that defines the interface between the kernel and the camera firmware has one bit for each case:

container$ grep -n 'INTR_STAT_PD_\|INTR_STAT_PH_ECC' $TREE/nvidia-oot/include/soc/tegra/camrtc-capture.h
1681:#define NVCSI_VC_ERR_INTR_STAT_PD_WC_SHORT_ERR     MK_BIT32(3)
1687:#define NVCSI_VC_ERR_INTR_STAT_PD_CRC_ERR      MK_BIT32(2)
1693:#define NVCSI_VC_ERR_INTR_STAT_PH_ECC_SINGLE_BIT_ERR   MK_BIT32(1)

The three bits are the three cases, from the bottom:

  • A header error of one bit, which the ECC corrected. The packet stays intact.
  • A payload with a wrong CRC. A damaged line stays in a delivered frame.
  • A line that is shorter than its word count. That case cannot be repaired.
Source: the three bits with NVIDIA's comments
Jetson Linux r39.2.1nvidia-oot/include/soc/tegra/camrtc-capture.hlines 1677–1693
    /**
     * CSI payload data word count short error. The received data line
     * was incomplete.
     */
#define NVCSI_VC_ERR_INTR_STAT_PD_WC_SHORT_ERR      MK_BIT32(3)

    /**
     * A CRC mismatch was detected in CSI packet payload data.
     * The payload is corrupted.
     */
#define NVCSI_VC_ERR_INTR_STAT_PD_CRC_ERR       MK_BIT32(2)

    /**
     * A single bit error was corrected by ECC in the DPHY CSI
     * packet header.
     */
#define NVCSI_VC_ERR_INTR_STAT_PH_ECC_SINGLE_BIT_ERR    MK_BIT32(1)

So the shape of the damage names the layer. Streaks or bands in frames that arrive at the right rate are payload errors. Frames that disappear, timeouts and short frames are header errors of the kind that cannot be corrected. Lesson 20 builds its decision tree on this difference.

Warning

A CRC error is expected to drop the frame.

  • Symptom: saved frames have streaks, and the frame counters and the frame rate are correct.
  • Cause: a CRC detects and does not correct. The receiver delivers the damaged line with a flag.
  • Fix: read streaks in a delivered frame as evidence about the link, and check the error counters. Do not search in the ISP or in the encoder first.

Embedded lines

A sensor can send lines that are not pixels. Each frame of the IMX477 starts with two lines of embedded metadata: the values of sensor registers for that frame. They travel as long packets with a data type of their own, and they have a CRC like every payload. The mode node of the Jetson states their number as embedded_metadata_height = "2", and virtcam states "0", because it has no sensor behind it.

The Raspberry Pi 5: discard counters, and a node for the embedded lines

The driver of the Raspberry Pi receiver shows link problems in another form. The receiver counts the packets that it discards, in four registers:

Raspberry Pi kernel 6.18drivers/media/platform/raspberrypi/rp1_cfe/csi2.clines 35–38
#define CSI2_DISCARDS_OVERFLOW  0x008
#define CSI2_DISCARDS_INACTIVE  0x00c
#define CSI2_DISCARDS_UNMATCHED 0x010
#define CSI2_DISCARDS_LEN_LIMIT 0x014

The names state the four reasons: an overflow, a channel that is not active, a packet that no channel accepts, and a length limit. When the driver is loaded with its parameter track_csi2_errors, it shows the counters in a debugfs file, csi2_errors. This driver has no counter for a header that the ECC corrected.

The embedded lines have a place of their own there. They leave the kernel through a separate video node, embedded (Lesson 03, section 2).

3. The same pixels on the wire and in memory

The payload of a long packet holds the pixels in a tighter form than the memory of a Jetson. The data type in the header names the form. For the two formats of this course it is one of these numbers:

container$ grep -n 'MIPI_CSI2_DT_RAW1[02]' $TREE/kernel/kernel-noble/include/media/mipi-csi2.h
40:#define MIPI_CSI2_DT_RAW10       0x2b
41:#define MIPI_CSI2_DT_RAW12       0x2c

RAW10 puts four pixels into five bytes. That is the packed layout of Lesson 04, section 2. Four bytes hold the upper eight bits, and one byte holds the four pairs of lower bits. RAW12 puts two pixels into three bytes. So one line on the wire has width × depth ÷ 8 bytes, and that number is the word count in the header of every line.

In memory, a Jetson stores each sample in a 16-bit word. So the same line has two sizes:

host$ echo "$((3840 * 10 / 8)) bytes on the wire, $((3840 * 2)) bytes in memory"
4800 bytes on the wire, 7680 bytes in memory

Both numbers are true, because VI unpacks the samples when it writes them. That gives one rule for every calculation. The bandwidth of a link is computed with the bits of the wire, and the size of a buffer with the bytes of the memory.

Warning

A bandwidth estimate uses the 16 bits of the memory layout.

  • Symptom: every RAW10 estimate is 60% too high, and a mode that works appears to be over the limit.
  • Cause: the wire carries 10 bits for each pixel, and the memory holds 16.
  • Fix: use the depth of the wire, which the mode node states as csi_pixel_bit_depth.

The mode node states the depth of the wire. virtcam writes both depth properties:

virtcamtegra234-p3767-camera-p3768-virtcam-cam0-2lane-overlay.dtslines 149–150
                                dynamic_pixel_bit_depth = "10";
                                csi_pixel_bit_depth = "10";

csi_pixel_bit_depth is the depth on the wire, and the bandwidth code of section 6 reads it. dynamic_pixel_bit_depth differs from it only for a sensor that compresses its pixels. The stock modes of the IMX477 leave it out.

The Raspberry Pi 5: the wire layout can stay

The receiver of the Raspberry Pi can write the payload to memory as it arrives. So a packed frame has the same bytes on the wire and in memory, and Lesson 04 read such a file. The depth of the wire is not a property there. The sensor driver reports it in its media-bus code, such as MEDIA_BUS_FMT_SRGGB10_1X10.

4. Virtual channels: several streams on one port

The first byte of a packet header holds the data type and one more number, the virtual channel. With it, one port can carry several streams at the same time. Every frame start, every line and every frame end is marked with the channel of its stream, and the receiver separates the streams again.

A single sensor does not need this. It sends everything on channel 0, and the cameras of this course do that. Virtual channels matter when several cameras share one port, through a serializer and a deserializer. Then the deserializer gives each camera a channel number. The sensor does not choose it. Lesson 13 covers that side, and this section covers the receiver.

The Jetson states the channel in an endpoint

The endpoint of the sensor in the overlay of virtcam has the property:

virtcamtegra234-p3767-camera-p3768-virtcam-cam0-2lane-overlay.dtslines 268–272
                                    virtcam_out0: endpoint {
                                        vc-id = <0>;
                                        port-index = <1>;
                                        bus-width = <2>;
                                        remote-endpoint = <&virtcam_csi_in0>;

Lesson 02 read this endpoint as a link of the graph. Its three properties are also settings of the protocol: channel 0, port 1 of NVCSI, two lanes. The VI driver reads the channel:

Jetson Linux r39.2.1nvidia-oot/drivers/media/platform/tegra/camera/vi/channel.clines 2581–2585
            /* Get virtual channel id */
            ret = of_property_read_u32(ep, "vc-id", &value);

            /* vc-id is optional, default is 0 */
            chan->virtual_channel = (ret < 0) ? 0 : value;

The property is optional, and a missing one means channel 0. The stock overlay of the IMX477 leaves it out. The check that follows these lines accepts values up to 16, which is more than the four channels of the original two-bit field.

One number in two spellings

The overlay of virtcam states the channel twice, with two names:

host$ grep -n 'vc-id\|vc_id' virtcam/tegra234-p3767-camera-p3768-virtcam-cam0-2lane-overlay.dts
140:                                vc_id = "0";
182:                                vc_id = "0";
224:                                vc_id = "0";
269:                                        vc-id = <0>;
container$ grep -rn '"vc_id"' $TREE/nvidia-oot/ | wc -l
0

vc-id, with a hyphen, is the property of the endpoint that the kernel reads. vc_id, with an underscore, is a string in each mode node. The count of 0 shows that no kernel code reads it. Userspace reads the mode nodes: Argus lists the modes from them. So the same fact is written in two places for two readers, and nothing compares them.

Warning

vc-id is changed and vc_id is not, or the reverse.

  • Symptom: the link is healthy and a capture channel times out. Or a V4L2 capture works and Argus does not.
  • Cause: the kernel separates the streams by vc-id, and Argus reads vc_id from the mode nodes.
  • Fix: change both together, and leave port-index as it is.
More detail: errors are reported for each channel

The error bits of section 2 belong to one virtual channel. The interface to the firmware says so:

Jetson Linux r39.2.1nvidia-oot/include/soc/tegra/camrtc-capture.hlines 1650–1657
    /**
     * NVCSI @ref NvcsiVirtualChannelErrors "virtual channel errors" map
     * to a single CSI virtual channel carried over a CSI port. These
     * errors are also forwarded to VI with each frame-end packet and
     * reported to the client with each affected capture request as
     * part of @ref notify_bits.
     */
    uint32_t nvcsi_virtual_channel_bits;

So when two streams share a port and one of them has errors, the report names the channel.

The receiver of the Raspberry Pi sorts packets by the same header byte. Each discard counter of section 2 also holds the data type and the virtual channel of the packet:

5. The bandwidth of a mode, on paper

A mode is a promise about a link: so many pixels, so many times a second, over so many lanes. Whether the link can keep the promise is arithmetic, and it can be done before any hardware exists.

Five steps

Pixels in a frame = width × height.
  • Pixels in a second = pixels in a frame × frames in a second.
  • Bits in a second = pixels in a second × the depth of the wire.
  • Bits in a second for each lane = bits in a second ÷ the number of lanes.
  • Compare that rate with the limit of the link.

    • The 4K mode of the IMX477

    The first mode of the stock overlay gives the numbers:

    container$ sed -n '205,223p' "$OVL"
                            mode0 { /* IMX477_MODE_3840x2160 */
                                mclk_khz = "24000";
                                num_lanes = "2";
                                tegra_sinterface = "serial_b";
                                phy_mode = "DPHY";
                                discontinuous_clk = "no";
                                dpcm_enable = "false";
                                cil_settletime = "0";
                                lane_polarity = "6";
                                active_w = "3840";
                                active_h = "2160";
                                mode_type = "bayer";
                                pixel_phase = "rggb";
                                csi_pixel_bit_depth = "10";
                                readout_orientation = "90";
                                line_length = "11200";
                                inherent_gain = "1";
                                mclk_multiplier = "80";
                                pix_clk_hz = "300000000";

    The mode is 3840×2160 at 10 bits over 2 lanes. Further down, the same node states max_framerate = "30000000", which is 30 frames in a second. The four steps, one number for each:

    host$ echo $((3840 * 2160)) $((3840 * 2160 * 30)) $((3840 * 2160 * 30 * 10)) $((3840 * 2160 * 30 * 10 / 2))
8294400 248832000 2488320000 1244160000

    So this mode needs 1244 megabits per second on each lane.

    The limit

    The fifth step needs a limit. The overlay of virtcam declares one for the devkit:

    virtcamtegra234-p3767-camera-p3768-virtcam-cam0-2lane-overlay.dtslines 53–54
                    num_csi_lanes = <2>;
                max_lane_speed = <1500000>;

    The unit of max_lane_speed is kilobits per second, so the limit is 1500 megabits per second for each lane. The comparison:

    host$ echo "$((1244160 * 1000 / 1500000)) of 1000 parts of the limit"
829 of 1000 parts of the limit

    The 4K mode uses 82.9% of a lane. It fits, with little room. That explains the mode list of this camera. At 60 frames in a second the same mode would need 2488 megabits per second on each lane, which is 166% of the limit. So the overlay declares 4K at 30 frames, and its second mode drops to 1920×1080 for 60 frames, which uses 41.5%.

    Warning

    max_lane_speed is read in the wrong unit.

    • Symptom: a worksheet shows a use of 0.08% or of 83,000%, and every mode fits or none does.
    • Cause: the unit of the property is kilobits per second.
    • Fix: write the unit on every line of a worksheet, and convert before the comparison.

    Warning

    A limit is carried from one system to another.

    • Cause: the limit is a declaration for one design. In r39.2.1 the stock overlay of the IMX477 no longer has this property, and no kernel code reads it.
    • Symptom: a mode is shown to fit, against the limit of a device tree that the board does not run.
    • Fix: take the limit of the system under review, from its design or from the data sheet of its receiver.
    More detail: the limit in the r39.2.1 tree 
    container$ grep -c 'max_lane_speed' "$OVL"
0
    • The stock overlay of r39.2.1 has no such line. Earlier releases declared the same 1500000 there.
    • The platform driver of r39.2.1, tegra_camera_platform.c, reads one property of that node, en_max_bw. So the number is a design budget, and nothing checks a mode against it at run time.

    The Raspberry Pi 5: the link rate is in the endpoint

    The Raspberry Pi tree states the rate of the link directly. The endpoint of the sensor has it:

    Raspberry Pi kernel 6.18arch/arm/boot/dts/overlays/imx477_378.dtsilines 20–21
                link-frequencies =
                /bits/ 64 <450000000>;

    link-frequencies is the frequency of the clock lane. Both clock edges carry data, so a lane carries twice that number of bits. The driver of the receiver asks the sensor for this frequency and doubles it:

    Raspberry Pi kernel 6.18drivers/media/platform/raspberrypi/rp1_cfe/cfe.clines 1093–1100

                       cfe->csi2.dphy.active_lanes * 2);
    if (link_freq < 0)
        goto err;

    /* x2 for DDR. */
    link_freq *= 2;
    cfe_info("Using a link rate of %lld Mbps\n", link_freq / (1000 * 1000));

    So this link runs at 900 megabits per second for each lane, and 1800 for both. The largest mode of the Raspberry Pi driver is 4056×3040 at 12 bits and 10 frames in a second:

    host$ echo "$((450000000 * 2 / 1000000)) Mbps for each lane, and the largest mode needs $((4056 * 3040 * 10 * 12 / 1000000)) Mbps in all"
900 Mbps for each lane, and the largest mode needs 1479 Mbps in all

    The mode needs 1479 of 1800 megabits per second, so it fits. The limit of this board is in code. The PHY range of section 1 ends at 1500 megabits per second for each lane, and the driver logs a rate outside it.

    6. The clock that the device tree declares

    The worksheet of section 5 used the size and the rate of the mode. The Jetson kernel does the same arithmetic with another number, pix_clk_hz, and that number is larger than the worksheet expects. This section explains the difference, because a wrong value there causes faults that look like a bad cable.

    The kernel computes the rate of a lane

    At probe, sensor_common.c reads the pixel clock of each mode:

    Jetson Linux r39.2.1nvidia-oot/drivers/media/platform/tegra/camera/sensor_common.clines 96–101
        err = read_property_u64(node, "pix_clk_hz", &val64);
    if (err) {
        dev_err(dev, "%s:pix_clk_hz property missing\n", __func__);
        return err;
    }
    signal->pixel_clock.val = val64;

    Then it turns pixels into bits for each lane, and bits into the frequency of the clock lane:

    Jetson Linux r39.2.1nvidia-oot/drivers/media/platform/tegra/camera/sensor_common.clines 129–138
        /* Convert pixel rate to lane data rate */
    if (check_mul_overflow(rate, (u64)depth, &lane_rate)) {
        dev_err(dev, "%s: convert pixel rate to lane data rate overflow\n", __func__);
        return -EINVAL;
    }
    rate = lane_rate / signal->num_lanes;

    if (signal->phy_mode == CSI_PHY_MODE_DPHY) {
        /* MIPI clock rate */
        signal->mipi_clock.val = rate / 2;

    These are steps 3 and 4 of the worksheet. The division by 2 is the fact of section 1: both clock edges carry data. With the declared clock of the 4K mode:

    host$ echo "$((300000000 * 10 / 2)) bits per second for each lane, $((300000000 * 10 / 2 / 2)) Hz on the clock lane"
1500000000 bits per second for each lane, 750000000 Hz on the clock lane

    So the firmware programs the receiver for 1500 megabits per second on each lane. The worksheet gave 1244. The receiver is set for the limit of the design, and the pixels of the mode use 82.9% of it.

    The declared clock covers the blanking

    The two numbers differ because they count different things. The worksheet counted the pixels of the picture: 248,832,000 in a second. pix_clk_hz is the pixel clock of the sensor, 300,000,000, and it also runs during the blanking, the time between lines and between frames. That is why line_length = "11200" is much larger than the width of 3840.

    Three modes show that the declared clock is a property of the timing and not of the picture:

    Mode Pixels of the picture in a second Declared pix_clk_hz Ratio
    IMX477, 3840×2160 at 30 248,832,000 300,000,000 1.21
    IMX477, 1920×1080 at 60 124,416,000 300,000,000 2.41
    virtcam, 1920×1080 at 30 62,208,000 74,250,000 1.19

    The two modes of the IMX477 declare the same clock for half the pixels. The sensor keeps one configuration of its link for both, and the blanking takes the difference. The number of virtcam can be checked exactly, because the course wrote it:

    host$ echo $((2200 * 1125 * 30))
74250000

    That is the standard timing of 1080p at 30 frames: 2200 clocks in a line, 1125 lines in a frame. The mode node of virtcam states line_length = "2200".

    Too high is safe, too low loses data

    The declared clock also sets the speed of the receiver blocks. When a capture channel starts, the VI driver takes the largest clock of all modes:

    Jetson Linux r39.2.1nvidia-oot/drivers/media/platform/tegra/camera/vi/channel.clines 1920–1929
        for (i = 0; i < s_data->sensor_props.num_modes; i++) {
        sensor_mode = &s_data->sensor_props.sensor_modes[i];
        if (sensor_mode->signal_properties.serdes_pixel_clock.val != 0ULL)
            val = sensor_mode->signal_properties.serdes_pixel_clock.val;
        else
            val = sensor_mode->signal_properties.pixel_clock.val;

        /* Select the value from the mode with largest pixel rate and lane numbers */
        if (*pixelclock < val)
            *pixelclock = val;

    A value that is too high runs those blocks faster than needed. That costs power and loses nothing. A value that is too low makes the kernel plan for a slower link than the one that delivers the data. Then the mode works at a small size and fails at full size.

    Warning

    pix_clk_hz is lower than the real pixel clock of the sensor.

    • Symptom: a small mode works, and the full mode has CRC errors or timeouts from time to time. It looks like a signal problem.
    • Cause: the kernel computes the clocks of the receiver for a slower link.
    • Fix: declare the real pixel clock of the sensor, and never a lower one.
    More detail: a second clock for a deserializer
    • In a system with a serializer and a deserializer, the link to the SoC belongs to the deserializer. It has its own clock, about which pix_clk_hz says nothing.
    • The mode node has a second property for that case, serdes_pix_clk_hz. When it is not zero, it replaces pix_clk_hz in the arithmetic of the link, and it must not be lower.
    • The loop above reads serdes_pixel_clock first for that reason. No overlay of the devkit declares it. Lesson 13 covers the deserializer.

    The Raspberry Pi 5: a wrong number stops the probe

    The Raspberry Pi sensor driver does not trust the number of the device tree. It checks each link-frequencies value against what the sensor can produce, and it refuses the device when none fits:

    Raspberry Pi kernel 6.18drivers/media/i2c/imx477.clines 2069–2073
        if (i == ep_cfg.nr_of_link_frequencies) {
        dev_err(dev, "No supported link frequency configured\n");
            ret = -EINVAL;
            goto error_out;
    }

    So a wrong frequency in an overlay gives one line in the log and no camera. On the Jetson, a wrong pix_clk_hz gives a camera that fails later, in some modes, without a message.

    Side by side

    Jetson Raspberry Pi 5
    Clock number in the device tree pix_clk_hz: the pixel clock of the sensor, with the blanking link-frequencies: the frequency of the clock lane
    Who computes the rate of a lane The kernel, from the declared clock, the depth and the lanes The device tree states it, and the receiver doubles it
    A wrong number Too low loses data in large modes, and nothing reports it The sensor driver refuses a frequency that it cannot produce

    Self-check

    1. A frame arrives with the right size and the right frame count, and several of its lines are garbage. Which part of a packet was damaged, and why did the receiver deliver the frame?
    Show the answer
    • The payload. Its CRC detects an error and cannot correct it.
    • The headers were intact, or the ECC corrected them. So the receiver knew every line and every frame boundary, and it delivered the damaged lines with a flag.
    Compute the rate of one lane for the second mode of the IMX477: 1920×1080, 10 bits, 2 lanes, 60 frames in a second. Does it fit under 1500 megabits per second?
    Show the answer
    • 1920 × 1080 × 60 × 10 ÷ 2 = 622,080,000 bits in a second for each lane.
    • That is 41.5% of the limit, so it fits.
    The mode node states cil_settletime = "0". What does the receiver do, and which processor programs the setting?
    Show the answer
    • The value 0 gives no settle time of its own. The receiver derives the time from the clock rate of the link.
    • The kernel sends the settings in one message, and the camera firmware on the RTCPU writes the registers.
    discontinuous_clk = "no": what does the clock lane do between bursts, and what changes when the line is deleted?
    Show the answer
    • The clock lane stays in HS and keeps running between bursts.
    • Without the property the parser assumes a discontinuous clock. The receiver then expects the clock lane to return to LP between bursts, and the sensor does not do that.
    Take one line of the 3840-pixel RAW10 mode. How many bytes are in the payload of its packet, and how many bytes does a Jetson write to memory for it?
    Show the answer
    • 3840 × 10 ÷ 8 = 4800 bytes on the wire.
    • 3840 × 2 = 7680 bytes in memory, because VI stores each sample in a 16-bit word.
    Two cameras share one port through a deserializer. Which part gives camera A the channel 0 and camera B the channel 1? Where does the Jetson state the channel that a capture path accepts?
    Show the answer
    • The deserializer. The sensors do not choose their channel.
    • The vc-id property in the endpoint of the capture path. The vc_id string of the mode nodes must state the same number for Argus.
    The 4K mode declares pix_clk_hz = "300000000", and its picture has 248,832,000 pixels in a second. Is the declaration wrong?
    Show the answer
    • No. The pixel clock also runs during the blanking, so it is always higher than the pixel rate of the picture.
    • The other direction is the fault: a declared clock below the real one makes the kernel plan for a slower link.
    The endpoint of the Raspberry Pi overlay states link-frequencies as 450,000,000. What is the bit rate of one lane, and which code checks it?
    Show the answer
    • 900 megabits per second, because both edges of the clock carry data.
    • The sensor driver checks that the sensor can produce the frequency. The driver of the receiver checks the rate against the range of its PHY, 80 to 1500 megabits per second.
    Which settings of a Jetson mode node have no property in the Raspberry Pi camera overlay, and where is each one decided there?
    Show the answer
    • The settle time: the driver of the receiver selects a PHY range from the link rate.
    • The pixel clock and the line length: they are constants and controls of the sensor driver.
    • The virtual channel and the swapped pairs: the camera overlay does not state them.
