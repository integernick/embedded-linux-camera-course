Step 1 — the first run

  • The count. The program asks for 4 buffers and gets 4. The driver allows 1 to 240, and vb2 allows 32.
  • The size. 4,147,200 bytes is 1920 × 1080 × 2, the sizeimage of the format.
  • The offsets. 0x0, 0x8000, 0x10000 and 0x18000. Each is the index of the buffer, shifted left by 15 bits.
  • The rotation. The indexes run 0, 1, 2, 3 and start again. Four buffers carry all eight frames.

  • The step comes from the timestamps of the driver, not from the clock of the program. So a late program does not change it.
  • The first line shows 0.000, because no earlier buffer exists.

Step 3 — the slow reader

The change is one argument and one call:

this course06-buffers/solutions/grab.clines 100–102
        /* A slow reader: the buffer stays with the program for a while. */
        if (delay_ms)
            usleep(delay_ms * 1000);
  • The first three steps stay at 16.667 ms. All four buffers were queued before the stream started. The hardware filled them one frame apart, while the program slept on the first one.
  • The fifth step is shorter than the later ones. Buffer 0 returned to the driver after the first sleep, in time for an early frame.
  • Then the step is 50 ms. A buffer returns to the driver only every 50 ms. Three frame times pass, and two frames find no buffer.
  • The sequence column hides the loss. The Jetson driver counts the buffers that it returns, so the numbers run 1 to 8. The step column shows the loss.
  • On a Raspberry Pi 5, the sequence numbers jump by more than one in the second half of the run.

Step 4 — the exported buffer

The export goes after VIDIOC_STREAMOFF:

this course06-buffers/solutions/grab.clines 111–118
    /* EXPBUF: buffer 0 gets a second name, a dmabuf file descriptor. */
    memset(&exp, 0, sizeof(exp));
    exp.type = type;
    exp.index = 0;
    exp.flags = O_RDONLY;
    check(ioctl(fd, VIDIOC_EXPBUF, &exp), "VIDIOC_EXPBUF");
    printf("buffer 0 through the mapping: %02x %02x\n",
           map[0].start[0], map[0].start[1]);

The second mapping goes after the close of the video node:

this course06-buffers/solutions/grab.clines 125–130
    /* The queue and the video node are gone. The dmabuf still names the pages. */
    shared = mmap(NULL, map[0].length, PROT_READ, MAP_SHARED, exp.fd, 0);
    check(shared == MAP_FAILED ? -1 : 0, "mmap of the dmabuf");
    printf("buffer 0 through the dmabuf: %02x %02x\n", shared[0], shared[1]);
    munmap(shared, map[0].length);
    close(exp.fd);
  • The two lines print the same bytes, because both mappings show the same pages.
  • VIDIOC_REQBUFS with a count of 0 does not free these pages. The dmabuf holds a reference, as section 6 showed in the allocator.
  • The pages are freed at close(exp.fd), the last use of the descriptor.

Step 5 — the two answers

Copies on the way to grab

  • None. The hardware writes the frame into the pages of a buffer.
  • The program maps the same pages and reads two bytes from them.
  • VIDIOC_DQBUF passes an index and a few numbers. It passes no pixels.

The first copy of the capture to a file

  • The path to the buffer is the same, so the frame arrives without a copy.
  • The first copy is the write of v4l2-ctl to the file. The kernel copies the frame from the buffer into its file cache.
  • A second transfer follows, from the cache to the storage device.
  • So a capture to a file is limited by the storage, not by the camera.
