Section 3 of the lesson read grab.c. In this lab you build it on the board and run it. Then you change it three times. Each change is a few lines, and each one shows a rule of the lesson on real frames.

Goal

  • grab built on the board, with the output of section 3.
  • The step between two frames, measured from the timestamps of the driver.
  • A run with a slow reader, and the frames that it loses.
  • A frame read through a dmabuf after its queue and its video node are closed.
  • Two written answers about copies.

Hardware

  • Orin Nano devkit with JetPack 7.2.1 (Jetson Linux r39.2.1), reachable over SSH. BOARD_USER and BOARD_IP are exported as in Lab 01.
  • The IMX477 on CAM0, with v4l-utils installed since Lab 03.
  • No container. The program builds on the board.

Steps

Step 1 — Build the program and run it (10 min)

  1. Install the compiler on the board, and make a folder for the lab:
orin$ sudo apt install -y build-essential
orin$ mkdir -p ~/lab06

The first command prints the progress of apt. The second prints nothing.

  1. Copy the program from the course repository to the board:
host$ scp lessons/06-buffers/examples/grab.c "$BOARD_USER@$BOARD_IP:lab06/"

scp prints one progress line.

  1. Build it with all warnings on:
orin$ cd ~/lab06 && gcc -Wall -Wextra -Werror -O2 -o grab grab.c

The compiler prints nothing on success.

  1. Select the 60-frame mode and its format, then run the program:
illustrative, not captured on a board
orin$ v4l2-ctl -d /dev/video0 -c bypass_mode=0,sensor_mode=1
orin$ v4l2-ctl -d /dev/video0 --set-fmt-video=width=1920,height=1080,pixelformat=RG10
orin$ ./grab
asked for 4 buffers, got 4
buffer 0: 4147200 bytes at offset 0x0
buffer 1: 4147200 bytes at offset 0x8000

Ten more lines follow, as in section 3 of the lesson. Check four things: the count, the size, the offsets and the rotation of the buffers.

Step 2 — Measure the step between two frames (10 min)

The driver stamps every buffer with the time of its frame. The difference of two stamps is the frame time.

  1. In the loop, compute the time of the buffer in milliseconds. Keep the time of the buffer before it in a variable.
  2. Print the difference in place of the time. Use %.3f ms.
  3. Build and run:
illustrative, not captured on a board
orin$ ./grab | tail -4
buffer 0: sequence 5, 4147200 bytes, step 16.667 ms, first bytes 5c 01
buffer 1: sequence 6, 4147200 bytes, step 16.666 ms, first bytes 5c 01
buffer 2: sequence 7, 4147200 bytes, step 16.667 ms, first bytes 5d 01
buffer 3: sequence 8, 4147200 bytes, step 16.667 ms, first bytes 5c 01

The step is one frame time of the mode. Repeat the run with sensor_mode=0 and the 3840×2160 format. Write both steps down.

Step 3 — A slow reader (10 min)

The loop returns each buffer at once. A real program works on the frame first. This step shows what a slow reader costs.

  1. Add a second argument to the program: a delay in milliseconds.
  2. Sleep for that time with usleep, after the printf and before the VIDIOC_QBUF of the loop.
  3. Select the 60-frame mode again. Build, and run with a delay of 50 ms:
illustrative, not captured on a board
orin$ ./grab /dev/video0 50 | tail -8
buffer 0: sequence 1, 4147200 bytes, step 0.000 ms, first bytes 5c 01
buffer 1: sequence 2, 4147200 bytes, step 16.667 ms, first bytes 5d 01
buffer 2: sequence 3, 4147200 bytes, step 16.667 ms, first bytes 5c 01
buffer 3: sequence 4, 4147200 bytes, step 16.666 ms, first bytes 5b 01
buffer 0: sequence 5, 4147200 bytes, step 33.333 ms, first bytes 5c 01
buffer 1: sequence 6, 4147200 bytes, step 50.001 ms, first bytes 5c 01
buffer 2: sequence 7, 4147200 bytes, step 50.000 ms, first bytes 5d 01
buffer 3: sequence 8, 4147200 bytes, step 49.999 ms, first bytes 5c 01

Record your eight steps. Two questions follow from them. Why do the first three steps stay at one frame time? And which column of the output hides the lost frames?

Step 4 — A buffer that outlives its queue (15 min)

This step gives buffer 0 a second name and then removes the first one.

  1. After VIDIOC_STREAMOFF, export buffer 0 with VIDIOC_EXPBUF. The structure is struct v4l2_exportbuffer. Set its type, its index and flags = O_RDONLY.
  2. Print the first two bytes of buffer 0 through the mapping of the program.
  3. Keep the rest of the teardown as it is: munmap, VIDIOC_REQBUFS with a count of 0, and close.
  4. After the close, map the descriptor of the export with mmap, at offset 0. Print the first two bytes again.
  5. Build and run:
illustrative, not captured on a board
orin$ ./grab | tail -2
buffer 0 through the mapping: 5c 01
buffer 0 through the dmabuf: 5c 01

The two lines must show the same bytes. At the second line, the program has no queue and no video node.

Step 5 — Two written answers (10 min)

This step is the writing exercise. Answer each question in three to five sentences.

  1. grab reads two bytes of each frame. How many times is a frame copied between the sensor and that read?
  2. The capture of Lab 04 used v4l2-ctl --stream-to=mode1.raw. Where is the first copy of a frame on that path, and who makes it?

None of the transcripts of this lab is captured on a board with JetPack 7.2.1 yet (verified-on-target: pending). Record what your board prints.

On a Raspberry Pi 5

The same file builds and runs on a Raspberry Pi 5. This form is not verified on a board yet (verified-on-target: pending).

  • Before Step 1. Enable the link to the video node and set the formats of the graph, as in Lesson 03.
  • Step 1. The offsets are 0x20000 apart, and the first sequence number is 0.
  • Step 3. The lost frames show as gaps in the sequence numbers.

Expected output

  1. The output of Step 1, with four buffers and eight frames.
  2. The two steps of Step 2, one for each mode.
  3. The eight steps of Step 3, with the two answers.
  4. The two lines of Step 4, with the same bytes.
  5. The two written answers.

Troubleshooting

Symptom Likely cause Fix
linux/videodev2.h: No such file or directory The kernel headers for programs are missing Install build-essential, which brings linux-libc-dev
/dev/video0: Permission denied The user is not in the group video Run with sudo, or add the user to the group as in Lab 04
VIDIOC_REQBUFS: Device or resource busy Another program streams the node Find it with sudo fuser -v /dev/video0 and stop it
The program prints the buffers and then hangs No frame arrives, and VIDIOC_DQBUF blocks Stop it with Ctrl-C. Set bypass_mode=0, then check dmesg
The size is 16588800 bytes The node still has the 3840×2160 format Set sensor_mode=1 and the 1920×1080 format again
Every step of Step 2 is 0.000 ms The time of the earlier buffer is not stored Store it after the printf
VIDIOC_EXPBUF: Invalid argument The type or the index of the structure is not set Clear the structure with memset, then set both fields
mmap of the dmabuf: Permission denied The mapping asks for more than the export allows Use PROT_READ with O_RDONLY
