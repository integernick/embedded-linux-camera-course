Lesson 04 captured raw frames with v4l2-ctl --stream-mmap, and the tool handled the buffers. This lesson opens that step. A frame is several megabytes, and it arrives many times in a second. So the kernel and the program do not copy it. They pass the ownership of a buffer back and forth.

The seven sections follow one buffer. They start at the queue in the kernel and at the states of a buffer. Then come the calls of a program, the hooks of a driver, and the three ways to put memory under a buffer. The last two sections cover dmabuf, which shares a buffer between devices, and the cost of a copy. Each section shows its commands together with their output, so the lesson can be read without a board.

Note

The text describes two boards. The Jetson Orin Nano runs JetPack 7.2.1 (Jetson Linux r39.2.1), with kernel 6.8 in the kernel-noble tree. The Raspberry Pi 5 side is read from the Raspberry Pi kernel at tag stable_20261103, which is Linux 6.18.60. The Jetson is the default board. Each section follows the Jetson first, and its last part shows the same step on the Raspberry Pi 5.

1. One queue, two owners

Every capture driver has the same problem. A program needs a steady stream of full frames. The hardware needs a steady supply of empty memory. Neither side may wait for the other, and neither may write into memory that the other one reads.

The kernel solves this problem once. videobuf2 owns the queue of buffers and implements the calls of the program. The driver adds a few hooks that feed its hardware. Lesson 01 showed the same division for a device: the framework owns the object, and the driver fills in the operations.

The queue belongs to the receiver

The buffers belong to the driver of the receiver, because the receiver writes the frames to memory. The sensor driver never sees a buffer. Its work ends when the sensor streams.

On the Jetson, the queue is a field of struct tegra_channel, with one channel for each video node. The channel driver initializes it:

Jetson Linux r39.2.1nvidia-oot/drivers/media/platform/tegra/camera/vi/channel.clines 2821–2832
    chan->queue.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    chan->queue.io_modes = VB2_MMAP | VB2_DMABUF | VB2_READ | VB2_USERPTR;
    chan->queue.lock = &chan->video_lock;
    chan->queue.drv_priv = chan;
    chan->queue.buf_struct_size = sizeof(struct tegra_channel_buffer);
    chan->queue.ops = &tegra_channel_queue_qops;
#if IS_ENABLED(CONFIG_VIDEOBUF2_DMA_CONTIG)
    chan->queue.mem_ops = &vb2_dma_contig_memops;
#endif
    chan->queue.timestamp_flags = V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC
                   | V4L2_BUF_FLAG_TSTAMP_SRC_EOF;
    ret = vb2_queue_init(&chan->queue);

Four of these assignments decide how the queue works:

  • io_modes lists the memory models that the queue accepts. Section 5 covers them.
  • mem_ops selects the allocator. vb2_dma_contig_memops gives each buffer one contiguous range of addresses for the hardware.
  • ops names the table of the driver's hooks. Section 4 reads it.
  • buf_struct_size makes vb2 allocate the driver's own buffer structure in place of the plain one.

One grep finds three of them:

The buffer structure of the driver

The structure that buf_struct_size names is the driver's wrapper around a vb2 buffer:

Jetson Linux r39.2.1nvidia-oot/include/media/mc_common.hlines 68–81
struct tegra_channel_buffer {
    struct vb2_v4l2_buffer buf;
    struct list_head queue;
    struct tegra_channel *chan;

    unsigned int vb2_state;
    unsigned int capture_descr_index[TEGRA_CSI_BLOCKS];

    dma_addr_t addr;

    u32 thresh[TEGRA_CSI_BLOCKS];
    int version;
    int state;
};

The first member is the buffer of vb2. The other members belong to the driver: a list node for its own lists, and addr, the address that the hardware writes to. This is the pattern of Lesson 01 again. The framework's structure sits inside the driver's structure, and container_of converts one pointer into the other.

More detail: why the allocator is "contiguous"
  • The capture hardware writes a frame through DMA, and it takes one start address for the whole frame.
  • So the frame must be one unbroken range in the address space of the device.
  • The physical pages do not have to be adjacent. The IOMMU of the SoC maps scattered pages to one range of device addresses.
  • vb2_dma_contig_memops hides this. The driver gets one address for each buffer.

2. A buffer is always in one state

videobuf2 models a capture as a loop of ownership. At every moment a buffer is in exactly one state, and the state says who may touch its memory. The header of the framework lists the states:

Jetson Linux r39.2.1kernel/kernel-noble/include/media/videobuf2-core.hlines 209–231
/**
 * enum vb2_buffer_state - current video buffer state.
 * @VB2_BUF_STATE_DEQUEUED: buffer under userspace control.
 * @VB2_BUF_STATE_IN_REQUEST:   buffer is queued in media request.
 * @VB2_BUF_STATE_PREPARING:    buffer is being prepared in videobuf2.
 * @VB2_BUF_STATE_QUEUED:   buffer queued in videobuf2, but not in driver.
 * @VB2_BUF_STATE_ACTIVE:   buffer queued in driver and possibly used
 *              in a hardware operation.
 * @VB2_BUF_STATE_DONE:     buffer returned from driver to videobuf2, but
 *              not yet dequeued to userspace.
 * @VB2_BUF_STATE_ERROR:    same as above, but the operation on the buffer
 *              has ended with an error, which will be reported
 *              to the userspace when it is dequeued.
 */
enum vb2_buffer_state {
    VB2_BUF_STATE_DEQUEUED,
    VB2_BUF_STATE_IN_REQUEST,
    VB2_BUF_STATE_PREPARING,
    VB2_BUF_STATE_QUEUED,
    VB2_BUF_STATE_ACTIVE,
    VB2_BUF_STATE_DONE,
    VB2_BUF_STATE_ERROR,
};

Five of the seven states carry a capture:

The states of one buffer during a capture. QBUF moves it from the program to videobuf2, and buf_queue gives it to the driver. vb2_buffer_done returns it as DONE or ERROR, and DQBUF gives it back to the program.
  • DEQUEUED. The program owns the buffer. It may read the pixels and save them.
  • QUEUED. The program has given the buffer to the kernel. The driver does not have it yet.
  • ACTIVE. The driver has the buffer, and the hardware may write to it at any moment.
  • DONE. The buffer holds a frame and waits for the program.
  • ERROR. The buffer returns to the program with a flag, V4L2_BUF_FLAG_ERROR. Its content is not trusted.

Who moves a buffer

The program moves a buffer with two calls. VIDIOC_QBUF gives it to the kernel, and VIDIOC_DQBUF takes it back. Inside the kernel, vb2 makes a buffer ACTIVE in the same function that hands it to the driver:

Jetson Linux r39.2.1kernel/kernel-noble/drivers/media/common/videobuf2/videobuf2-core.clines 1462–1472
static void __enqueue_in_driver(struct vb2_buffer *vb)
{
    struct vb2_queue *q = vb->vb2_queue;

    vb->state = VB2_BUF_STATE_ACTIVE;
    atomic_inc(&q->owned_by_drv_count);

    trace_vb2_buf_queue(q, vb);

    call_void_vb_qop(vb, buf_queue, vb);
}

The driver ends the ACTIVE state. It calls vb2_buffer_done with DONE or ERROR. The Jetson driver chooses between the two from the status of the frame:

container$ sed -n '608,611p' $TREE/nvidia-oot/drivers/media/platform/tegra/camera/vi/vi5_fops.c
    if (frame_err)
        buf->vb2_state = VB2_BUF_STATE_ERROR;
    else
        buf->vb2_state = VB2_BUF_STATE_DONE;

The function that returns the buffer also numbers it:

Jetson Linux r39.2.1nvidia-oot/drivers/media/platform/tegra/camera/vi/vi5_fops.clines 466–481
static void vi5_release_buffer(struct tegra_channel *chan,
    struct tegra_channel_buffer *buf)
{
    struct vb2_v4l2_buffer *vbuf = &buf->buf;

    if (check_add_overflow(chan->sequence, 1U, &chan->sequence)) {
        dev_err(chan->vi->dev, "%s:chan sequence overflow\n", __func__);
        return;
    }

    vbuf->sequence = chan->sequence;
    vbuf->field = V4L2_FIELD_NONE;
    vb2_set_plane_payload(&vbuf->vb2_buf, 0, chan->format.sizeimage);

    vb2_buffer_done(&vbuf->vb2_buf, buf->vb2_state);
}

The counter grows by one for each buffer that the driver returns. So the first frame of a Jetson capture has the sequence number 1, and the numbers have no gaps.

Two rules of the loop

Warning

A buffer that is read between QBUF and DQBUF holds parts of two frames.

  • Symptom: a picture with a horizontal break, and no error from any call.
  • Cause: after QBUF the memory belongs to the hardware, which writes into it while the program reads.
  • Fix: read a buffer only between its DQBUF and its next QBUF.

Warning

A queue that runs empty loses frames.

  • Symptom: the frame rate of the capture is lower than the rate of the sensor.
  • Cause: the sensor sends a frame every 16.7 ms in the 60-frame mode. A frame that finds no ACTIVE buffer is not stored.
  • Fix: return each buffer with QBUF before the next frame, or request more buffers.

The same states on a Raspberry Pi 5

The states are the same, because the header is the same file of the kernel. The driver of the receiver returns a buffer in its interrupt handler, at the end of a frame:

The function that it calls sets the number and ends the ACTIVE state:

Raspberry Pi kernel 6.18drivers/media/platform/raspberrypi/rp1_cfe/cfe.clines 654–655

    vb2_buffer_done(&node->cur_frm->vb.vb2_buf, state);

Here the number comes from fs_count, the count of frame starts on the link. So the two boards number their buffers in different ways. On a Raspberry Pi 5, a lost frame leaves a gap in the sequence numbers. On the Jetson it does not, and only the timestamps show it.

3. The loop of a capture program

The calls of the program are the verbs of the state machine. One capture makes them in this order:

The calls of one capture, from REQBUFS to the release of the buffers. The four parties are the program, videobuf2, the driver of the receiver and the capture hardware.

examples/grab.c makes exactly these calls and nothing else. It sets no format, so the format of the node is set with v4l2-ctl first. The program starts with the request for buffers:

this course06-buffers/examples/grab.clines 48–54
    /* REQBUFS: the kernel allocates the buffers and answers with a count. */
    memset(&req, 0, sizeof(req));
    req.count = NBUF;
    req.type = type;
    req.memory = V4L2_MEMORY_MMAP;
    check(ioctl(fd, VIDIOC_REQBUFS, &req), "VIDIOC_REQBUFS");
    printf("asked for %d buffers, got %u\n", NBUF, req.count);

VIDIOC_REQBUFS is a negotiation. The program asks for a count, and the kernel writes the granted count back into the same structure. Then the program maps each buffer and queues it:

this course06-buffers/examples/grab.clines 59–76
    for (i = 0; i < req.count; i++) {
        memset(&buf, 0, sizeof(buf));
        buf.type = type;
        buf.memory = V4L2_MEMORY_MMAP;
        buf.index = i;

        /* QUERYBUF and mmap: the program maps the pages of buffer i. */
        check(ioctl(fd, VIDIOC_QUERYBUF, &buf), "VIDIOC_QUERYBUF");
        map[i].length = buf.length;
        map[i].start = mmap(NULL, buf.length, PROT_READ, MAP_SHARED,
                    fd, buf.m.offset);
        check(map[i].start == MAP_FAILED ? -1 : 0, "mmap");
        printf("buffer %u: %u bytes at offset 0x%x\n",
               i, buf.length, buf.m.offset);

        /* QBUF: the buffer now belongs to the driver. */
        check(ioctl(fd, VIDIOC_QBUF, &buf), "VIDIOC_QBUF");
    }

VIDIOC_QUERYBUF returns the length of a buffer and an offset. mmap with that offset gives the program a view of the pages of the buffer. Nothing is copied: the hardware and the program then use the same memory under two addresses. The rest is the stream itself:

this course06-buffers/examples/grab.clines 78–95
    /* STREAMON: the driver starts the hardware. */
    check(ioctl(fd, VIDIOC_STREAMON, &type), "VIDIOC_STREAMON");

    for (i = 0; i < NFRAMES; i++) {
        memset(&buf, 0, sizeof(buf));
        buf.type = type;
        buf.memory = V4L2_MEMORY_MMAP;

        /* DQBUF: wait for a full buffer. It belongs to the program. */
        check(ioctl(fd, VIDIOC_DQBUF, &buf), "VIDIOC_DQBUF");
        printf("buffer %u: sequence %u, %u bytes, time %ld.%06ld, first bytes %02x %02x\n",
               buf.index, buf.sequence, buf.bytesused,
               (long)buf.timestamp.tv_sec, (long)buf.timestamp.tv_usec,
               map[buf.index].start[0], map[buf.index].start[1]);

        /* QBUF: give the buffer back for a later frame. */
        check(ioctl(fd, VIDIOC_QBUF, &buf), "VIDIOC_QBUF");
    }

VIDIOC_DQBUF blocks until a buffer is DONE. The kernel fills in the index of the buffer, the sequence number, the count of bytes and the timestamp. The program reads two bytes of the frame through its mapping, and it gives the buffer back.

  • The size. Each buffer has 4,147,200 bytes, which is 1920 × 1080 × 2. It is the frame size of Lesson 04.
  • The offsets. They are 32,768 apart, and the buffers are four megabytes each. So an offset is not an address. It is a ticket that names the buffer to mmap.
  • The rotation. Four buffers carry eight frames. Each buffer is filled, read, returned and filled again.
  • The time. Two timestamps are 16.667 ms apart, which is one frame at 60 frames in a second.
Source: how videobuf2 computes the offset
Jetson Linux r39.2.1kernel/kernel-noble/drivers/media/common/videobuf2/videobuf2-core.clines 375–389
    /*
     * The offset "cookie" value has the following constraints:
     * - a buffer can have up to 8 planes.
     * - v4l2 mem2mem uses bit 30 to distinguish between
     *   OUTPUT (aka "source", bit 30 is 0) and
     *   CAPTURE (aka "destination", bit 30 is 1) buffers.
     * - must be page aligned
     * That led to this bit mapping when PAGE_SHIFT = 12:
     * |30                |29        15|14       12|11 0|
     * |DST_QUEUE_OFF_BASE|buffer index|plane index| 0  |
     * where there are 15 bits to store the buffer index.
     * Depending on PAGE_SHIFT value we can have fewer bits
     * to store the buffer index.
     */
    offset = vb->index << PLANE_INDEX_SHIFT;
  • With pages of 4 KB, PAGE_SHIFT is 12, and the shift is 15. So buffer 1 has the offset 0x8000.
  • The offset holds the index of the buffer and the index of the plane. It holds no address.
More detail: waiting with a limit
  • A blocking VIDIOC_DQBUF waits without a limit. A program with a dead sensor then hangs.
  • poll() on the video node returns when a buffer is DONE, and it takes a timeout.
  • v4l2-ctl waits this way. Its select timeout message of Lesson 04 is that timeout.
  • A real program uses poll(). grab.c blocks, so that the loop stays short.

The same program on a Raspberry Pi 5

The same file builds and runs on a Raspberry Pi 5, because the calls belong to V4L2 and not to a board. Three things differ, and none of them is captured on a board yet (verified-on-target: pending).

  • The graph comes first. The link to the video node and the formats of the pads are set with media-ctl, as in Lesson 03.
  • The bytes are packed. The count of bytes follows the packed layout of Lesson 04, and the first bytes are not one sample.
  • The offsets are wider. The kernel of the Raspberry Pi 5 uses pages of 16 KB, so the shift is 17 and buffer 1 has the offset 0x20000.

Three of its entries handle buffers: queue_setup, buf_prepare and buf_queue.

queue_setup answers REQBUFS

vb2 calls queue_setup when the program requests buffers. The hook answers two questions: how many buffers, and how large.

Jetson Linux r39.2.1nvidia-oot/drivers/media/platform/tegra/camera/vi/channel.clines 776–791
    if (*nplanes) {
        if (sizes[0] < chan->format.sizeimage) {
            dev_info(chan->vi->dev, "sizes[0] = %d chan->format.sizeimage = %d, for num_planes = %d ...\n"
                    , sizes[0], chan->format.sizeimage, *nplanes);
            return -EINVAL;
        }
    } else {
        sizes[0] = chan->format.sizeimage;
    }

    *nplanes = 1;
    alloc_devs[0] = tegra_channel_get_vi_unit(chan);

    if (vi->fops && vi->fops->vi_setup_queue)
        return vi->fops->vi_setup_queue(chan, nbuffers);
    return ret;

The size is sizeimage, a field of the current format. So the format decides the size of a buffer at the moment of the request.

Warning

Buffers that were requested before the format have the size of the old format.

  • Symptom: the capture of a new mode fails at QBUF, or the frames have the size of the earlier mode.
  • Cause: queue_setup reads sizeimage once, when the buffers are requested.
  • Fix: set the format first, then request the buffers. After a format change, free the buffers and request them again.

The count has two limits. vb2 applies its own before the hook runs:

container$ sed -n '872,873p' $VB2/videobuf2-core.c
    num_buffers = max_t(unsigned int, *count, q->min_queued_buffers);
    num_buffers = min_t(unsigned int, num_buffers, q->max_num_buffers);
container$ grep -n 'define VB2_MAX_FRAME' $TREE/kernel/kernel-noble/include/media/videobuf2-core.h
23:#define VB2_MAX_FRAME    (32)

A queue that sets no limit of its own gets VB2_MAX_FRAME, so a request for 300 buffers is granted as 32. The last lines of the hook then pass the count to a second function of the driver. It allows 1 to 240, by two constants in mc_common.h, and on this kernel that range changes nothing. This is why grab.c prints the granted count and uses it.

buf_prepare and buf_queue

vb2 calls buf_prepare at each QBUF, while the buffer is still QUEUED:

Jetson Linux r39.2.1nvidia-oot/drivers/media/platform/tegra/camera/vi/channel.clines 834–847
static int tegra_channel_buffer_prepare(struct vb2_buffer *vb)
{
    struct vb2_v4l2_buffer *vbuf = to_vb2_v4l2_buffer(vb);
    struct tegra_channel *chan = vb2_get_drv_priv(vb->vb2_queue);
    struct tegra_channel_buffer *buf = to_tegra_channel_buffer(vbuf);

    buf->chan = chan;
    vb2_set_plane_payload(&vbuf->vb2_buf, 0, chan->format.sizeimage);
#if IS_ENABLED(CONFIG_VIDEOBUF2_DMA_CONTIG)
    buf->addr = vb2_dma_contig_plane_dma_addr(vb, 0);
#endif

    return 0;
}

The hook stores the address that the hardware writes to. vb2 calls buf_queue when the buffer becomes ACTIVE:

Jetson Linux r39.2.1nvidia-oot/drivers/media/platform/tegra/camera/vi/channel.clines 849–875
static void tegra_channel_buffer_queue(struct vb2_buffer *vb)
{
    struct vb2_v4l2_buffer *vbuf = to_vb2_v4l2_buffer(vb);
    struct tegra_channel *chan = vb2_get_drv_priv(vb->vb2_queue);
    struct tegra_channel_buffer *buf = to_tegra_channel_buffer(vbuf);

    /* for bypass mode - do nothing */
    if (chan->bypass)
        return;

    if (!queue_init_ts) {
        /*
         * Record videobuf2 queue initial timestamp.
         * Note: latency is accurate when streaming is already turned ON
         */
        queue_init_ts = ktime_to_ms(ktime_get());
    }

    /* Put buffer into the capture queue */
    spin_lock(&chan->start_lock);
    list_add_tail(&buf->queue, &chan->capture);
    spin_unlock(&chan->start_lock);

    /* Wake up kthread for capture */
    wake_up_interruptible(&chan->start_wait);
}

The hook adds the buffer to a list and wakes a kernel thread. That thread gives the buffer to the capture hardware, and a second thread returns it. Lesson 11 follows a buffer through both.

The early return for chan->bypass is the bypass_mode control of Lesson 04. When the camera service of NVIDIA owns the camera, the driver accepts a buffer and never fills it.

More detail: why cat /dev/video0 works on the Jetson
  • The file operations of the channel driver set .read = vb2_fop_read.
  • vb2 then emulates read() with the same queue. It requests buffers, streams, and copies each frame to the caller.
  • The emulation returns no sequence number, no timestamp and no error flag. It serves as a first test and nothing more.

5. Three ways to put memory under a buffer

The memory field of VIDIOC_REQBUFS selects where the memory of the buffers comes from. The kernel header has four values, and three are in use:

Jetson Linux r39.2.1kernel/kernel-noble/include/uapi/linux/videodev2.hlines 187–192
enum v4l2_memory {
    V4L2_MEMORY_MMAP             = 1,
    V4L2_MEMORY_USERPTR          = 2,
    V4L2_MEMORY_OVERLAY          = 3,
    V4L2_MEMORY_DMABUF           = 4,
};

The three models differ in one question: who allocates the memory. The answer decides how long the memory lives.

V4L2_MEMORY_MMAP V4L2_MEMORY_USERPTR V4L2_MEMORY_DMABUF
Who allocates The kernel, through the allocator of the queue The program, with malloc Another device or allocator
The program names a buffer by Its index A pointer A file descriptor
Kernel work at each QBUF None Pins the pages and maps them for the device Attaches and maps the buffer, when a new descriptor arrives
The memory lives until The queue is freed The program frees it The last descriptor is closed
Use A program that reads the frames itself Old programs Frames that go to another device or process

MMAP

MMAP is the model of grab.c and of v4l2-ctl --stream-mmap. The kernel allocates each buffer in memory that the hardware can reach. The program maps the same pages. So the only copies are the ones that the program makes itself, such as a write to a file.

USERPTR

USERPTR turns the allocation around: the program brings the memory. The pages behind a pointer of a program can move and are not adjacent. So the kernel pins and maps them at every QBUF, and it releases them afterwards. The model exists for programs that owned their frame memory before V4L2. New code does not use it.

DMABUF

With DMABUF the program queues a file descriptor. The descriptor names memory that another device or allocator provides, such as a buffer of an encoder. The receiver then writes its frame straight into that memory. Section 6 covers the descriptor itself.

What each board accepts

The driver states its models in io_modes:

container$ grep -n 'io_modes' $CH $CFE | sed 's|.*/||'
channel.c:2822: chan->queue.io_modes = VB2_MMAP | VB2_DMABUF | VB2_READ | VB2_USERPTR;
cfe.c:1964: q->io_modes = VB2_MMAP | VB2_DMABUF;

The Jetson driver accepts all three models and the read() emulation of section 4. The driver of the Raspberry Pi 5 accepts two. A request with V4L2_MEMORY_USERPTR fails there, and so does cat on the video node.

Warning

A program that works on one board fails on the other at REQBUFS.

  • Symptom: VIDIOC_REQBUFS returns EINVAL on a Raspberry Pi 5 for a program that runs on the Jetson.
  • Cause: the program requests V4L2_MEMORY_USERPTR, and the queue of that driver does not list it.
  • Fix: use MMAP or DMABUF. Both boards accept them.

6. dmabuf: memory with a file descriptor as its name

dmabuf is not a part of V4L2. It is the kernel's general way to share a buffer between drivers, and V4L2 is one of its users. A dmabuf is a block of memory that a device can reach, with a file descriptor as its name.

The descriptor behaves like any other one. The kernel counts its users. A process can send it to another process over a Unix socket. A driver can take it and map the memory for its own device.

A queue exports a buffer

VIDIOC_EXPBUF takes the index of an MMAP buffer and returns a descriptor for it. The table of section 4 routes the call to vb2, and vb2 asks the allocator:

Jetson Linux r39.2.1kernel/kernel-noble/drivers/media/common/videobuf2/videobuf2-dma-contig.clines 517–524
    dbuf = dma_buf_export(&exp_info);
    if (IS_ERR(dbuf))
        return NULL;

    /* dmabuf keeps reference to vb2 buffer */
    refcount_inc(&buf->refcount);

    return dbuf;

The comment states the consequence. The new dmabuf holds a reference to the memory of the buffer. The allocator drops that reference only when the dmabuf is released:

container$ grep -n 'refcount_inc\|drop reference' $VB2/videobuf2-dma-contig.c
422:    /* drop reference obtained in vb2_dc_get_dmabuf */
522:    refcount_inc(&buf->refcount);

So the same pages now have three names:

One block of memory with three names. The capture hardware writes through a DMA address, the capturing program reads through its mapping, and another process or device maps the dmabuf file descriptor.

The memory outlives the queue

The lifetime follows from the reference. A program can free the buffers of the queue with a count of 0, and the exported memory stays. vb2 names this case in its own code:

Jetson Linux r39.2.1kernel/kernel-noble/drivers/media/common/videobuf2/videobuf2-core.clines 843–850
        /*
         * We already have buffers allocated, so first check if they
         * are not in use and can be freed.
         */
        mutex_lock(&q->mmap_lock);
        if (debug && q->memory == VB2_MEMORY_MMAP &&
            __buffers_in_use(q))
            dprintk(q, 1, "memory in use, orphaning buffers\n");

The queue forgets the buffers, and the memory lives on for the holders of the descriptors. The lab shows this on the board: it frees the buffers, closes the video node, and still reads a frame.

Warning

Exported buffers keep their memory after the capture ends.

  • Symptom: the free memory of the board shrinks with every start of a program, by the size of its buffers.
  • Cause: descriptors from VIDIOC_EXPBUF are still open, in this process or in one that received them.
  • Fix: close every exported descriptor, in every process that holds one.

A queue imports a buffer

The other direction is V4L2_MEMORY_DMABUF. The program requests buffers without memory, and it gives a descriptor at each QBUF. The allocator of the queue attaches to the dmabuf and maps it for the receiver. The frame then lands in memory that another party allocated.

This is how a frame crosses from one device to the next without a copy. A queue of the receiver exports a buffer, and the queue of an encoder or of a converter imports it. What moves between the two is a small integer.

More detail: what dmabuf does not solve
  • Ownership in time. Two holders of a descriptor can use the memory at the same moment. The states of section 2 protect a buffer only inside one queue.
  • The format. A dmabuf is bytes. The width, the height and the pixel format travel in another way, such as the caps of GStreamer in Lesson 18.

dmabuf on a Raspberry Pi 5

The allocator is the same file, so export and import work in the same way. The Raspberry Pi 5 shows the use of it inside the kernel tree. Its ISP has a second driver with queues of its own, and they accept the same two models:

7. The cost of a copy

Lesson 05 computed the load of a mode on the wires. A buffer lives in memory, where every pixel of the Jetson's raw formats takes two bytes. The traffic of the two IMX477 modes follows from the frame size:

container$ echo $((1920 * 1080 * 2)) $((1920 * 1080 * 2 * 60))
4147200 248832000
container$ echo $((3840 * 2160 * 2)) $((3840 * 2160 * 2 * 30))
16588800 497664000

The 60-frame mode writes 249 megabytes into memory in every second. The 4K mode writes 498 megabytes. This is the work of the receiver alone, before any program reads a pixel.

One copy doubles the traffic

A copy reads every byte of a frame and writes it again. One copy of the 4K stream adds 498 megabytes of reads and 498 megabytes of writes in every second. That is one gigabyte of memory traffic with no new information in it.

A pipeline with a copy at each step multiplies this. The memory of the SoC is shared: the ISP, the GPU, the encoder and the programs all use the same memory bus. A copy also takes processor time, and a 16.6-megabyte frame pushes other data out of the caches.

The time is limited too. At 60 frames in a second, a frame has 16.7 ms. A step that needs longer holds its buffer, the queue runs empty, and section 2 named the result.

The design that follows

Both mechanisms of this lesson exist to remove copies. MMAP removes the copy from the kernel to the program. dmabuf removes the copies between devices. With both, a frame is written once by the receiver, and every later stage maps the same pages.

So the rule for a camera pipeline is to count its copies. Lesson 18 counts them in a GStreamer pipeline.

Warning

A pipeline that works at a small mode drops frames at the full mode.

  • Symptom: the frame rate falls when the resolution rises, and the processor load is high.
  • Cause: a stage copies each frame, and the copy takes longer than one frame time at the larger size.
  • Fix: find the stage that copies, and pass the buffer as a dmabuf in its place.

The same arithmetic on a Raspberry Pi 5

The receiver of the Raspberry Pi 5 can store raw frames packed, so a pixel takes less than two bytes. Its driver rounds each line up to a multiple of 16 bytes. The full mode of the IMX477 there is 4056×3040 at 12 bits and 10 frames in a second:

container$ echo $(( (4056 * 12 / 8 + 15) / 16 * 16 )) $(( (4056 * 12 / 8 + 15) / 16 * 16 * 3040 )) $(( (4056 * 12 / 8 + 15) / 16 * 16 * 3040 * 10 ))
6096 18531840 185318400

A line has 6096 bytes, a frame has 18.5 megabytes, and the stream writes 185 megabytes in a second. The rule about copies is the same on both boards.

Self-check

A buffer is ACTIVE. Which code may write to its memory, which code may read it, and which call ends this state?
Show the answer
  • The capture hardware may write to it. Nothing may read it.
  • The driver ends the state with vb2_buffer_done, which makes the buffer DONE or ERROR.
A program requests 2 buffers on a Raspberry Pi 5 and 300 buffers on the Jetson. How many does it get on each board, and which code decides?
Show the answer
  • 3 on the Raspberry Pi 5, where queue_setup raises the count. 32 on the Jetson, where vb2 limits it before the hook runs.
  • The count of VIDIOC_REQBUFS is a request, and the kernel writes the granted count back.
The offsets of four buffers are 0x0, 0x8000, 0x10000 and 0x18000, and each buffer has four megabytes. What is an offset?
Show the answer
  • A ticket for mmap. It holds the index of the buffer, shifted left by 15 bits with pages of 4 KB.
  • It is not an address and not a position in a file.
A capture on the Jetson returns the sequence numbers 1 to 8 without a gap. One step between two timestamps is 33.3 ms, and the others are 16.7 ms. What happened?
Show the answer
  • One frame was lost, most likely because no buffer was ACTIVE when it arrived.
  • The Jetson driver counts the buffers that it returns, so its numbers show no gap. The timestamps show the lost frame.
A program sets a new format and then captures with the buffers that it requested earlier. Why can this fail?
Show the answer
  • queue_setup took the size of a buffer from sizeimage at the time of the request.
  • A larger format does not fit into those buffers. The program must free them and request new ones.
Which memory model does a program choose when it only saves frames to a file? Which one when the frames go to an encoder?
Show the answer
  • MMAP for the file. The program reads the frames itself, and the kernel allocates the memory.
  • DMABUF for the encoder. The frame passes as a descriptor, and no stage copies it.
A program exports four buffers, frees the queue with a count of 0, and exits without closing anything. Is the memory of the buffers lost?
Show the answer
  • No. The kernel closes all descriptors of a process when it exits, and the last close releases each dmabuf.
  • The memory stays only if another process still holds a descriptor.
Compute the memory traffic of the 4K mode of the IMX477 with one copy in the pipeline.
Show the answer
  • The receiver writes 3840 × 2160 × 2 × 30 = 497,664,000 bytes in a second.
  • The copy reads the same amount and writes it again. The total is 1,492,992,000 bytes in a second, three times the traffic of the receiver.
